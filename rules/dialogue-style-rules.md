# 对话语气与表情规则 V3

> 当前规则服从 `docs/product/CURRENT_EFFECTIVE_REQUIREMENTS_LEDGER_20260825.md`。本文件只负责用户可见对话语气，不定义业务状态、内容方向或创作正文格式。

## 目标

当前三个用户入口（IP 人设、脚本改写、小红书排版）的对话都应自然、简洁、专业，不像后台表单或工程日志。适量 emoji 可用于关键节点，但不能掩盖信息或改变业务含义。

## 使用范围

适用于：
- IP 人设问答；
- 脚本改写过程中的提示、确认、反馈；
- 小红书排版过程中的提示、确认、反馈；
- Loading / 已完成 / 重试等用户可见状态文案。

`SUPERSEDED`：独立“内容规划问答”已撤销，不再作为当前用户入口；历史兼容代码不得据此恢复产品功能。

不用于：
- 用户自己的消息；
- 可复制的脚本正文/小红书正文；
- 固定合规声明；
- 数据、编号、错误详情等必须精确呈现的内容。

## 用户可见文案：说人话，不暴露内部实现

“结构化解析、上下文、字段匹配、生成链路、模型调用、阅读节奏处理”等属于内部实现语言，不能直接作为普通用户等待提示。

处理中提示应：
1. 简单直白；
2. 1 句优先，必要时不超过 2 句；
3. 不解释内部步骤；
4. 不使用夸张、油腻或营销式口吻；
5. 由公共状态组件统一管理，同一种状态不能多处各写一套文案。

### 当前固定 Loading 文案

- 小红书排版：`正在排版，请稍候…`
- 脚本改写：`正在改写，请稍候…`

以上属于当前产品固定口径。旧的“见证奇迹”“正在整理手机阅读节奏”“马上给你三版”等历史文案不得覆盖公共 Loading Owner。

IP 资料理解/方案生成等非固定状态可以保持自然简洁，但仍不能暴露内部处理步骤。

## 普通对话 Emoji 密度

- 不要求每条助手消息都有 emoji；
- 普通聊天约每 2～4 条消息出现一次视觉点缀即可；
- 完成、提醒、下一步等关键节点可优先使用；
- 同一条普通消息原则上最多 1 个 emoji。

注意：本节只约束**产品对话气泡**，不约束“小红书正文排版”的 Emoji 密度。小红书正文必须服从 `rules/xhs-formatting-rules.md` 的专项硬规则（平均每 1～2 句话至少一个锚点、任意连续两句至少一个）。

## 语义匹配

可使用常见语义表情：
- 资料 / 填写：📋
- 完成：✅
- 下一步：🧭
- 方案：✨
- 内容方向：💡
- 提醒 / 合规：📌
- 普通轻互动：🙂 / 👀

不使用夸张、暧昧、庆功感过强或明显营销化的表情组合。

## 实现原则

- 表情属于表现层，不得改变业务状态；
- 不为了加 emoji 修改用户原文或正式创作结果；
- Loading 由公共创作状态 Owner 管理；
- 自动测试优先验证“固定 Loading 不泄露内部术语、公共状态唯一、业务不受影响”，而不是逐条锁死普通聊天文案。
