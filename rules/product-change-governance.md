# 产品修改与回归治理规则

> 长期规则。目的：从工程流程上防止“这次改好了，下一次修改别处后旧问题又回来”。
> 适用于 AIA Auto IP 后续所有产品修改、Bug 修复、Preview 验收与发布。

## 1. 核心原则：修改不是累加制，而是版本制

1. 同一功能存在多次需求时，以**最新明确确认的产品决策**为当前有效规则。
2. 新需求只覆盖其明确修改的维度；未冲突的旧规则继续有效。
3. 被新需求替代的旧需求必须标记为 `SUPERSEDED`，不得继续驱动代码、Prompt、测试或 UI。
4. 历史聊天、历史 PR、旧 Vxx 脚本不能作为当前产品规则的最高事实源。
5. 当前最高产品事实源为最新的 `docs/product/CURRENT_EFFECTIVE_REQUIREMENTS_LEDGER_*.md`；专项规则负责其对应维度的详细实现口径；`CURRENT_PRODUCT_RULES_BASELINE_*.md` 保留为上一版产品基线快照，不得覆盖更新日期更晚的有效需求总账。
6. 如果最新总账明确把某个细节委托给专项规则（例如小红书 Emoji 密度），以该专项规则的当前有效版本为准。

## 2. 单一规则源（Single Source of Truth）

每个核心业务输出只能有一个 owner：

- `primaryGoal`：拓客 / 增员目标判断
- nickname policy：昵称判断与推荐
- bio policy：简介主体
- content policy：保险主线 / 内容支线
- compliance policy：声明、执业编号、复制合规
- recommendation policy：脚本推荐与去重
- shared UI component：多选、复制反馈、弹窗、悬浮入口等公共交互

禁止：

- 多个 Vxx 文件同时修改同一个最终字段；
- `renderProposal()` 被多层 wrapper 反复包装；
- MutationObserver 在渲染完成后再次修改核心业务数据；
- AI、前端补丁、后端分别生成同一份声明/执业编号；
- 为修一个回归问题继续新增 V34/V35 等“最后覆盖层”。

如果发现同一输出有多个 owner，必须先收口 owner，再修产品问题。

## 3. 修改前必须做影响范围检查

每次修改前先回答：

1. 当前需求属于哪个 owner？
2. 当前字段/组件还有哪些旧文件会写它？
3. 新需求是否替代历史需求的某个维度？
4. 哪些已有功能可能被这次修改影响？
5. 最新有效需求总账中，这个维度的当前状态是什么？

未完成以上检查，不直接写“最后覆盖补丁”。

## 4. 已确认问题必须变成回归测试

产品验收中发现并确认的问题，修复时必须同步增加 regression test / contract test。

典型永久回归案例包括但不限于：

- 昵称“无”不得判断为建议保留；
- QS 前 100 不得推断具体大学；
- 昵称必须有且只能有一个称呼；
- 健康养生不得进入保险主线；
- IP方案与脚本推荐必须读取同一个内容支线；
- 每个简介的执业编号只能出现一次；
- 一句话 IP 定位不带称呼；
- 多选标签后 Enter 可直接发送；
- 推荐脚本不得重复、不得空白；
- 复制改写/排版结果必须有成功反馈；
- 客户反馈按问题分组展示；
- 个人介绍必须展示并参与资料语义提取。

原则：**同一个已确认问题不应该再依赖产品负责人第二次人工发现。**

## 5. 测试分层，避免浪费 Actions

### 开发阶段
只跑与当前 owner 和影响范围直接相关的必要测试；连续完成同一阶段修改，不因每个小改动重复完整 QA / Preview / 发布。

### 自然验收节点
统一执行：

1. 当前 owner contract tests；
2. 与其依赖关系有关的 regression tests；
3. 固定真实营销员样本回归；
4. 必要的页面 smoke test；
5. 再统一部署一次 Preview。

### 合并 main 前
才执行完整 QA / 发布门禁。

GitHub-hosted Actions 不作为日常每次小改动的默认执行环境；能在 ECS/self-hosted/本地完成的阶段检查优先使用低成本方式。

## 6. 固定真实样本回归

维护一组固定验收样本，至少覆盖：

- 主要拓客；
- 主要增员；
- 报名资料“两者都要/打造专业形象”；
- 强学历但学校不明确；
- 强过往职业；
- 多兴趣；
- 无昵称；
- 客户反馈丰富；
- 有真实服务字段；
- 无完整资料。

每次核心 IP 规则变化时，用相同样本比较修改前后结果，避免修 A 坏 B。

## 7. 输出契约

核心输出先定义结构，再允许 AI 负责自然语言。

例如简介：

- `body`：人物简介主体；
- `complianceFooter`：固定声明、营销服务部、执业编号。

只有 `complianceFooter` 可以输出执业编号。AI、简介模板和旧渲染层都不得再次追加。

同理，内容方向必须先形成标准化 `insuranceMainline` / `secondaryContent`，IP方案和推荐脚本共同读取，不得各自重新推断。

## 8. Preview 前的“禁止复活”检查

每次统一 Preview 前必须检查：

1. 当前页面实际加载了哪些规则脚本；
2. 已停用的 Vxx 文件是否仍被 `index.html` 引用；
3. 同一核心字段是否仍有多个写入点；
4. 是否存在后加载脚本重新覆盖当前规则；
5. 是否存在 MutationObserver/DOM patch 改写核心业务结果；
6. 最新有效需求总账中的本阶段条目是否都有实现或明确未实现状态；
7. 历史 `SUPERSEDED` 规则是否意外重新出现；
8. 专项规则与总账委托维度是否一致，测试是否仍在验证旧规则。

任一项失败，不进入产品负责人 Preview 验收。

## 9. 产品负责人验收边界

产品负责人主要验收：

- 业务逻辑是否符合真实使用场景；
- 推荐内容是否合理；
- 产品表达是否符合预期；
- 新需求方向是否正确。

工程侧应在交付 Preview 前主动发现：

- 页面空白；
- 重复字段；
- 按钮失效；
- 旧规则复活；
- 多选 Enter 失效；
- 重复脚本；
- 固定文案错误；
- 明确违反 contract 的输出。

不得把这些基础回归问题长期转嫁给产品负责人逐项人工发现。

## 10. 失败先诊断

Actions、Preview、部署、接口或页面失败时：

1. 先读取日志/网络错误/实际加载链；
2. 确定根因；
3. 一次修复；
4. 再验证。

禁止连续提交“试试看”的 commit 来碰运气，避免浪费 Actions 分钟和开发额度。

## 11. 阶段完成标准（Definition of Done）

一个产品修改只有同时满足以下条件才算完成：

- 当前有效需求已写入/更新最新有效需求总账；
- 旧冲突规则已标记替代或失去写权限；
- 代码只有一个最终 owner；
- 已确认缺陷有回归测试；
- 影响范围测试通过；
- Preview 前禁止复活检查通过；
- 产品验收通过后才进入合并 main 建议节点。

仅仅“页面现在看起来对”不等于完成。
