# AIA-Auto-IP · 友邦 AI 内容工作台

面向友邦营销员培训与日常使用的 AI 网页工具。当前用户可见主要功能包括：

1. IP 人设
2. 脚本推荐
3. 脚本改写
4. 小红书排版

项目同时沉淀方法论、Prompt、合规规则、业务规则、Web 实现、自动测试和部署流程。

## 当前技术形态

- 前端：`web/` 下原生 HTML / CSS / JavaScript
- 后端：Python `server.py`
- AI：DeepSeek API
- 数据库：正式环境使用阿里云 RDS；Preview 使用独立 SQLite 测试数据库
- 自动测试：Playwright + axe-core + contract/regression tests
- 部署：开发阶段优先 ECS/本地轻量检查；自然验收节点统一 Preview；正式发布才走 main 门禁

> 当前项目采用渐进式工程化，不为了局部需求强制重构到大型前端框架。通用工程能力优先复用成熟方案，AIA Auto IP 独有业务流程才重点自定义。

## 核心业务设计

### IP 人设

- 根据已有营销员报名资料、个人介绍、客户反馈和历史档案自动跳过已知字段，只追问缺失信息；
- 自我介绍需要语义提取过往职业、长期身份、爱好等真实信息并回填资料；
- 营销员编号只用于身份识别和资料匹配，**不得**自动当成执业证编号；
- 最终自媒体业务目标 `primaryGoal` **只能二选一：拓客 / 增员**；
- 报名资料若是“两者都要”“打造专业形象”“个人品牌”等非唯一目的，进入 IP 对话后必须重新询问并收束到拓客或增员；
- 账号表达风格参与后续脚本改写，并按脚本题材自动调整强弱；
- 资料完整后生成 IP 方案；
- 昵称、简介、一句话定位、内容方向遵循当前产品规则基线和合规规则。

### 内容方向

IP 方案中的板块名称为 **“内容方向”**，只分：

1. **保险主线**：由 `primaryGoal` 和真实保险业务资料决定；
2. **内容支线**：从家庭/生活身份、过往职业、自我介绍、爱好、客户反馈等真实证据中综合排序后选择。

硬边界：

- 健康养生、育儿、美食、读书、旅行、智能家居、运动等属于内容支线候选，**不得进入保险主线**；
- IP 方案和脚本推荐必须读取同一个标准化主线/支线结果；
- 支线候选排序规则见 `product-rules-v14.js` / `rules/content-branch-ranking-v1.md`；
- 最终业务输出由 `web/ip-policy-core.js` 唯一负责。

### 昵称

- 推荐昵称必须有且只能有一个人物称呼；
- 称呼优先来自客户反馈中的高频真实称呼，其次本人填写称呼，再次才是姓名自然化；
- “无/暂无/没有”等必须识别为空；
- 不得从 QS 前 100 推断具体学校；
- 不得机械生成“成都+称呼”“TOT+称呼”“985+称呼”“有温度+称呼”等；
- 原有昵称应谨慎评价，好昵称优先建议保留；不同平台建议统一，避免频繁改名；
- 最终推荐昵称唯一 Owner：`web/nickname-policy-v1.js`。

### 简介

简介从真实资料中选 3～5 个有价值的信息点，自然表达“我是谁、为什么值得关注、主要分享什么、有什么真实特色”，不得做标签墙。

- 信息来源：个人介绍、过往职业、家庭身份、学历、从业年限、真实荣誉、客户反馈、真实服务字段、保险主内容方向；
- 保险/增员业务必须是账号主内容，生活兴趣只能作为次要人设；
- 不得出现“二孩宝妈｜宝妈”“宝妈｜环保工程师”“靠谱”单独一行等机械拼接；
- 服务型版本可使用 `养老规划｜保障规划` 等，但只能来自真实资料；
- 简介正文唯一 Owner：`web/ip-policy-core.js`。

### 简介合规尾部

- 小红书：正文 → 最后一句固定个人意见声明；
- 视频号 / 抖音：正文 → **个人意见声明 → 营销服务部 → 执业证编号**；
- 三项必须连续，且每项只出现一次；
- 营销员编号与执业证编号严格分离；真实执业证编号暂未采集时，预览使用 `000` 占位；
- 合规尾部唯一 Owner：`web/ip-policy-core.js`；复制前合规弹窗仅由 `web/product-rules-v10.js` 做 UI 展示，不得再次生成简介。

### 脚本推荐

- 有 IP 方案：展示“保险主线 + 内容支线”两板块；
- 两板块独立支持“换一批”；
- 推荐脚本不得重复；
- 页面展示今日日期；
- 无 IP 方案：按一级/二级标签浏览脚本库并支持分页；
- IP 方案和推荐页不得各自重新推断内容支线。

### 脚本改写 / 小红书排版

- 智能改写需要代入账号表达风格，不只代入称呼；
- DeepSeek 返回结构偶发异常时先自动重试/宽容解析，不把“重新提交原文”的成本直接丢给用户；
- 小红书排版不得出现单个括号/标点独占一行等不合格排版；
- 复制改写或排版结果必须以真实复制成功为前提显示成功反馈。

## 防回归工程规则

项目已经禁止继续使用“V34/V35 最后覆盖层”式开发。

每个核心业务输出只能有一个 Owner。历史文件如果仍需兼容，只允许做 UI、数据标准化或辅助计算，不能再写最终业务字段。

已确认缺陷必须转成 contract/regression test。Preview 前必须检查：

- 实际脚本加载链；
- SUPERSEDED 文件没有重新加载；
- 同一字段没有第二写入点；
- 当前 Owner contract tests 通过；
- 影响范围回归通过；
- 页面 smoke 没有空白、重复字段、按钮失效等基础回归。

详见：

- `rules/product-change-governance.md`
- `rules/product-rule-ownership.md`
- `docs/项目管理/产品修改防回归规则.md`

## 开发与发布流程

当前默认流程：

`需求 → 读取当前规则基线/Owner/任务看板 → 影响范围检查 → 开发分支连续开发 → owner/回归测试 → 自然节点统一 Preview → 产品验收 → 明确允许上线 → 合并 main → 完整 QA → 正式 ECS → 健康检查 → 更新管理文档`

长期原则：**开发优先、阶段验收、一次发布、失败先诊断。**

硬性规则：

- 不为每个小改动重复完整 QA / Preview / 正式发布；
- QA 全绿不等于允许正式上线；
- 未经明确授权，不自行合并 main；
- 普通需求不直接在正式 ECS 上试错；
- Preview 与正式数据保持隔离；
- Actions / 部署失败先读取日志判断根因，不连续提交试错；
- GitHub-hosted Actions 不作为日常小修改的默认执行环境，能在 ECS/self-hosted/本地完成的检查优先低成本执行。
