# AIA IP 人设生成 PRD V1

> 状态：**DRAFT / 持续增量审计中**  
> 日期：2026-09-08  
> 范围：推荐昵称、一句话 IP、推荐简介及其资料、证据、合规、稳定稿和页面交互。  
> 工作方式：本文件是持续累加 Draft。已经确认的规则只做增量修改，不因后续审计重新生成整份 PRD。发现遗漏时补充具体 Rule ID；冻结前必须完成 Rule Coverage Audit。

## 0. 规则治理

- **GOV-001**：本 Draft 固化当前已确认规则；冻结后升级为本子系统唯一产品事实源。
- **GOV-002**：冻结条件：全部 ACTIVE 历史规则映射到具体 Rule ID，`ACTIVE 未映射=0`、`CONFLICT=0`。
- **GOV-003**：冻结后历史 nickname/headline/bio 规则文件统一标记 `DEPRECATED / SUPERSEDED BY AIA_IP_PERSONA_PRD_V1`，仅保留历史追溯价值，不再拥有运行态、开发或测试的当前规则权威。
- **GOV-004**：后续新增规则以增量 Rule ID 修订本文件，不恢复多层继承链。

## 1. 数据与证据

- **DATA-001**：生成输入读取报名/基础资料、个人介绍、客户反馈、历史账号资产、人工确认昵称预设、当前稳定稿以及本次新增真实资料。
- **DATA-002**：昵称完整输入至少包括：原昵称、基础资料/本人自我介绍、客户/身边人真实称呼、高频评价、他人角色认知、愿意咨询/交流的话题、身份/经历/兴趣、账号目标/目标人群和合规规则。
- **DATA-003**：自媒体运营经验只用于了解运营基础，不属于对外人设资产。账号运营时长、平台、粉丝、播放、作品、咨询、留资以及由自媒体产生的成交/增员等不得进入推荐昵称、一句话 IP、推荐简介，也不得参与强事实竞争。主持人、记者、媒体从业者等真实职业经历可按职业事实处理，但账号运营成绩仍排除。
- **EVID-001**：证据等级：A=报名/基础资料明确事实；B=本人自我介绍明确表达；C=合格客户/身边人反馈；D=AI 推断。A/B/C 可进入候选；D 原则上不得作为最终人物事实。
- **EVID-002**：事实强度只能保持或降低，不得由关键词、类别或 AI 推断升级成具体职业、资质、经历、服务能力、婚育情况、学校、国家等事实。
- **EVID-003**：原始资料存在明确时间/数字精度时必须保留，不得把 `7年+` 随意改成“多年”；无年限证据不得补“多年/长期”。
- **EVID-004**：人物资产竞争优先级：稀缺且具体事实 > 有数字经历 > 有证据强反差/转型 > 专业资质/荣誉 > 客户反馈稳定特点 > 有记忆点生活身份 > 普通兴趣 > 泛化形容词。
- **EVID-005**：当前行业从业不足5年默认不作为推荐简介/一句话 IP 卖点；满5年可参与竞争但不是必选。原始资料保留。
- **EVID-006**：A1、PA转任、团队1+2等行业内部职级/黑话默认不作为陌生客户卖点。MDRT/COT/TOT 等有专项有效规则的真实荣誉仍参加真实性、价值和合规竞争。

## 2. 稳定稿与增量更新

- **STABLE-001**：生成顺序首先读取现有稳定稿，再读取新增真实资料。
- **STABLE-002**：已有真实、合规、成立的稳定内容默认保护；新增资料采用增量补充，不无故整体重生成。
- **STABLE-003**：仅在新增资料证明原内容事实冲突、原内容违反最新规则/合规、新增事实明显更强需要竞争，或用户明确要求修改时，允许替换原稳定内容。
- **STABLE-004**：增量更新后仍重新执行事实、去重、长度、Emoji、平台合规、固定声明和总字数门禁。
- **STABLE-005**：资料不足时允许少于默认信息量，不得为满足格式编造内容。

## 3. 推荐昵称

- **NICK-001**：昵称目标是像真实的人、顺口、好记、好搜、有稳定识别；首选尽量有记忆点和网感，但证据不足时宁缺毋滥。
- **NICK-002**：每个最终昵称必须有且只有一个人物锚点。不得只有地域、荣誉、行业标签等而没有人物主体。
- **NICK-003**：人物锚点优先：客户/身边人高频真实称呼 > 本人明确希望使用称呼 > 成熟合规原昵称中的稳定人物锚点 > 长期英文名 > 本名/自然两字以上姓名片段兜底。禁止无证据随意截取姓名单字、机械加“哥/姐”或创造小名。
- **NICK-004**：多个真实称呼同频时依次比较：公开使用自然无歧义、亲和力、记忆度、发音/输入简单、与真实姓名关联、是否便于与真实鲜明特点组合、是否符合账号表达风格。
- **NICK-005**：当 `nicknamePreset.status=approved` 时，`nicknamePreset.primary` 固定为系统默认首选，优先于 AI 临时生成和通用规则重新组合。AI 不得自行写入 `approved`；预设仅覆盖昵称，不改其他真实资料。`allowAiFallback=true` 时 AI 可在用户要求修改、补候选或预设不足时产生受控补充候选，但不得顶掉人工首选。人工首选变化应更新 preset，而不是关闭 AI fallback。
- **NICK-006**：已有自然、合规、有特色、有用户记忆的成熟原昵称优先保护，不为“体现规则”机械加修饰语或改坏。
- **NICK-007**：过往职业不得进入新生成推荐昵称；即使加“前”也不作为默认路线。当前仍真实持续的生活身份、兴趣、内容特点可以有证据地参与。
- **NICK-008**：客户评价可辅助人物印象和创意，但普通“靠谱/专业/真诚”等不得机械变成昵称前缀。只有足够鲜明、自然、有明确证据且提升辨识度的修饰语才可参与。
- **NICK-009**：新昵称默认不用 Emoji、特殊符号、花体/装饰繁体、装饰标点、无意义数字尾缀。全英文原则上不做首选；中英混合时中文部分必须承担人物记忆或语义识别。
- **NICK-010**：禁止动作标题句、重复人物主体、字段机械拼接、生硬难念组合。`XX的小世界/XX的日常/XX聊生活/XX看世界` 等万能模板不作为批量默认路线；成熟原昵称例外按保护规则判断。
- **NICK-011**：通常推荐3–5个真正不同路线；纯姓名、真实称呼及极简变体合计最多2个。只有2–3个好候选时不凑满5个。
- **NICK-012**：首选不默认裸本名/裸称呼。存在真实鲜明、当前成立且自然的兴趣/生活/内容特点或鲜明评价时，应优先尝试“记忆点+人物锚点”等有辨识度组合；资料不足才回退裸称呼/本名。
- **NICK-013**：Nickname Memory Score 为确定性排序门禁：成熟受保护原昵称 +3；当前真实鲜明兴趣/生活/内容特点 +3；真实高频人物称呼锚点 +2；有证据鲜明记忆点修饰语 +2；裸姓名/裸称呼 0；姓名/称呼+无意义数字 -2；全英文或英文+无意义数字 -3；万能模板 -5。
- **NICK-014**：Memory Score 同分顺序：成熟原昵称 > 有证据鲜明修饰语 > 当前兴趣/生活/内容特点 > 真实称呼 > 本名。存在通过事实和自然度门禁的高分特色候选时裸姓名/裸称呼不得排第一；没有合格特色候选时不得为了分数造标签。
- **NICK-015**：原昵称必须独立给出“建议保留 / 建议优化 / 不建议保留”及稳定具体理由，依次检查合规、用户记忆、自然顺口、真实人物感、明显优化项、中文记忆/输入/搜索。已有人工固定结论时优先读取人工结论，AI 不得每次随机重写理由。
- **NICK-016**：系统不主动推荐含 `保险 / 友邦 / 友邦保险 / 友邦人寿 / AIA` 的新昵称；已有含相关词原昵称只进入谨慎审查，不自动推荐。
- **NICK-017**：AI 只负责在受控范围内补充候选和自然语言组合；最终事实、合规、排序和首选由确定性 Owner 决定。

## 4. 一句话 IP / Canonical Headline

- **HEAD-001**：一句话 IP 是简洁自我介绍/记忆句，不是标签墙、业务说明或履历堆砌。
- **HEAD-002**：使用2–3个最强真实特点，执行 `账号目的 × 我的不同之处 × 目标人群关注内容 → 我的IP`，但不强制把“我是谁/优势/价值”全部塞入一句。
- **HEAD-003**：资产优先级遵守 EVID-004；不得用无证据的“0人脉/多年/擅长/懂XX/专家/导师/顾问”等表达。
- **HEAD-004**：禁止机械模板如“从XX跨界，用自己的经验讲清……”以及“靠谱/真诚是我的标签”“XX是我的专业底色”“做一个让人记得住的人”等空泛表达。
- **HEAD-005**：不使用姓名/昵称作为句首锚点，不写职业+转型+行业+荣誉标签墙，不使用 `｜` / `|` 拼标签。
- **HEAD-006**：数字与时间精度遵守 EVID-003。
- **HEAD-007**：`proposal.headline` 是 canonical 单一来源：IP 顶部一句话 = 小红书简介固定声明前的 headline = 视频号/抖音固定尾部前的 headline，必须逐字一致；Bio 不得自行截断、改写或另造 slogan。
- **HEAD-008**：因为 headline 复用于小红书简介，必须通过小红书共同合规门禁。

## 5. 推荐简介

- **BIO-001**：简介必须回答“我是谁 / 我的优势 / 我能提供什么价值”，各维度按真实资料丰富程度使用1–3行，不要求平均分配。
- **BIO-002**：素材优先级：差异化身份/经历 > 强专业背书 > 真实内容/服务价值 > 有证据客户评价结论 > 有定位价值地域 > 真实兴趣 > 普通泛化形容词。
- **BIO-003**：跨行必须做语义去重。重复时保留：具体量化事实 > 明确身份/经历/资质 > 明确荣誉 > 模糊概括 > AI 总结。
- **BIO-004**：客户反馈进入简介只呈现结论，例如 `靠谱｜细致｜有耐心`；禁止“客户高频评价/客户都评价我/大家眼中的我/多位客户认为/多人评价/多人反馈”等系统解释前缀。本人自评不得升级为多人反馈。
- **BIO-005**：兴趣只使用真实资料；不机械限制1–2个，空间允许且有助人设时可保留多个。
- **BIO-006**：可提供服务仅使用明确真实资料，不因营销员身份、目标或为了凑行推断。数量不机械限制；每个服务项 **≤6个汉字**，使用 `｜` 分隔，并受平台合规和总字数预算共同约束。
- **BIO-007**：每人只输出1套小红书最终简介和1套视频号/抖音共用最终简介；除固定声明和明确平台合规差异外，人物正文默认使用同一套真实信息。
- **BIO-008**：正文默认至少3行（不含固定合规声明/尾部）。只有真实资料不足、继续增加会造成重复、空话或推断时允许少于3行；绝不能为凑3行编造。
- **BIO-009**：单行去除 Emoji、标点和分隔符后，有效内容优先约12–20个汉字等效长度；21–25仅在保持语义完整且无法自然压缩时允许；**25为绝对上限**。
- **BIO-010**：短资产不足12时按顺序处理：寻找同维度真实信息合并 → 凝练重组 → 并入同一核心问题的相邻行 → 仍不足则不强制独立成行。不得用空话补长度。
- **BIO-011**：每行保持同一语义维度。真实性和语义一致优先于填满空间；经历/荣誉等原则上清晰分开，短资产可与同属“我的优势”的自然信息合并。
- **BIO-012**：正文各行长度尽量均衡，不为等长增加废话。
- **BIO-013**：每个正文行使用不同 Emoji 作为视觉锚点；不重复 Emoji；`👤` 退出推荐模板。
- **BIO-014**：canonical headline 插入人物正文之后、平台固定合规尾部之前；它不受正文单行 Emoji/行宽格式重写，但必须原样复用。
- **BIO-015**：**小红书、视频号、抖音完整简介总长度均≤100个汉字等效字符**，预算包括人物正文 + canonical headline + 固定声明/固定尾部。先预留 headline 和固定尾部预算，再生成/压缩人物正文；固定声明不得为适配长度而删改。

## 6. Compliance Matrix

合规来源统一标记：`P=平台公开可验证规则`、`C=公司/项目合规要求`、`A=AIA Auto IP 主动采用的更严格产品策略`。没有充分平台公开依据时，不把内部安全策略冒充平台官方规则；但产品门禁本身继续执行。

- **COMP-001 [P/C]**：简介不得包含电话、微信、邮箱、QQ、微博、二维码、URL/站外联系方式或其他导流信息；以当前可验证平台规则和公司要求中的更严格者执行。
- **COMP-002 [A/C]**：小红书推荐简介正文和 canonical headline 禁止 `保险、金融、理财、贷款、股票、基金、医疗、护理、教育、玄学` 等当前产品敏感行业词；小红书简介正文禁止 `友邦 / AIA` 品牌字。除非后续有权威来源重新分类，不声称这些全部都是平台官方普遍禁词。
- **COMP-003 [C/A]**：小红书个人简介不得输出执业证编号。
- **COMP-004 [C]**：小红书固定最后一句逐字为：`本账号所述内容为个人意见，不代表任何官方意见。` 必须最后出现，不得改写、缩短或重复。
- **COMP-005 [C]**：视频号/抖音末尾固定连续三行且顺序不变：`本账号上所陈述或表达的内容仅为我个人意见，并不代表友邦人寿的意见`；`营销服务部：XXX`；`执业证编号：XXX`。
- **COMP-006 [C]**：营销员编号 ≠ 执业证编号，绝不能用 agentId 冒充。营销服务部/执业证编号缺失时 AI 不得编造。
- **COMP-007 [C/A]**：历史 Preview `000` 仅视为旧技术占位策略，**正式推荐、复制、稳定稿和 Production 输出禁止使用 `000` 伪装真实执业证编号**；缺失字段必须进入缺失处理并在正式输出前补真实值。
- **COMP-008**：平台合规过滤必须发生在最终推荐展示之前，而不是“先生成不合规稿、复制时再提醒”。固定合规尾部由唯一 Owner 追加，Prompt/AI/历史 Vxx 不得重复生成。
- **COMP-009**：合规门禁不得反向篡改真实事实；不合规素材应淘汰、替换为同事实的合规表达或不进入最终稿，不能创造新事实。

## 7. 页面与 Interaction Contract

- **UI-001**：本轮重写目标是人设生成 Engine，不默认重做成熟页面。除本 PRD 明确修改项外，现有已经成熟且正确的页面布局、视觉和交互保持。
- **UI-002**：IP 方案继续展示推荐昵称候选/首选、原昵称判断、一句话 IP、小红书简介、视频号/抖音简介及相关操作，不因 Engine 重构删减成熟功能。
- **UI-003**：昵称/简介标题保留 `?` 合规入口；点击只展示合规说明，不改变卡片布局。
- **UI-004**：第一次复制相关输出时显示与当前平台相关、能指导行动的合规提醒；后续复制保留明确成功反馈。合规提醒不能替代生成前硬门禁。
- **UI-005**：用户点击“就按这个改”时生成新的 proposal 版本，历史版本不可变；用户明确修改事实字段时先更新事实，再只重算受影响输出。
- **UI-006**：用户修改要求不能绕过真实性和合规门禁；不得因为用户要求而生成无证据头衔/经历/资质或不合规输出。
- **UI-007**：稳定稿读取和展示遵守 STABLE 规则；新增资料不导致页面随机换稿。
- **UI-008**：内容方向与脚本推荐成熟能力继续保留；有 IP 方案时读取 canonical 人设推荐，无 IP 方案时仍允许按现有脚本库逻辑浏览并提示完成人设。
- **UI-009**：脚本详情仅保留一组“上一篇/下一篇”，位于文章正文底部；固定底部工具栏仅保留“脚本改写 / 小红书排版”。从 IP 推荐或无 IP 脚本库进入均适用，切换上一篇/下一篇后滚动回顶部。
- **UI-010**：响应式布局继续遵守现有成熟桌面/平板/手机体验；本 PRD 不授权因 Engine 重构恢复已废弃的浮层/旧版布局。

## 8. Engine 与唯一 Writer

- **ENG-001**：目标生成链：`Stable Output Resolver → Profile Facts → Evidence Engine → Asset Ranking → Nickname Builder → Headline Builder → Bio Builder → Compliance Gate → Canonical Output → UI`。
- **ENG-002**：AI 只负责受控语言候选，不负责决定事实真伪、证据等级、合规放行、人工 preset 优先级或最终确定性排序。
- **ENG-003**：nickname/headline/bio 每个最终字段只能存在一个运行态 Writer/Owner；旧 Prompt、旧 Vxx、fallback、stable runtime 不得形成第二写入权。
- **ENG-004**：新 Engine 先独立实现并用 Contract 验证，再切换页面读取；确认旧 Writer 不再运行后再退役历史 Writer，避免补丁叠加。
- **ENG-005**：统一生成顺序：`读取现有稳定稿 → 读取新增真实资料 → 排除自媒体运营素材 → 事实证据分级 → 人物资产竞争 → 低价值从业年限/内部黑话过滤 → 昵称/IP/简介生成或增量补充 → 计算平台总字数预算 → 平台合规硬检查 → 固定声明追加 → Canonical 最终输出`。

## 9. Contract / 验收
