# AIA IP 人设生成 PRD V1

> 状态：**DRAFT / 已固化确认规则，待最终覆盖审计冻结**  
> 日期：2026-09-08  
> 范围：资料与证据、稳定稿、推荐昵称、一句话 IP、推荐简介、平台合规、页面交互、上下游保护、唯一 Writer、验收。  
> 维护原则：这是唯一持续累加 Draft。已确认规则不得因后续总结被删减；发现遗漏只新增/修订具体 Rule ID。冻结后本文件成为该子系统唯一产品事实源。

## 0. 规则治理
- **GOV-001**：本 Draft 固化当前已确认规则；冻结后升级为本子系统唯一产品事实源。
- **GOV-002**：冻结条件：全部 ACTIVE 历史规则映射到具体 Rule ID，`ACTIVE 未映射=0`、`CONFLICT=0`。
- **GOV-003**：冻结后历史 nickname/headline/bio 规则文件统一标记 `DEPRECATED / SUPERSEDED BY AIA_IP_PERSONA_PRD_V1`，仅保留历史追溯价值，不再拥有运行态、开发或测试的当前规则权威。
- **GOV-004**：后续新增规则只以增量 Rule ID 修订本文件，不恢复多层继承链。
- **GOV-005**：代码现状、历史 Prompt、旧测试或旧 UI 只能用于发现实现差异，不能反向覆盖本 PRD 已确认产品规则。

## 1. 数据、资料与证据
- **DATA-001**：输入读取报名/基础资料、个人介绍、客户/身边人反馈、历史账号资产、人工确认昵称预设、当前稳定稿以及新增真实资料。
- **DATA-002**：昵称完整输入至少包括：原昵称、基础资料/本人自我介绍、客户/身边人真实称呼、高频评价、他人角色认知、愿意咨询/交流的话题、身份/经历/兴趣、账号目标/目标人群和合规规则。
- **DATA-003**：自媒体运营经验只用于了解运营基础，不属于对外人设资产。账号运营时长、平台、粉丝、播放、作品、咨询、留资以及由自媒体产生的成交/增员等不得进入推荐昵称、一句话 IP、推荐简介，也不得参与强事实竞争。主持人、记者、媒体从业者等真实职业经历可按职业事实处理，但账号运营成绩仍排除。
- **DATA-004**：账号目的仅保留“拓客 / 增员”；起号建议优先单方向。账号目的用于定位与内容策略，不得机械写成昵称/简介标签。
- **DATA-005**：身边人评价与个人资料属于同一人物事实体系；多人评价可作为 C 级证据参与资格与排序，但最终展示遵守反馈表达规则。
- **DATA-006**：内容支线可读取过往职业、宝爸宝妈等真实生活身份、真实兴趣等资料；“内容可用”不等于“昵称可用”，必须分别经过对应 Gate。
- **EVID-001**：A=报名/基础资料明确事实；B=本人自我介绍明确表达；C=合格客户/身边人反馈；D=AI 推断。A/B/C 可进入候选；D 原则上不得作为最终人物事实。
- **EVID-002**：事实强度只能保持或降低，不得由关键词、类别或 AI 推断升级成具体职业、资质、经历、服务能力、婚育情况、学校、国家等事实。
- **EVID-003**：原始资料存在明确时间/数字精度时必须保留；不得把 `7年+` 随意改成“多年”；无年限证据不得补“多年/长期”。
- **EVID-004**：人物资产竞争优先级：稀缺且具体事实 > 有数字经历 > 有证据强反差/转型 > 专业资质/荣誉 > 客户反馈稳定特点 > 有记忆点生活身份 > 普通兴趣 > 泛化形容词。
- **EVID-005**：当前行业从业不足5年默认不作为推荐简介/一句话 IP 卖点；满5年可参与竞争但不是必选。原始资料保留。
- **EVID-006**：A1、PA转任、团队1+2等内部职级/黑话默认不作为陌生客户卖点。MDRT/COT/TOT 等真实荣誉仍参加真实性、价值和合规竞争。
- **EVID-007**：同一事实多来源时合并证据，不重复占人物资产位；冲突事实不得由 AI 自行选择“更好听”的版本。

## 2. 稳定稿、上下游保护与增量更新
- **STABLE-001**：先读取现有稳定稿，再读取新增真实资料。
- **STABLE-002**：已有真实、合规、成立的稳定内容默认保护；新增资料采用增量补充，不无故整体重生成。
- **STABLE-003**：仅在新增资料证明原内容事实冲突、违反最新规则/合规、新增事实明显更强，或用户明确要求修改时允许替换。
- **STABLE-004**：增量更新后仍重新执行事实、去重、长度、Emoji、平台合规、固定声明和总字数门禁。
- **STABLE-005**：资料不足允许少于默认信息量，不得为满足格式编造。
- **STABLE-006**：上游资料更新必须先进入统一 Profile Facts/Evidence 层；页面脚本、旧 Prompt 或 fallback 不得绕过证据层写最终 nickname/headline/bio。
- **STABLE-007**：下游内容方向、脚本推荐、脚本改写等只消费 Canonical Output；不得自行重算或改写 nickname/headline/bio。
- **STABLE-008**：稳定稿版本与新 proposal 分离。用户修改产生新 proposal，不覆盖历史稳定版本；只有经过明确稳定/晋级流程的新版本才能成为新的 stable output。

## 3. 推荐昵称
- **NICK-001**：目标是像真实的人、顺口、好记、好搜、有稳定识别；首选尽量有记忆点和网感，证据不足宁缺毋滥。
- **NICK-002**：每个最终昵称必须有且只有一个人物锚点，不得只有地域、荣誉、行业标签而没有人物主体。
- **NICK-003**：人物锚点优先：高频真实称呼 > 本人明确希望称呼 > 成熟合规原昵称稳定锚点 > 长期英文名 > 本名/自然两字以上姓名片段兜底。禁止随意截单字、机械加哥姐或造小名。
- **NICK-004**：多个真实称呼同频时比较：公开自然无歧义、亲和、记忆、发音/输入简单、与姓名关联、与真实特点组合能力、账号表达风格。
- **NICK-005**：`nicknamePreset.status=approved` 时，`primary` 固定默认首选，优先于 AI 和通用规则。AI 不得写 approved；preset 仅覆盖昵称。`allowAiFallback=true` 时可受控补候选，但不得顶掉人工首选；首选变化更新 preset。
- **NICK-006**：已有自然、合规、有特色、有用户记忆的成熟原昵称优先保护，不机械加修饰语或改坏。
- **NICK-007**：过往职业不得进入新推荐昵称，即使加“前”也不作为默认路线。当前仍真实持续的专业身份、生活身份、兴趣、内容特点可有证据参与。
- **NICK-008**：客户评价可辅助创意，但普通“靠谱/专业/真诚”不得机械前缀化；只有鲜明、自然、有明确证据且提升辨识度的修饰语才可参与。
- **NICK-009**：新昵称默认不用 Emoji、特殊符号、装饰字、装饰标点、无意义数字尾缀。全英文原则上不做首选；中英混合时中文必须承担人物记忆/语义识别。
- **NICK-010**：禁止动作标题句、重复人物主体、字段机械拼接、生硬难念组合。万能模板不作为批量默认路线。
- **NICK-011**：通常推荐3–5个真正不同路线；纯姓名、真实称呼及极简变体合计最多2个。只有2–3个好候选时不凑满5个。
- **NICK-012**：首选不默认裸本名/裸称呼；有真实鲜明且当前成立的兴趣/生活/内容特点或鲜明评价时，优先尝试“记忆点+人物锚点”；资料不足才回退裸称呼/本名。
- **NICK-013**：Nickname Memory Score：成熟受保护原昵称 +3；当前真实鲜明兴趣/生活/内容特点 +3；真实高频称呼锚点 +2；有证据鲜明修饰语 +2；裸姓名/称呼 0；姓名/称呼+无意义数字 -2；全英文或英文+无意义数字 -3；万能模板 -5。
- **NICK-014**：同分：成熟原昵称 > 有证据鲜明修饰语 > 当前兴趣/生活/内容特点 > 真实称呼 > 本名。存在合格高分特色候选时裸姓名不得第一；没有合格特色候选时不得强造标签。
- **NICK-015**：原昵称独立给出“建议保留 / 建议优化 / 不建议保留”及稳定具体理由，检查合规、用户记忆、自然顺口、人物感、明显优化项、中文记忆/输入/搜索。已有人工固定结论时优先读取，AI 不得随机重写。
- **NICK-016**：系统不主动推荐含 `保险 / 友邦 / 友邦保险 / 友邦人寿 / AIA` 及明显品牌变体/规避写法的新昵称；已有相关原昵称只谨慎审查。
- **NICK-017**：AI 只负责受控候选和自然语言组合；事实、合规、排序、首选由确定性 Owner 决定。
- **NICK-018**：六种受控命名路线：突出身份、性格、地域、专业、学历、成就。它们是候选方向，不要求各生成一个，且不能突破事实/自然度/记忆度/合规/资产竞争。旧“过往职业可作为专业昵称”被 NICK-007 覆盖；专业仅指当前仍成立的真实专业身份/资质/内容能力。
- **NICK-019**：受控连接词仅开放 `说 / 聊 / 讲 / 谈 / 看`，优先 `说 / 聊 / 讲`；连接词只提升口语自然度，不构成人物特色。
- **NICK-020**：生成顺序：合规硬过滤 → 真实证据校验 → 唯一人物锚点 → 核心资产竞争 → 六种路线 → 受控组合 → 无自然方案才 AI 兜底 → 再做事实/自然度/合规/Memory Score/首选排序。
- **NICK-021**：地域仅使用真实档案，默认一层地域；学历不得由 QS/985/211 反推具体学校；成就必须有证据且可公开，不夸张为第一/顶级/最强。

## 4. 一句话 IP / Canonical Headline
- **HEAD-001**：一句话 IP 是简洁自我介绍/记忆句，不是标签墙、业务说明或履历堆砌。
- **HEAD-002**：使用2–3个最强真实特点，执行 `账号目的 × 我的不同之处 × 目标人群关注内容 → 我的IP`，不强制把所有维度塞入一句。
- **HEAD-003**：遵守 EVID-004；不得用无证据的“0人脉/多年/擅长/懂XX/专家/导师/顾问”。
- **HEAD-004**：禁止“从XX跨界，用自己的经验讲清……”以及“靠谱/真诚是我的标签”“XX是我的专业底色”“做一个让人记得住的人”等机械空话。
- **HEAD-005**：不使用姓名/昵称作句首锚点，不写职业+转型+行业+荣誉标签墙，不使用 `｜` / `|` 拼标签。
- **HEAD-006**：数字与时间精度遵守 EVID-003。
- **HEAD-007**：`proposal.headline` 是 canonical 单一来源：IP顶部一句话 = XHS固定声明前 headline = 视频号/抖音固定尾部前 headline，逐字一致；Bio 不得截断、改写或另造 slogan。
- **HEAD-008**：headline 因复用于 XHS，必须通过 XHS 共同合规门禁。

## 5. 推荐简介
- **BIO-001**：回答“我是谁 / 我的优势 / 我能提供什么价值”，各维度按真实资料丰富程度1–3行，不要求平均。
- **BIO-002**：优先：差异化身份/经历 > 强专业背书 > 真实内容/服务价值 > 有证据评价结论 > 有定位价值地域 > 真实兴趣 > 泛化形容词。
- **BIO-003**：跨行语义去重；重复时保留：具体量化事实 > 明确身份/经历/资质 > 明确荣誉 > 模糊概括 > AI总结。
- **BIO-004**：客户反馈只呈现结论，如 `靠谱｜细致｜有耐心`；禁止“客户高频评价/客户都评价我/大家眼中的我/多位客户认为/多人评价/多人反馈”等来源前缀；本人自评不得升级为多人反馈。
- **BIO-005**：兴趣只用真实资料，不机械限制1–2个。
- **BIO-006**：可提供服务只用明确真实资料，不因营销员身份或为了凑行推断；数量不机械限制；每项 **≤6个汉字**，使用 `｜` 分隔，并受合规和总字数预算约束。
- **BIO-007**：每人只输出1套 XHS 最终简介和1套视频号/抖音共用最终简介；除固定声明/平台差异外正文默认同源。
- **BIO-008**：正文默认至少3行（不含固定尾部）；只有真实资料不足、继续增加会重复/空话/推断时允许少于3行，绝不为凑3行编造。
- **BIO-009**：单行有效内容优先约12–20个汉字等效长度；21–25仅语义完整且无法自然压缩时允许；**25绝对上限**。
- **BIO-010**：短资产不足12时：同维度合并 → 凝练重组 → 并入同核心问题相邻行 → 仍不足则不强制独立成行；不得空话补长。
- **BIO-011**：每行保持同一语义维度；经历/荣誉原则清晰分开，短资产可与同属“我的优势”的自然信息合并。
- **BIO-012**：正文各行长度尽量均衡，不为等长加废话。
- **BIO-013**：每个正文行使用不同 Emoji；不重复；`👤` 退出推荐模板。
- **BIO-014**：canonical headline 插在正文之后、平台固定尾部之前；不受正文 Emoji/行宽规则改写，必须原样复用。
- **BIO-015**：**XHS、视频号、抖音完整简介总长度均≤100个汉字等效字符**，包括正文 + canonical headline + 固定声明/尾部。先预留 headline 和尾部预算，再生成/压缩正文；固定声明不得删改。
- **BIO-016**：取消固定3–5资产、兴趣1–2、服务3–4、荣誉1–2等机械上限；真实、有价值、有辨识度、合规且空间允许的信息尽量保留，只删重复、低价值、无证据、AI套话、不合规内容。

## 6. Compliance Matrix
来源：`P=平台公开可验证规则`、`C=公司/项目合规要求`、`A=AIA Auto IP 更严格产品策略`。无充分平台公开依据时，不把内部策略冒充平台官方规则；产品门禁仍执行。
- **COMP-001 [P/C]**：简介不得包含电话、微信、邮箱、QQ、微博、二维码、URL/站外联系方式或其他导流信息；执行平台/公司更严格者。
- **COMP-002 [A/C]**：XHS 推荐简介正文和 canonical headline 禁止 `保险、金融、理财、贷款、股票、基金、医疗、护理、教育、玄学` 等当前产品敏感词；正文禁止 `友邦 / AIA`。不声称这些全部都是平台官方普遍禁词。
- **COMP-003 [C/A]**：XHS 个人简介不得输出执业证编号。
- **COMP-004 [C]**：XHS 固定最后一句逐字为：`本账号所述内容为个人意见，不代表任何官方意见。` 必须最后出现，不得改写、缩短、重复。
- **COMP-005 [C]**：视频号/抖音末尾固定连续三行：`本账号上所陈述或表达的内容仅为我个人意见，并不代表友邦人寿的意见`；`营销服务部：XXX`；`执业证编号：XXX`。顺序固定。
- **COMP-006 [C]**：营销员编号 ≠ 执业证编号；不得用 agentId 冒充。营销服务部/执业证编号缺失时 AI 不得编造。
- **COMP-007 [C/A]**：历史 Preview `000` 仅为旧技术占位；正式推荐、复制、稳定稿和 Production 禁止 `000` 伪装真实执业证编号；缺失字段必须补真实值。
- **COMP-008**：合规过滤发生在最终推荐展示之前；固定尾部由唯一 Owner 追加，Prompt/AI/历史 Vxx 不得重复生成。
- **COMP-009**：合规门禁不得篡改真实事实；不合规素材淘汰、同事实合规改写或不进入最终稿，不能创造新事实。
- **COMP-010 [时效提醒]**：现有 UI 提醒保留：视频号昵称“每年最多修改5次”；视频号简介“暂无明确修改次数限制”；XHS简介“7天内最多修改3次，频繁修改也可能影响账号稳定”。这些可能随平台变化，发布前以平台实时提示/最新合规通知复核，不作为永久生成事实。

## 7. 页面与 Interaction Contract
- **UI-001**：本轮重写人设 Engine，不默认重做成熟页面；除 PRD 明确修改项外，成熟布局、视觉、交互保持。
- **UI-002**：继续展示推荐昵称候选/首选、原昵称判断、一句话 IP、XHS简介、视频号/抖音简介及相关操作。
- **UI-003**：昵称/简介标题保留 `?` 合规入口，位于板块标题同一行；点击展示合规说明，不恢复旧折叠式窗口，不改变卡片布局。
- **UI-004**：第一次复制昵称/简介时显示对应平台合规/修改次数提醒；后续复制保留成功反馈。提醒不能替代生成前硬门禁。
- **UI-005**：“就按这个改”生成新 proposal，历史版本不可变；明确修改事实字段时先更新事实，再只重算受影响输出。
- **UI-006**：用户修改不能绕过真实性/合规门禁。
- **UI-007**：稳定稿读取/展示遵守 STABLE；新增资料不导致随机换稿。
- **UI-008**：内容方向与脚本推荐成熟能力保留；有 IP 时消费 canonical 人设，无 IP 时按现有脚本库浏览并提示完成人设。
- **UI-009**：脚本详情仅保留一组“上一篇/下一篇”，位于正文底部；固定底栏仅“脚本改写 / 小红书排版”；切换后滚动回顶部。
- **UI-010**：保持成熟桌面/平板/手机响应式体验，不恢复已废弃旧浮层/布局。
- **UI-011**：资料保存后，用户以编号+姓名再次进入应读取历史资料、稳定稿和版本历史，不因刷新/二次进入丢失。
- **UI-012**：未生成 IP 时脚本推荐按二级标签展示脚本库（PC/Pad两列、手机一列），顶部提示完成人设并跳转；生成后切换 canonical 人设推荐。
- **UI-013**：资料入口与最新 IP 方案入口遵守当前成熟交互；最新 IP 方案仅在已生成时出现，不恢复淘汰实现。

## 8. Engine、上下游与唯一 Writer
- **ENG-001**：目标链路：`Stable Output Resolver → Profile Facts → Evidence Engine → Asset Ranking → Nickname Builder → Headline Builder → Bio Builder → Compliance Gate → Canonical Output → UI`。
- **ENG-002**：AI 只负责受控语言候选，不决定事实、证据等级、合规放行、人工 preset 优先级或最终排序。
- **ENG-003**：nickname/headline/bio 每个最终字段只能有一个运行态 Writer/Owner；旧 Prompt、旧 Vxx、fallback、stable runtime 不得形成第二写入权。
- **ENG-004**：新 Engine 先独立实现+Contract 验证，再切页面；确认旧 Writer 不再运行后退役历史 Writer，避免补丁叠加。
- **ENG-005**：统一顺序：`稳定稿 → 新真实资料 → 排除运营素材 → 证据分级 → 资产竞争 → 低价值年限/黑话过滤 → 生成/增量补充 → 总字数预算 → 平台合规 → 固定声明 → Canonical 输出`。
- **ENG-006**：资料层、生成层、稳定稿层、UI层、脚本推荐/改写层单向消费明确数据契约；下游不得回写或偷偷修正 canonical 人设字段。
- **ENG-007**：历史兼容脚本可暂存，但不得拥有最终字段写权限；Contract 防止旧 Writer 重新获得权威。

## 9. Contract / 验收
- **ACC-001**：Contract 覆盖事实不升级、时间精度、反馈不伪造、稳定稿增量保护、nicknamePreset、Memory Score、六种路线/连接词、自然度、前职业退出昵称、canonical headline、Bio去重/行宽/Emoji/3行例外、服务≤6字、总长≤100、固定声明、执业证缺失、唯一 Writer、上下游只读消费。
- **ACC-002**：`≤100` 按完整最终简介验收，不能只测正文。
- **ACC-003**：真实 fixtures 至少覆盖：资料丰富、资料不足、只有反馈、approved preset、成熟原昵称、全英文原昵称、前职业强资产、从业<5年、执业证缺失、多项服务、多人评价冲突、增量资料更新、用户修改新 proposal。
- **ACC-004**：发布顺序：Contract → API → Playwright/浏览器 → 隔离 Preview → 技术验收 → 用户业务验收 → 冻结相同 RC → 明确批准后 Production。
- **ACC-005**：PRD/Matrix 固化阶段不修改业务代码、数据库、Preview 或 Production。
- **ACC-006**：旧测试全绿不能代替产品规则实现；旧测试与本 PRD 冲突时更新/淘汰旧测试，而不是把产品规则改回旧行为。
