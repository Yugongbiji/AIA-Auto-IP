# AIA IP 人设生成 PRD V1

> 状态：**DRAFT / 已固化确认规则，待最终覆盖审计冻结**  
> 日期：2026-09-08  
> 范围：资料与证据、首次进入与资料复用、稳定稿、推荐昵称、一句话 IP、推荐简介、平台合规、内容方向、脚本推荐、页面交互、上下游保护、唯一 Writer、验收。  
> 维护原则：这是唯一持续累加 Draft。已确认规则不得因后续总结被删减；发现遗漏只新增/修订具体 Rule ID。冻结后本文件成为该子系统唯一产品事实源。

## 0. 规则治理
- **GOV-001**：本 Draft 固化当前已确认规则；冻结后升级为本子系统唯一产品事实源。
- **GOV-002**：冻结条件：全部 ACTIVE 历史规则映射到具体 Rule ID，`ACTIVE 未映射=0`、`CONFLICT=0`。
- **GOV-003**：冻结后历史 nickname/headline/bio 规则文件统一标记 `DEPRECATED / SUPERSEDED BY AIA_IP_PERSONA_PRD_V1`，仅保留历史追溯价值，不再拥有运行态、开发或测试的当前规则权威。
- **GOV-004**：后续新增规则只以增量 Rule ID 修订本文件，不恢复多层继承链。
- **GOV-005**：代码现状、历史 Prompt、旧测试或旧 UI 只能用于发现实现差异，不能反向覆盖本 PRD 已确认产品规则。
- **GOV-006**：已经正确、成熟的页面布局、交互、复制、内容方向、脚本推荐等功能保持；重写人设生成 Engine 不代表重做页面或下游功能。
- **GOV-007**：产品规则、数据事实、稳定输出、历史版本、UI 展示、下游消费必须分层。任何下游层不得反向篡改上游真实事实或 Canonical Output。

## 1. 数据、资料、首次进入与证据
- **DATA-001**：输入读取报名/基础资料、个人介绍、客户/身边人反馈、历史账号资产、人工确认昵称预设、当前稳定稿以及新增真实资料。
- **DATA-002**：昵称完整输入至少包括：原昵称、基础资料/本人自我介绍、客户/身边人真实称呼、高频评价、他人角色认知、愿意咨询/交流的话题、身份/经历/兴趣、账号目标/目标人群和合规规则。
- **DATA-003**：自媒体运营经验只用于了解运营基础，不属于对外人设资产。账号运营时长、平台、粉丝、播放、点赞、作品、咨询、留资以及由自媒体产生的成交/增员/获客等不得进入推荐昵称、一句话 IP、推荐简介，也不得参与强事实竞争。主持人、记者、媒体从业者等“媒体/内容本身就是职业经历”的真实事实可按职业处理，但账号运营成绩仍排除。
- **DATA-004**：最终 `primaryGoal` 只能是 `customer_acquisition`（拓客）或 `recruitment`（增员）。报名资料若是“两者都要 / 同时 / 兼顾 / 打造个人品牌 / 打造专业形象”等非唯一答案，必须重新询问并二选一；起号阶段建议先聚焦一个方向。后续提问、IP方案、内容方向、脚本推荐全部读取同一标准化 `primaryGoal`，不得各自重新猜 raw `purpose`。
- **DATA-005**：客户/身边人评价与营销员本人自评是两个不同证据来源，必须分别保留来源。本人填写“靠谱”只能证明本人自评，不能转换成“客户认为靠谱”。
- **DATA-006**：内容支线可读取过往职业、宝爸宝妈等真实生活身份、真实兴趣等资料；“内容可用”不等于“昵称可用”，必须分别经过对应 Gate。
- **DATA-007**：客户/身边人评价可辅助人物印象、自然称呼、社会角色、愿意咨询/交流的话题、昵称创意、一句话 IP、简介、内容支线和脚本表达；但评价不能自动升级为学历、职业经历、专业资质、荣誉、兴趣或实际服务能力。
- **DATA-008**：“大家愿意找我聊养老”等咨询话题只证明话题关联，不等于本人可提供“养老规划”等服务；服务能力必须有独立真实资料支持。
- **DATA-009**：首次进入 IP 人设时，同一次初始化必须完成：`功能介绍 → 合并已有资料 → 标准化 primaryGoal → 找到第一个真正缺失字段 → 立即提问`。已有资料不重复问；欢迎卡强调用户价值，不强调模型技术，之后不能停在“接下来会问几个问题”。
- **DATA-010**：系统先扫描并标准化完整 profile：报名表、后台导入、历史保存、个人介绍语义提取、客户反馈摘要。报名资料、个人介绍、客户反馈中已经有的有效信息不得重复询问。
- **DATA-011**：`selfIntro` 若已有，先语义提取明确的过往职业、长期身份、真实爱好等，**只填缺失字段**；不得覆盖已有真实资料，不把推断当事实。个人介绍必须在“我的资料”最后一栏整行展示。
- **DATA-012**：没有匹配到历史资料时，不用“失败 / 没找到”等负面表达；欢迎后直接进入第一题。营销员编号为9位数字，仅用于匹配已有资料/历史报名，绝不能作为执业证编号。
- **DATA-013**：目标人群题随 `primaryGoal` 切换。拓客使用客户人群/年龄；增员使用“准增员对象 / 准增员年龄”，增员年龄选项不含55岁以上。语义预填也必须读取 `primaryGoal`，不能把“我主要服务企业主”误当成“我希望招募企业主”。
- **DATA-014**：当前资料链至少覆盖：姓名/营销员编号、primaryGoal、城市、目标人群/年龄、当前行业从业时间、优势、荣誉、学历（含大专/本科/硕士/博士）、学校背景层级、留学背景、账号表达风格 `contentTone`、过往职业/长期经历、家庭/生活身份、真实爱好、真实可提供服务、营销服务部。`contentTone` 可选1–2项，并提示会影响后续脚本改写；过往职业/长期经历、生活身份、爱好多选。
- **DATA-015**：快捷选项不得出现“其他 / 不希望填写 / 跳过 / 暂不填写”等逃逸项，但用户仍可自由输入补充；多选由同一个业务状态管理，底部“发送”是唯一提交动作；点击快捷标签不主动拉起手机键盘，已选标签显示在输入框内部。
- **DATA-016**：所有当前必需资料已足够时，不为了制造互动继续提问，可直接进入方案生成。有可恢复历史对话时不重复完整欢迎卡；已有方案但没有对话时载入档案和方案，不因普通刷新要求重填。历史独立内容规划数据不得决定当前默认导航或覆盖当前 IP 内容方向。
- **DATA-017**：生成方案后，用户可在 IP 对话中修改目标、职业/经历、身份、爱好、服务等事实字段并保存；明确事实修改先更新事实层，再重算受影响输出，不由 UI 直接改最终文案字段。
- **DATA-018**：数据分层必须明确：`agents` 保存报名原始资料；`saved_profiles` 保存用户后续确认过的人物事实；`conversation_messages` 保存后续沟通原文，作为新增事实追溯来源；`proposals` 保存不可变推荐方案版本历史；`current_ip_outputs` 保存每位营销员当前正式稳定版本的指针与完整输出。
- **DATA-019**：客户评价采用“一名营销员 → 多条原始评价”的一对多结构，9位 `agentId` 为稳定匹配键。每位评价者原始记录保留，不把多人评价摊平成个人表一行；个人档案保存聚合摘要，后台可保留评价人数、频率、关系、印象、咨询话题、角色认知、代表性自然语言和来源。
- **DATA-020**：`peerReviewSummary` / `peerReviewKeywords` 属于独立第三方评价来源，不覆盖 `services`、`education`、`previousCareer`、`hobbies` 等本人事实字段。未匹配到现有营销员主表的评价编号必须报告，不得静默编造或新建营销员。
- **EVID-001**：A=报名/基础资料明确事实；B=本人自我介绍明确表达；C=合格客户/身边人反馈；D=AI 推断。A/B/C 可进入候选；D 原则上不得作为最终人物事实。本人后续明确确认的事实视为可用真实事实来源。
- **EVID-002**：事实强度只能保持或降低，不得由关键词、类别或 AI 推断升级成具体职业、资质、经历、服务能力、婚育情况、学校、国家等事实。
- **EVID-003**：原始资料存在明确时间/数字精度时必须保留；不得把 `7年+` 随意改成“多年”；只有原资料本身是“多年”才允许写“多年”；无年限证据不得补“多年/长期”。
- **EVID-004**：人物资产竞争优先级：稀缺且具体事实 > 有数字经历 > 有证据强反差/转型 > 专业资质/荣誉 > 客户反馈稳定特点 > 有记忆点生活身份 > 普通兴趣 > 泛化形容词。总体执行 `具体、量化、稀缺、可验证 > 模糊概括 > 泛化形容词`。
- **EVID-005**：当前行业从业不足5年默认不作为推荐简介/一句话 IP 卖点；满5年可参与竞争但不是必选。原始资料保留。
- **EVID-006**：A1、PA转任、团队1+2等内部职级/黑话默认不作为陌生客户卖点。MDRT/COT/TOT 等真实荣誉仍参加真实性、价值和合规竞争。
- **EVID-007**：同一事实多来源时合并证据，不重复占人物资产位；冲突事实不得由 AI 自行选择“更好听”的版本。
- **EVID-008**：昵称、一句话 IP、简介共用统一 Profile Facts / Evidence / Asset Ranking 体系，先完成人物资产竞争，再生成输出；禁止按数据库字段顺序机械拼接。
- **EVID-009**：类别信息不能升级为具体事实：QS前100≠某具体大学；985/211≠某具体学校；留学背景≠某个国家；宝妈/宝爸≠孩子数量年龄；MDRT/COT/TOT≠具体业绩数字。

## 2. 稳定稿、历史数据、上下游保护与增量更新
- **STABLE-001**：`current_ip_outputs` 是当前正式稳定输出/当前被认可版本；读取人设时优先读取它。
- **STABLE-002**：已有 `current_ip_outputs` 时，刷新、重新登录、二次进入或模型变化都不得触发 AI 重新生成；优先原样读取稳定稿。
- **STABLE-003**：`proposals` 保存历史候选/修改版本，历史 proposal 不可覆盖；用户“就按这个改”等操作产生新 proposal 版本。
- **STABLE-004**：`saved_profiles` 只保存人物真实事实与资料，不保存“当前最好文案”；当前最好文案属于 `current_ip_outputs`。
- **STABLE-005**：新增资料不能直接覆盖 `current_ip_outputs`。新增资料流程必须是：`新增事实 → 用户确认 → 写入事实资料 → 去重 → 人物资产竞争 → 生成新候选 → 全规则/合规门禁 → 与稳定稿比较`。
- **STABLE-006**：新候选只有在整体明显更好时才允许晋级稳定版本；仅仅换一种说法、同质改写或随机措辞变化不能覆盖稳定稿。
- **STABLE-007**：若新候选出现事实退化、人物资产质量下降、自然度下降、信息损失或合规风险，继续保持原稳定稿。
- **STABLE-008**：允许修改/替换原稳定内容的核心条件仅包括：新增资料证明原稿事实错误；原稿违反最新规则/合规；出现明显更强人物资产需要重新竞争；用户明确要求修改。
- **STABLE-009**：资料不足人员已有稳定稿时，后续补资料采用增量优化，保留已成立内容，不无理由整体推倒重来。
- **STABLE-010**：增量更新后仍重新执行事实、去重、长度、Emoji、平台合规、固定声明和总字数门禁。
- **STABLE-011**：资料不足允许少于默认信息量，不得为满足格式编造。
- **STABLE-012**：上游资料更新必须先进入统一 Profile Facts/Evidence 层；页面脚本、旧 Prompt 或 fallback 不得绕过证据层写最终 nickname/headline/bio。
- **STABLE-013**：下游内容方向、脚本推荐、脚本改写等只消费 Canonical Output；不得自行重算或改写 nickname/headline/bio。
- **STABLE-014**：稳定稿与 proposal 分层：proposal 可持续新增，stable 只有经过比较、门禁和明确稳定/晋级流程后才更新。
- **STABLE-015**：所有旧 proposal 版本永久保留并支持回滚；稳定版本晋级不能删除历史版本。
- **STABLE-016**：稳定稿晋级前硬门禁至少包括：事实可追溯；“我是谁/我的优势/我能提供什么价值”信息成立；canonical headline 单一；XHS整段合规；两平台 headline 不漂移；固定声明结构正确；不因合规改写制造新事实；无明显语义重复。任一硬门禁失败都不得覆盖稳定稿。
- **STABLE-017**：新候选不得以 `保险保障 / 风险保障 / 保险认知` 等空泛词、孤立职业、泛化生活方式等低信息量表达冒充“明显更好”。
- **STABLE-018**：完整真实个人资料、客户反馈、人工验收 Excel 等不提交 GitHub；仓库只保存规则、导入程序、测试和数据结构。真实数据只在受控数据库/ECS临时导入文件等受控环境流转。

## 3. 推荐昵称
- **NICK-001**：目标是像真实的人、顺口、好记、好搜、有稳定识别；首先帮助陌生人记住这个人，而不是把业务塞进昵称。首选尽量有记忆点和网感，证据不足宁缺毋滥。
- **NICK-002**：每个最终昵称必须有且只有一个人物称呼主体/锚点，不得只有地域、荣誉、行业标签；不得双称呼拼接。
- **NICK-003**：人物锚点优先：高频真实称呼 > 本人明确希望称呼 > 成熟合规原昵称稳定锚点 > 长期英文名 > 本名/自然两字以上姓名片段兜底。禁止随意截单字、机械加哥姐或造小名。二字姓名无真实简称时默认完整姓名兜底。
- **NICK-004**：多个真实称呼同频时比较：公开自然、无歧义、亲和、记忆、发音/输入简单、与姓名关联、与真实特点组合能力、账号表达风格。
- **NICK-005**：`nicknamePreset.status=approved` 时，`primary` 固定默认首选，优先于 AI 和通用规则。AI 不得写 approved；preset 仅覆盖昵称。`allowAiFallback=true` 时可受控补候选，但不得顶掉人工首选；首选变化更新 preset。
- **NICK-006**：已有自然、合规、有特色、有用户记忆的成熟原昵称优先保护，不机械加修饰语或改坏；有记忆点不等于必须加修饰语。
- **NICK-007**：过往职业不得进入新推荐昵称，即使加“前”也不作为默认路线。当前仍真实持续的专业身份、生活身份、兴趣、内容特点可有证据参与。
- **NICK-008**：客户评价可辅助创意，但普通“靠谱/专业/真诚”不得机械前缀化；只有鲜明、自然、有明确证据且提升辨识度的修饰语才可参与，例如有真实证据时的“有料有趣的流火”。
- **NICK-009**：新昵称默认不用 Emoji、特殊符号、花体字、装饰繁体、装饰标点、无意义数字尾缀。全英文原则上不做首选；中英混合时中文必须承担人物记忆/语义识别。
- **NICK-010**：禁止动作标题句、重复人物主体、字段机械拼接、生硬难念组合。`XX的小世界 / XX的日常 / XX聊生活 / XX看世界` 等万能模板不作为批量默认路线；若本来就是成熟原昵称，可按 NICK-006 保护。
- **NICK-011**：通常推荐3–5个真正不同路线；纯姓名、真实称呼及极简变体合计最多2个。只有2–3个好候选时不凑满5个，禁止多个称呼占满全部候选。
- **NICK-012**：首选不默认裸本名/裸称呼；有真实鲜明且当前成立的兴趣/生活/内容特点或鲜明评价时，优先尝试“记忆点+人物锚点”；资料不足才回退裸称呼/本名，不硬造人设。
- **NICK-013**：当前真实兴趣可参与昵称竞争，如健身、八块腹肌、手帐、攀岩、滑雪、网球、读书等，但必须来自真实资料，不得为了“网感”编造。
- **NICK-014**：Nickname Memory Score：成熟受保护原昵称 +3；当前真实鲜明兴趣/生活/内容特点 +3；真实高频称呼锚点 +2；有证据鲜明修饰语 +2；裸姓名/称呼 0；姓名/称呼+无意义数字 -2；全英文或英文+无意义数字 -3；万能模板 -5。
- **NICK-015**：同分：成熟原昵称 > 有证据鲜明修饰语 > 当前兴趣/生活/内容特点 > 真实称呼 > 本名。存在合格高分特色候选时裸姓名不得第一；没有合格特色候选时不得强造标签。
- **NICK-016**：原昵称独立给出“建议保留 / 建议优化 / 不建议保留”及稳定具体理由，检查合规、用户记忆、自然顺口、人物感、明显优化项、中文记忆/输入/搜索。已有人工固定结论时优先读取，AI 不得随机重写。
- **NICK-017**：`无 / 暂无 / 没有 / 0 / 未设置` 等属于缺失值，不得作为昵称、人物锚点或可保留原昵称。
- **NICK-018**：六种受控命名路线：突出身份、性格/人物特点、地域、专业、学历、成就。它们是创意思路库，不要求各生成一个，且不能突破事实/自然度/记忆度/合规/资产竞争。旧“过往职业可作为专业昵称”被 NICK-007 覆盖；专业仅指当前仍成立的真实专业身份。
- **NICK-019**：突出身份仅使用当前真实持续身份；突出性格仅在真实且有辨识度时使用；地域必须真实且不得机械批量“城市+称呼”；学历可用博士、硕士、985/211、QS层级、真实海归等但不得反推学校；成就如 MDRT/COT/TOT/真实销冠必须真实、允许公开、自然，不夸张为第一、最强、顶级、一哥、大师、权威。
- **NICK-020**：受控连接词仅开放 `说 / 聊 / 讲 / 谈 / 看`，优先 `说 / 聊 / 讲`；连接词只提升口语自然度，不构成人物特色。
- **NICK-021**：生成顺序：合规硬过滤 → 真实证据校验 → 唯一人物锚点 → 核心资产竞争 → 六种路线 → 受控组合 → 无自然方案才 AI 兜底 → 再做事实/自然度/合规/Memory Score/首选排序。
- **NICK-022**：AI 只能在受控候选不足时补充昵称，不能自由命名；AI 候选必须重新经过真实性、称呼主体、合规、自然度、记忆度、中文可搜索门禁。
- **NICK-023**：产品策略比最低平台合规更严格：系统不主动推荐含 `保险 / 友邦 / 友邦保险 / 友邦人寿 / AIA` 及明显品牌变体/规避写法的新昵称；现实账号存在不构成推荐依据；相关原昵称仅谨慎审查，不自动保留。
- **NICK-024**：账号唯一识别号不得包含友邦及其品牌变体；该规则独立于昵称推荐规则。
- **NICK-025**：当前已确认规则中**没有冻结一个昵称数字字符上限**；在获得明确产品确认前，不得由 AI、代码或开发者自行编造数字上限。自然度、可搜索、平台实时限制继续作为 Gate。
- **NICK-026**：候选来源顺序明确为：`人工 approved primary → 人工 approved backups/备选 → 受控规则自然候选 → AI/DeepSeek 受控兜底`。AI 不能越级覆盖人工顺序。
- **NICK-027**：推荐列表至少保留一个最真实、最自然的人物称呼/本名方向作为稳妥备选；但它不因此自动成为首选。若连真实人物锚点都不存在，不得退化成城市/荣誉/学历/抽象标签昵称，应提示称呼信息不足。
- **NICK-028**：原视频号/小红书昵称不一致时可建议逐步统一，但不武断要求立即修改。原昵称存在多个问题时按1/2/3给出可解释理由，不做一句话武断否定。
- **NICK-029**：新生成候选、人工预设、原昵称在进入“推荐候选”前统一清理 Emoji、特殊符号、装饰字符和末尾装饰标点；清理仅做形式标准化，不改变人物事实或人工 approved 首选意图。
- **NICK-030**：推荐理由只解释“这个昵称为什么自然/好记/有辨识度”，不向用户暴露产品负责人、人工验收状态、内部排序权、Memory Score 或 AI fallback 等内部实现逻辑。

## 4. 一句话 IP / Canonical Headline
- **HEAD-001**：一句话 IP 是一句浓缩版自我介绍 / slogan，不是标签墙、业务说明或履历堆砌；核心回答“这个人最不一样、最吸引人、为什么值得被记住”。
- **HEAD-002**：使用2–3个最强真实记忆点，执行 `账号目的 × 我的不同之处 × 目标人群关注内容 → 我的IP`，不强制把“我是谁/优势/价值”全部塞入一句。
- **HEAD-003**：资产优先：稀缺且具体事实 > 有数字经历 > 真实反差/转型 > 专业资质/荣誉 > 稳定人物特点 > 有记忆点生活身份 > 普通兴趣 > 泛化形容词。当前行业<5年、自媒体成绩、内部黑话均不作为核心 headline 资产。
- **HEAD-004**：有明确数字/年限时保留精度；不得把7年降为“多年”；不得生成无证据“0人脉/多年/擅长/懂XX/专家/导师/顾问”。
- **HEAD-005**：不出现人物姓名/推荐昵称作为锚点，不使用 `｜` / `|`；使用自然中文标点。
- **HEAD-006**：禁止“从XX跨界，用自己的经验讲清……”以及“XX是我的标签”“XX是我的专业底色”“做一个让人记得住的人”“宝妈，靠谱是我的标签”等机械空话；普通身份+普通性格不得为了凑 slogan 强行拼。
- **HEAD-007**：如果没有足够强人物资产，宁可更简单、真实，也不批量造金句；headline 必须自然、凝练、响亮、有记忆点。
- **HEAD-008**：`proposal.headline` 是 canonical 单一来源：IP顶部一句话 = XHS固定声明前 headline = 视频号/抖音固定尾部前 headline，逐字一致；Bio 不得二次生成、截短、重新断句或改写 headline。
- **HEAD-009**：headline 因复用于 XHS，必须提前通过 XHS 共同合规门禁。
- **HEAD-010**：当前已确认规则中**没有冻结一个 headline 数字字符上限**；不得凭空补数字。headline 仍受自然凝练、页面适配以及完整简介总长≤100的共同约束。
- **HEAD-011**：headline 候选可来自家庭/生活身份、明确职业经历、具体年限、学历/专业资质、真实荣誉、客户反馈、兴趣/生活特点、已证实内容能力、真实转型经历、账号目标与目标人群，但所有候选先过事实证据和 EVID 资产竞争。
- **HEAD-012**：`primaryGoal` 只作为候选排序上下文：增员可提高真实职业经历/转型/荣誉的排序权重；拓客可适当提高真实家庭/生活身份，但不能强制把业务词塞进 slogan。
- **HEAD-013**：fallback 与 AI 候选必须使用同一事实池、同一资产竞争和同一 #119 自然度门禁，不得按固定数据库字段顺序机械拼接，也不得在 fallback 恢复被禁模板。

## 5. 推荐简介
- **BIO-001**：简介回答“我是谁 / 我的优势 / 我能提供什么价值”，各维度按真实资料丰富程度1–3行，不要求平均，也不要求每个问题只占一行。简介不是履历表、不是口播稿，目标是有限空间内最大化单位空间真实有效信息量。
- **BIO-002**：优先：差异化身份/经历 > 强专业背书 > 真实内容/服务价值 > 有证据评价结论 > 有定位价值地域 > 真实兴趣 > 泛化形容词。
- **BIO-003**：家庭身份必须真实；过往职业可进入简介，但高度概括、不写故事；学历可写博士、硕士、985/211、QS层级、真实留学背景等，不得反推学校；专业资质和真实荣誉可进入，不再机械限1–2个。
- **BIO-004**：兴趣不机械限1–2个；服务不机械限3–4项；不再机械做减法。真实、有价值、有辨识度、合规且空间允许的信息尽量保留；删除重复、无证据、AI推断/套话、明显低价值和不合规内容。能短写时优先短写，如“硕士学历→硕士”。
- **BIO-005**：跨行语义去重；重复时保留：具体量化事实 > 明确身份/经历/资质 > 明确荣誉 > 模糊概括 > AI总结。`10年建筑行业财务经验` 优先于 `长期财务管理经验`；不同事实如职称与年限可同时保留。
- **BIO-006**：客户反馈只呈现结论，如 `靠谱｜细致｜有耐心`；禁止“客户高频评价/客户都评价我/大家眼中的我/多位客户认为/多人评价/多人反馈”等来源前缀；本人自评不得升级为多人反馈。
- **BIO-007**：可提供服务只用明确真实资料，不因营销员身份、客户愿聊话题或为了凑行推断；数量不机械限制；每项 **≤6个汉字**，使用 `｜` 分隔，并受合规和总字数预算约束。此前“≤4字”口径已被本次确认的“≤6字”覆盖，不能回退为4字。
- **BIO-008**：每人只输出1套 XHS 最终简介和1套视频号/抖音共用最终简介；历史每平台“专业背书/人设记忆/价值服务”3套方案废止。除固定声明/平台差异外正文默认同源，不能无理由让 XHS 丢失大量人物信息。
- **BIO-009**：最终结构固定为：`人物正文 → proposal.headline → 平台固定合规尾部`。
- **BIO-010**：正文默认至少3行（不含固定尾部）；只有真实资料不足、继续增加会重复/空话/推断时允许少于3行。禁止为凑3行虚构“家庭成长/育儿经验/长期陪伴/家庭保障”等内容。
- **BIO-011**：单行有效内容优先约12–20个汉字等效长度；21–25仅语义完整且无法自然压缩时允许；**25绝对上限**。数字、Emoji、英文、标点按视觉宽度，不机械按 Unicode 字符数。
- **BIO-012**：短资产不足12时：同维度合并 → 凝练重组 → 并入同核心问题相邻行 → 仍不足则不强制独立成行；不得让“靠谱/细致/MDRT/硕士/法学本科/财务中级职称”等在有可合并信息时独占一行。
- **BIO-013**：每行保持同一语义维度，共同回答“我是谁/优势/价值”之一；不得为填满一行混合无关维度。经历、学历、荣誉、评价优先保持子维度清晰，但短资产可在同一“优势”大维度自然合并。
- **BIO-014**：正文各行长度尽量均衡，避免一行接近25、下一行4–6字的明显失衡；不为等长加废话。
- **BIO-015**：每个人物正文行使用一个与语义尽量匹配的视觉 Emoji；同一简介正文 Emoji 不重复；`👤` 淘汰。headline 与固定声明不参与正文 Emoji 规则。
- **BIO-016**：canonical headline 插在正文之后、平台固定尾部之前；不受正文 Emoji/行宽规则改写，必须原样复用。
- **BIO-017**：**XHS、视频号、抖音完整简介总长度均≤100个汉字等效字符**，包括正文 + canonical headline + 固定声明/尾部。先预留 headline 和尾部预算，再生成/压缩正文；固定声明不得删改。此前“总字数未知”的黄色缺口已被本次明确确认的≤100规则解决。
- **BIO-018**：本人明确填写的 strengths/traits/personality、自我介绍中的明确事实、合格客户反馈都可以作为对应来源的人物资产；来源必须保留，不能互相升级。
- **BIO-019**：兴趣只能来自明确的 `hobbies/interests` 或自我介绍中直接出现的真实兴趣；“内容支线”只是内容策略结果，不能反向自动写成本人的兴趣事实。
- **BIO-020**：当真实素材足够时，优先拆成更多合格、信息密度高的正文行，不把所有优势压成一行；同时仍受每维度1–3行、单行宽度和总长≤100约束。

## 6. Compliance Matrix
来源：`P=平台公开可验证规则`、`C=公司/项目合规要求`、`A=AIA Auto IP 更严格产品策略`。无充分平台公开依据时，不把内部策略冒充平台官方规则；产品门禁仍执行。
- **COMP-001 [P/C]**：简介不得包含电话、微信、邮箱、QQ、微博、二维码、URL/站外联系方式或其他导流信息；不得做站外导流或利益诱导；执行平台/公司更严格者。
- **COMP-002 [A/C]**：XHS 推荐简介正文和 canonical headline 禁止 `保险、金融、理财、贷款、股票、基金、医疗、护理、教育、玄学` 等当前产品敏感词；正文禁止 `友邦 / AIA` 及相关品牌变体。不声称这些全部都是平台官方普遍禁词。
- **COMP-003 [C/A]**：XHS 个人简介不得输出执业证编号。
- **COMP-004 [C]**：XHS 固定最后一句逐字为：`本账号所述内容为个人意见，不代表任何官方意见。` 一个字和标点都不能改，不能由 AI 改写，必须是整个简介最后一句，不得重复。
- **COMP-005 [C]**：视频号/抖音末尾固定连续三行：`本账号上所陈述或表达的内容仅为我个人意见，并不代表友邦人寿的意见`；`营销服务部：XXX`；`执业证编号：XXX`。三行顺序固定，不得拆开、换序或合并一行。
- **COMP-006 [C]**：视频号/抖音固定尾部中的“友邦人寿”不参与正文品牌敏感词误判；固定尾部不参与人物正文最低字数、12–20推荐区间、25字红线、Emoji或行长均衡规则。
- **COMP-007 [C]**：营销员编号 ≠ 执业证编号；不得用 agentId 冒充。营销服务部/执业证编号缺失时 AI 不得编造。
- **COMP-008 [C/A]**：历史 Preview `000` 仅为旧技术占位；正式推荐、复制、稳定稿和 Production 禁止 `000` 伪装真实执业证编号；缺失字段必须补真实值。
- **COMP-009**：合规过滤发生在最终推荐展示之前；不能“先推荐违规稿，复制时再提醒”。不合规候选不得成为最终推荐稿。固定尾部由唯一 Owner 追加，Prompt/AI/历史 Vxx 不得重复生成。
- **COMP-010**：合规门禁不得篡改真实事实；不合规素材淘汰、同事实合规改写或不进入最终稿，不能创造新事实。
- **COMP-011 [时效提醒]**：现有 UI 提醒保留：视频号昵称“每年最多修改5次”；视频号简介“暂无明确修改次数限制”；XHS简介“7天内最多修改3次，频繁修改也可能影响账号稳定”。这些可能随平台变化，发布前以平台实时提示/最新合规通知复核，不作为永久生成事实。

## 7. AI 权限边界
- **AI-001**：AI 可以在真实事实范围内做自然表达、提供候选、排列组合、优化自然度。
- **AI-002**：AI 不得创建人物事实，包括客户评价、无证据称呼/小名、学历、学校、职业、资质、荣誉、家庭身份、兴趣、服务能力、地域、年限等。
- **AI-003**：AI 原始输出不能直接成为最终输出，必须经过统一事实、资产、合规、长度和确定性排序 Gate。
- **AI-004**：AI 不拥有固定合规尾部，不拥有最终昵称排序，不得覆盖人工批准昵称，不得直接覆盖 `current_ip_outputs` 稳定稿。

## 8. 页面与 Interaction Contract
- **UI-001**：本轮重写人设 Engine，不默认重做成熟页面；除 PRD 明确修改项外，成熟布局、视觉、交互保持。
- **UI-002**：继续展示推荐昵称候选/首选、原昵称判断、一句话 IP、XHS简介、视频号/抖音简介及相关操作。
- **UI-003**：昵称/简介标题保留 `?` 合规入口，位于板块标题同一行；点击展示合规说明，不恢复旧折叠式窗口，不改变卡片布局。
- **UI-004**：第一次复制昵称和第一次复制简介分别独立展示一次对应平台合规/修改次数提醒；同一类型本页面会话看过后不重复弹。提醒不能替代生成前硬门禁。
- **UI-005**：页面保留短提醒：`AI 推荐仅供参考，本人长期喜欢且有特殊含义的昵称可能更适合。`
- **UI-006**：“就按这个改”生成新 proposal，历史版本不可变；明确修改事实字段时先更新事实，再只重算受影响输出。
- **UI-007**：用户修改不能绕过真实性/合规门禁。
- **UI-008**：稳定稿读取/展示遵守 STABLE；新增资料、刷新、重新登录或模型变化不导致随机换稿。
- **UI-009**：内容方向与脚本推荐成熟能力保留；有 IP 时消费 canonical 人设，无 IP 时按现有脚本库浏览并提示完成人设。
- **UI-010**：脚本详情仅保留一组“上一篇/下一篇”，位于正文底部；固定底栏仅“脚本改写 / 小红书排版”；切换后滚动回顶部。
- **UI-011**：保持成熟桌面/平板/手机响应式体验，不恢复已废弃旧浮层/布局。
- **UI-012**：资料保存后，用户以编号+姓名再次进入应读取历史资料、稳定稿和版本历史，不因刷新/二次进入丢失。
- **UI-013**：未生成 IP 时脚本推荐按一级标签→二级标签展示脚本库，PC/Pad两列、手机一列，顶部提示完成人设并跳转；生成后切换 canonical 人设推荐。
- **UI-014**：“我的资料”和“IP方案”入口均为纯图标，不显示文字/V1/V2；只在 IP 对话页展示，登录页、方案详情、脚本页、其他工具页隐藏；返回 IP 对话页恢复。资料浮层有明确关闭/收起，成熟拖动可保留但不得修改资料业务数据。可见性以真实页面状态为唯一真源，不建立与 DOM 并列的第二状态真源。
- **UI-015**：“我的资料”中个人介绍固定在最后一栏整行展示；客户反馈独立成“客户反馈”板块，按原问卷问题展示称呼、关系、眼中的我、愿意聊什么、角色认知、代表性评价等。重复答案聚合为 `靠谱 ×5`；代表性长文本可折叠查看更多。
- **UI-016**：原昵称板块位于“推荐昵称”上方，但不放在整个 IP 方案最顶部；原昵称多个问题按1/2/3解释。删除历史长提示“推荐昵称会综合人物称呼……不会为了标准化而强行塞满标签”。
- **UI-017**：首次复制合规弹窗沿用成熟两栏“可以说 / 不可以说”样式，不恢复“返回检查”按钮或长期折叠大板块；只保留确认后继续复制。
- **UI-018**：真正 Clipboard 写入由公共 `aiaClipboard` 统一执行，复制成功/失败均有明确反馈；业务组件不得各自实现第二套 Clipboard 行为。

## 9. 内容方向与脚本推荐的下游保护
- **CONTENT-001**：IP 内容结构遵循“主线 + 1条内容支线”。板块标题为“内容方向”；专业主线与内容支线明确分开。内部可以保留多个支线候选，但最终 IP 方案只展示排名第一、最值得长期经营的一条支线；没有足够真实、可持续积累时不硬凑支线。
- **CONTENT-002**：当 `primaryGoal=customer_acquisition`，专业主线只能来自受控拓客保险主题，如保险科普、家庭/医疗/重疾/意外保障、理赔知识、养老/财富/教育规划、税优/个人养老金等；纯招聘/加入团队/职业机会内容不得成为拓客主线。
- **CONTENT-003**：当 `primaryGoal=recruitment`，专业主线统一属于“增员与职业发展”，可围绕转型经历、行业发展、公司与团队、个人成长、从业日常、职业价值；重疾险、医疗险、教育金、家庭保障、理赔、保单配置等纯拓客内容不得成为增员主线。不存在第三种“双主线”最终状态。
- **CONTENT-004**：内容支线来自真实身份、过往经历、兴趣、客户反馈等，与专业主线是不同维度。泛健康/养生≠医疗保障；育儿/升学≠教育金保险；泛养老生活≠养老保险规划；一般职场成长≠增员招募。脚本库标签名称不能把生活支线反向升级成保险/增员主线。
- **CONTENT-005**：支线不能按用户选择顺序、字段顺序或 first-match 决定；必须做统一候选归一、去重和业务价值竞争。同一方向可保留多个真实来源。
- **CONTENT-006**：支线排序基础维度：目标人群重合度30%、客群价值20%、增员价值15%、信任建立能力15%、本人持续输出能力15%、传播潜力5%。这些是业务排序规则，不得把“骑行/高尔夫等兴趣”直接断言成高净值事实；年龄也不硬编码成单一30–50岁门槛。
- **CONTENT-007**：未知支线方向不能因为词库未收录而丢弃，仍按同一评分框架判断；一次 AI 推断不能永久提高基础分。分数接近时优先目标人群重合更高、本人真实积累更强者。
- **CONTENT-008**：IP 方案与推荐脚本必须读取同一个 canonical `primaryGoal`、专业主线和内容支线；历史内容规划、旧 purpose、旧 Vxx、脚本标签都不得覆盖当前 canonical 内容方向。
- **CONTENT-009**：内容方向展示保留成熟信息：内容方向、合集推荐、对账号的作用、来源、内容聚焦提醒，并提供“查看推荐脚本”入口；合集名称前台使用中文书名号。
- **SCRIPT-001**：有 IP 方案时，推荐页只分“保险主线/专业主线”和“内容支线”两个板块，主线在前；不在板块内再次重复内容方向层级。推荐脚本不得重复，不为填满数量跨到明显无关脚本。
- **SCRIPT-002**：每个推荐板块独立提供“换一批”；可匹配脚本不足两批时按钮禁用并说明原因。页面显示用户本地当天日期/“今日推荐”。
- **SCRIPT-003**：无 IP 方案时使用一级标签→二级标签筛选；“全部脚本”覆盖完整脚本库并提供真实分页（上一页、数字页码、下一页、总条数），不能只显示首屏结果。PC/Pad两列、手机一列，顶部提示完成 IP 方案可获得更精准推荐并提供跳转。
- **SCRIPT-004**：脚本库一级/二级标签只是内部匹配层；具体脚本正文内容优先于标签名，标签映射配置化，不能反向修改 IP 内容方向。推荐页面不得空白，导航必须真实加载推荐面板。

## 10. Engine、上下游与唯一 Writer
- **ENG-001**：目标链路：`Stable Output Resolver → Profile Facts → Evidence Engine → Asset Ranking → Nickname Builder → Headline Builder → Bio Builder → Compliance Gate → Canonical Output → UI`。
- **ENG-002**：推荐昵称、canonical headline、推荐简介、固定合规尾部分别只能有一个最终 Owner/Writer；Prompt 只提供候选，不是 Owner。
- **ENG-003**：历史 Vxx 只能承担明确的兼容/UI职责，不能继续写最终 nickname/headline/bio/compliance footer。
- **ENG-004**：禁止 MutationObserver、DOM 二次补丁或其他前端运行时再次改写已经生成的业务结果。
- **ENG-005**：禁止继续通过新增 V34/V35/V36 等 patch 脚本修 nickname/headline/bio；后续修改必须进入唯一规则模块/Engine 和对应 Contract。
- **ENG-006**：新 Engine 先独立实现+Contract 验证，再切页面；确认旧 Writer 不再运行后退役历史 Writer，避免补丁叠加。
- **ENG-007**：统一顺序：`稳定稿 → 新真实资料 → 排除运营素材 → 证据分级 → 资产竞争 → 低价值年限/黑话过滤 → 生成/增量补充 → 总字数预算 → 平台合规 → 固定声明 → Canonical 输出`。
- **ENG-008**：资料层、生成层、稳定稿层、UI层、内容方向、脚本推荐/改写层单向消费明确数据契约；下游不得回写或偷偷修正 canonical 人设字段。
- **ENG-009**：历史兼容脚本可暂存，但 Contract 必须防止旧 Writer 重新获得权威。
- **ENG-010**：页面成熟展示 Owner 可以存在，但“展示 Owner”不得等于“业务 Writer”。显示层可以排版/展开/复制，不能二次过滤、截断、重写 canonical nickname/headline/bio。

## 11. Contract / 验收
- **ACC-001**：Contract 覆盖事实不升级、时间精度、反馈来源隔离、反馈不伪造、稳定稿优先读取/刷新不重生成、proposal历史不可覆盖、saved_profiles/current_ip_outputs职责分离、稳定稿晋级门禁、nicknamePreset、Memory Score、六种路线/连接词、自然度、前职业退出昵称、canonical headline、Bio去重/行宽/Emoji/3行例外、服务≤6字、总长≤100、固定声明、执业证缺失、唯一 Writer、上下游只读消费。
- **ACC-002**：`≤100` 按完整最终简介验收，不能只测正文。
- **ACC-003**：真实 fixtures 至少覆盖：资料丰富、资料不足、只有反馈、approved preset、成熟原昵称、全英文原昵称、前职业强资产、从业<5年、执业证缺失、多项服务、多人评价冲突、增量资料更新、用户修改新 proposal、刷新/重新登录稳定稿不变化、弱新候选不得覆盖稳定稿。
- **ACC-004**：发布顺序：Contract → API → Playwright/浏览器 → 隔离 Preview → 技术验收 → 用户业务验收 → 冻结相同 RC → 明确批准后 Production。
- **ACC-005**：PRD/Matrix 固化阶段不修改业务代码、数据库、Preview 或 Production。
- **ACC-006**：旧测试全绿不能代替产品规则实现；旧测试与本 PRD 冲突时更新/淘汰旧测试，而不是把产品规则改回旧行为。
- **ACC-007**：Onboarding Contract 必须覆盖：已有资料不重复问、自我介绍只补缺失、模糊目标重新二选一、增员年龄无55+、学历含大专、contentTone 1–2、多选+自由文本、快捷标签不弹键盘、历史用户恢复。
- **ACC-008**：客户评价 Contract 必须覆盖：原始明细与聚合分层、本人自评/第三方来源隔离、咨询话题不升级服务能力、未匹配 agentId 报告且不静默建人。
- **ACC-009**：内容方向/脚本 Contract 必须覆盖：主目标硬过滤、只展示一个 canonical 支线、支线不按 first-match、标签不反向改内容方向、两板块顺序、去重、换一批、今日日期、无IP真实分页、全部脚本可达。
- **ACC-010**：UI Contract 必须覆盖：原昵称位置、客户反馈独立板块、个人介绍最后整行、纯图标悬浮入口页面可见性、首次复制独立一次提醒、两栏合规弹窗、统一 Clipboard、脚本详情唯一上一篇/下一篇。

## 12. 明确 SUPERSEDED 的历史规则
不得恢复：
- 同平台固定3套 Bio；
- 固定只选3–5个人物资产；
- 兴趣最多1–2；服务最多3–4；**服务单项≤4字（已被≤6字覆盖）**；荣誉最多1–2；
- “简介越短越好”；25字作为普通目标（当前只作为正文单行绝对上限）；
- 每行相同 Emoji / `👤`；
- 客户反馈来源前缀进入最终简介；
- 模糊关键词升级职业/经历；
- headline 与 Bio slogan 分别生成；headline 使用 `｜` 标签墙；
- 强制保险业务价值进入 headline；
- 过往职业作为新昵称；裸姓名默认首选；多个称呼凑满5个；全英文默认首选；
- 新昵称装饰符号/Emoji/无意义数字；万能尾缀批量默认；无人物锚点纯定位昵称；
- 旧 `purpose` 直接作为最终目标、双主线、模糊目标不再询问；
- “其他/不希望填写/跳过”等快捷逃逸项；
- 历史独立内容规划覆盖当前 IP 内容方向；
- 旧折叠式合规大板块和“返回检查”按钮；
- 正式输出 `000`；
- 历史旧 Writer/旧 Prompt/MutationObserver/DOM patch 对最终 nickname/headline/bio 的写入权。
