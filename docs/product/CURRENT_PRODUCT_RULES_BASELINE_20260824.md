# AIA Auto IP 当前有效产品规则基线（2026-08-24）

> 目的：把历史修改意见从“累加需求”改成“版本化决策”。同一功能以最新明确确认的意见为准；新意见只覆盖其明确修改的维度，未冲突的旧规则继续有效。
>
> 本文不是把 082101/0824 的历史意见机械照搬，而是整理当前有效规则。历史需求若与本文冲突，以本文为准；历史需求仍可保留在决策记录中，但不得重新驱动代码。

## 1. 需求版本规则

1. 同一功能冲突时，以最新明确确认的意见为准。
2. 新需求只覆盖它明确修改的维度。例如“悬浮按钮改为纯图标”只替代文字样式，不替代“只在 IP 对话页显示”。
3. 被替代的规则标记为 SUPERSEDED，不得继续作为实现或测试依据。
4. 无法判断是否覆盖时才提请产品确认，不自行合并矛盾规则。
5. 每次修复已确认缺陷，都应补充回归测试；不得只靠 Preview 人工发现复发。
6. 同一业务输出只能有一个 owner/唯一规则源；禁止继续用 Vxx 后加载脚本覆盖同一字段。

## 2. IP 业务目标（当前有效）

- 最终 `primaryGoal` 只能是：拓客 / 增员。
- 报名资料如果是“两者都要”“打造专业形象”“个人品牌”等非唯一答案，必须重新询问并二选一。
- 提示语要表达：刚起号阶段建议先从增员和拓客中选择一个方向，不要贪多；成熟后再扩展。
- 后续提问、IP方案、内容方向、脚本推荐全部读取标准化后的 `primaryGoal`，不得各自重新猜测。
- 增员路径的人群问题使用准增员对象语义；删除“有转型意愿的人群”等非具体人群特征；年龄选项不含 55 岁以上。

## 3. 资料收集与复用

- 已有报名资料、个人介绍、客户反馈中能提取的信息，不重复询问。
- 个人介绍需要语义提取过往职业、长期身份、爱好等，并回填基本资料。
- “过去做过什么工作/代表性长期经历”为多选；已有资料则不问。
- 学历选项包含“大专”。
- 所有问题删除“其他 / 不希望填写 / 跳过”等逃逸选项，但仍可允许用户自行输入补充（适用题型）。
- 个人介绍在“我的资料”最后一栏整行展示。
- 客户反馈单独成板块，按原问卷问题分别展示；相同答案聚合为 `靠谱 ×5` 等，不把所有反馈挤进一个字段。
- 登录后应复用已保存的资料和 IP 方案，不应因普通刷新要求重新填写。

## 4. 悬浮入口（最新规则）

- “我的资料”和“IP方案”均为**纯图标悬浮按钮**，不显示“我的/资料”“IP/方案”等文字。
- 不显示 V1/V2 等版本号。
- 只在 IP 人设**对话页**展示；登录页、IP方案详情页、脚本页等其他页面不展示。
- 从 IP 方案返回对话页后必须恢复显示。
- 点击后可展开资料/方案，并提供成熟、明确的收起交互。
- 视觉必须遵守既有 UI 组件库和友邦视觉规则，不另造孤立样式。

### 已替代
- 42：两行文字“我的/资料”“IP/方案” → 被 71“纯图标”替代。
- 52/62：图标+文字等中间方案 → 被 71 替代；其中“美观、遵守组件库”和“无版本号”继续有效。

## 5. 昵称

- 昵称**必须包含人物称呼**，且一个昵称中称呼只能出现一次。
- 称呼优先级：客户反馈中高频称呼 > 询问环节收集的称呼 > 根据真实姓名自然生成的亲和称呼 > 本名。
- 客户反馈次数相同，可按亲和力、好记程度、自然度排序。
- 原有视频号/小红书昵称先谨慎审查；好则优先建议保留，并给备选。不同平台昵称建议统一；昵称不宜频繁修改。
- “无/暂无/没有”等缺失值必须识别为空，绝不能评价为“建议保留”。
- 不得从“QS前100”等模糊学历信息推断具体学校。
- 不得机械生成 `成都+称呼`、`TOT+称呼`、`985+称呼`、`有温度+称呼` 等标签堆砌昵称。
- 不得出现“保险”二字等合规禁止项；详细以合规规则为准。
- 推荐昵称只能在已确认的受控昵称模板/词库范围内优先生成，匹配不到才允许 AI 补充。
- 对原昵称判定“不合适”必须理由充分、可解释；多个问题按 1/2/3 列出，不武断否定。
- 昵称板块保留提醒：标准化推荐仅供参考，用户最喜欢且有特殊含义、愿意长期使用的昵称可能更适合本人。
- 原有昵称板块位于“推荐昵称”上方，不放在整个 IP 方案最顶部。
- 删除长提示：“推荐昵称会综合人物称呼……不会为了标准化而强行塞满标签。”

## 6. 一句话 IP 定位

- 不包含人物称呼。
- 目标是“一句话让别人记住这个账号是什么定位/有什么差异点”，不是标签堆砌。
- 保险相关内容必须是主内容价值；生活兴趣不能反客为主。
- 使用最强差异点 + 保险主内容价值；禁止连续拼“称呼+职业+转型+行业+荣誉”。
- 不自行发明“专家/导师/顾问”等身份。
- 输出必须是自然中文，不能出现“留德华环保工程师转型保险顾问”一类机械拼接。

## 7. 内容方向：主线与支线

- IP方案板块标题为“内容方向”，不是“内容主线”。
- 保险主线与内容支线必须明确分开。
- **保险主线只能来自受控保险业务主题**：保险科普/家庭保障/重疾保障/医疗保障/养老规划/财富规划/教育规划等拓客业务主题，或增员/职业发展主题（具体取决于 `primaryGoal`）。
- 健康养生、育儿、美食、读书、旅行、智能家居、运动等均不得进入保险主线。
- 内容支线来源综合：家庭/生活身份、过往职业、个人介绍、爱好、客户反馈、口头补充等，不只读取某一个字段。
- 支线要按业务价值排序，不是原始标签顺序。育儿等能较自然触达保险核心年龄/家庭客群的内容，通常应高于泛美食等弱关联兴趣。
- 支线排序可考虑：目标客群年龄与保险主力购买年龄重合度、家庭责任相关性、高净值客群触达潜力、专业差异化、持续创作能力、本人真实积累。
- IP方案与推荐脚本必须读取同一个标准化支线，不得一个显示“育儿”、另一个变成“家庭与生活身份”。
- 脚本匹配允许受控的语义/同义映射，例如“家庭身份/宝爸宝妈”可关联育儿内容，但不得把支线映射成保险主线。
- 内容方向板块底部提供跳转“推荐脚本”的入口。

## 8. 推荐简介（当前重构目标）

### 8.1 信息来源
简介必须从真实资料选材，不自行补充事实：
- 个人介绍 / 自我介绍语义提取
- 过往职业和长期经历
- 家庭身份
- 学历（仅真实且足够具体的信息）
- 从业年限
- 真实荣誉
- 客户反馈高频评价
- 报名资料中明确填写的可提供服务
- 标准化后的保险主内容方向

### 8.2 生成原则
- 简介首先回答：你是谁、为什么值得关注、主要分享什么、有什么真实特色。
- 从素材池选 3～5 个最有价值的信息点，形成自然语言；不是字段标签墙。
- 保险必须是主内容；智能家居、读书、美食、养生等只能作为次要生活人设，不能成为主介绍。
- 不允许“二孩宝妈｜宝妈”同义重复。
- 不允许“宝妈｜环保工程师”这种不同维度信息无语义关系地硬拼。
- 不允许“靠谱”两个字单独成行。
- 不允许“读书｜美食”等纯兴趣为了凑丰富度机械成行。
- 可提供的服务可形成一个版本的服务行，例如 `养老规划｜保障规划`，但必须来自真实资料，每项尽量 4 字以内，不自行创造服务。
- 三个版本可以分别突出：专业背书 / 人设记忆 / 价值服务，但都必须有足够信息密度，不能为了差异化变得空洞。

### 8.3 合规尾部唯一输出
- AI 和简介主体不得生成营销服务部、执业编号、固定声明。
- 只有 `complianceFooter` 有权追加这些内容，并且每项只出现一次。
- 视频号/抖音合规声明顺序按已确认规则固定：
  1. `本账号上所陈述或表达的内容仅为我个人意见，并不代表友邦人寿的意见`
  2. `营销服务部：XXX`
  3. `执业证编号：XXX`
- 不允许任何旧 Vxx 层再次追加职业/执业编号或声明。

## 9. 昵称/简介复制合规

- 第一次复制昵称或简介时强制展示合规提醒；修改次数提醒使用平台固定文案，不由 AI 改写。
- 合规弹窗沿用既有成熟样式：左侧“可以说”，右侧“不可以说”。
- 不提供“返回检查”按钮，只保留确认后继续复制的操作。
- IP方案中不再使用原来的折叠式合规窗口。
- 昵称、简介板块的合规 `?` 位于各自板块**标题同一行**，不是贴在卡片角落。

## 10. 脚本推荐

- 有 IP 方案：只分“保险主线”和“内容支线”两个板块，保险主线在前；不在板块内部再次重复内容方向层级。
- 推荐脚本不得重复。
- 每个板块有“换一批”。
- 推荐页面显示当天日期，增强“今日推荐”感。
- 无 IP 方案：按一级标签 + 二级标签浏览；选择一级标签后展示对应二级标签；支持分页；电脑/平板两列、手机一列；顶部提示完成 IP 方案可获得更精准推荐并提供跳转按钮。
- “全部脚本”必须真的可通过分页访问全部结果，不能只展示首批。
- 脚本推荐页面不得空白；导航必须正确加载 recommendation 面板。
- IP方案中的内容方向与脚本推荐使用同一标准化主线/支线数据。

## 11. 脚本详情

- 底部工具栏只保留“智能改写”“小红书排版”。
- 上一篇/下一篇放在文章底部：上一篇左、下一篇右，使用成熟分页/文章导航组件样式。
- 详情正文去掉“开头：/正文1：/正文2：/结尾：”等结构标签。

## 12. 智能改写

- 人设代入不只是称呼，还要代入账号表达风格；界面要明确说明已经代入表达风格。
- DeepSeek 第一次返回格式不完整时自动重试/宽容解析，不能直接把“重新提交原文”的成本丢给用户。
- 复制改写结果必须有明确“复制成功”反馈。

## 13. 小红书排版

- 等待文案不得再出现已否定的“正在整理手机阅读节奏”等旧表达。
- 禁止 `【`、`】` 或其他单个标点独占一行；排版完成后需要结构校验。
- 表情使用需要有足够多样性，但不得为了数量机械堆表情；具体表情库/密度以专门排版规则为准。
- 复制排版结果必须有明确“复制成功”反馈。

## 14. 多选组件

- 选择标签后，输入焦点/键盘行为必须符合成熟组件交互：用户选完标签后可直接按 Enter 发送，不要求再点击输入框。
- 修复应在共享多选组件层完成，不允许每个问题单独打补丁。

## 15. Preview 专用能力

- Preview 提供“清空测试数据/从登录页重新开始”的入口；正式版不展示。
- Preview 与正式数据隔离时，需要明确说明哪些生产报名资料/客户反馈是否已同步，不能让产品验收误以为功能缺失。

## 16. 页面文案与 UI

- 页面固定文案优先级：已确认产品文档/规则 > 既有业务资料 > AI生成。
- “生成昵称、账号简介和表达方向”统一为“生成昵称、账号简介和内容方向”。
- 所有 UI 优先使用既有成熟组件和仓库 UI 规范；不得为了修单点问题新增孤立样式。
- 列表卡片之间必须有正常间距；响应式遵守既有桌面/平板/手机规范。

## 17. 禁止复发的典型案例

以下问题修复后必须转成回归测试：
- `视频号昵称=无` → 不得“建议保留”。
- `学历=QS前100` → 不得推断“诺丁汉大学”等具体学校。
- 昵称不得出现两个称呼，如“静姐说保障静静”。
- 昵称必须有称呼，不能只输出“成都”“暖心”等。
- 成都/TOT/985/有温度等不得机械拼昵称。
- 健康养生不得进入保险主线。
- 育儿支线不得在推荐脚本中无故变成“家庭与生活身份”。
- 执业编号在每个简介中只能出现一次。
- 简介不得出现同义重复“二孩宝妈｜宝妈”。
- 一句话 IP 定位不带称呼，不得机械标签拼接。
- 推荐脚本不得重复，不得空白。
- 多选后 Enter 必须可以直接发送。
- 复制改写/排版结果必须显示成功反馈。
- 客户反馈必须按问题分组展示，不得挤在一个字段。
- 个人介绍必须展示，并参与语义提取。

## 18. 工程治理

- 禁止新增 V34/V35 之类后加载覆盖层来解决上述核心规则。
- 目标判断、昵称、简介、内容方向、合规逐步迁移到唯一规则模块。
- 旧 Vxx 文件即使保留历史代码，只要与唯一规则源冲突，就必须停止加载或移除其写权限。
- 每次业务修改先确定 owner，再改 owner；不得在页面渲染后通过 MutationObserver/DOM 二次改业务数据。
- 每个核心输出建立 contract test；每个已确认缺陷建立 regression test。
- 阶段开发只跑影响范围内必要测试；自然验收节点再统一 Preview；适合合并 main 时再统一完整 QA/发布。
