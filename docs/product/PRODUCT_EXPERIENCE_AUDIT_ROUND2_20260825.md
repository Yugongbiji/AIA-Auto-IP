## 一、第二轮新增确定问题

### 1. 增员路径题目语义漏迁移
- `primaryGoal` 二选一已在 Core，但 V30/V31 停载后，“服务人群/客户年龄”切换成“准增员人群/准增员年龄”的逻辑没有迁入当前 Owner。
- 增员年龄应不含 55 岁以上；非具体人群特征不应作为快捷项。
- 判定：确定回归。

### 2. 个人介绍语义分析调用链丢失
- 后端 `/api/profile/analyze` 和 `backend/profile_semantic.py` 仍存在。
- 旧 V30 会在进入工作区前调用语义分析并只补空字段；V30 停载后前端没有等价调用，只剩 V27 的有限正则提取。
- 影响：个人介绍中已写明的信息可能再次被询问；职业/身份/爱好/服务等人物资产提取能力下降。
- 判定：确定回归。

### 3. 客户反馈存在双展示 Owner
- V27 已实现客户反馈分问题展示；V29 又实现一套 `renderStructuredFeedback()`，并会删除另一套反馈 DOM 后重新渲染。
- Owner 清单声明资料展示属于 V27，而 V29 应主要负责原昵称审查。
- 影响：双渲染、顺序竞争、闪烁、未来再次消失的高风险。
- 判定：确定治理违规；必须收成一个展示 Owner。

### 4. 昵称称呼来源优先级与最新规则不一致
- 最新规则：客户反馈高频真实称呼 > 询问环节收集的称呼 > 姓名自然称呼 > 本名。
- 当前最终昵称 Owner `nickname-policy-v1.js` 的 `anchors()` 把 `preferredName` 放在客户反馈 `topNicknames` 前。
- V19 辅助函数顺序正确，但最终昵称 Owner 没有复用它。
- 判定：确定业务回归。

### 5. 昵称受控生成引擎只实现了部分确认规则
当前已确认的昵称 V1 规则要求六类模板：身份、性格、地域、专业/过往经历、学历、成就；推荐 3–5 个方案尽量走不同路线，受控模板均无法自然匹配时才允许 AI 兜底。

当前 `nickname-policy-v1.js` 主要只覆盖：人物称呼本身、少量职业、家庭身份、博士、少量多人高频性格。

明显缺口包括：
- 地域模板未完整实现；
- MDRT/COT/TOT/五星等成就模板未完整实现；
- 硕士、985、211、QS 等学历路线未完整实现；
- 受控连接词路线未完整实现；
- 已长期使用原昵称中的人物称呼未进入生成锚点；
- 六类模板无法自然组合时的受控 AI 兜底未实现；
- 资料较少时可能只返回 1 个昵称，而不是规则要求的 3–5 个差异化方案。

判定：确定“规则已确认、Owner 实现不完整”。

### 6. 内容支线排序规则只实现了固定词表的简化版
最新内容支线规则要求：统一真实证据池、六维业务价值、目标（拓客/增员）影响排序、未知方向不能因词库未收录直接丢弃。

当前 V14 的缺口：
- 固定正则 `RULES` 未命中的未知方向会被直接丢弃；
- 没有按 `primaryGoal` 调整排序；
- 证据池相比已确认规则缺少/弱化口头补充、部分服务字段、服务人群等来源；
- 多来源证据使用 `Math.max`，没有充分体现多个独立真实证据叠加；
- 智能家居、家居改造、茶文化、收藏、桨板、马术等不在现有映射时无法按统一框架进入候选。

判定：确定实现不完整。

### 7. 推荐简介引擎未完整落实已确认 V1 模板
已确认简介规则要求：人物资产证据等级、最强资产选择、A/B/C 三种策略、自动删减、自然表达、地域/兴趣等可选资产。

当前 Core 仍主要是固定 4 行左右的字段式组合：
- 缺少完整的人物资产证据分级；
- 缺少“最强资产”选择流程；
- 地域、真实兴趣等有效素材利用不足；
- 同义性格/多个类似身份等自动删减不完整；
- 三个版本策略差异存在，但仍偏固定模板；
- 个人介绍的利用又受到语义分析调用链断开的影响。

判定：确定未完整迁移；78 不能只修 Emoji/版式。

### 8. `QS前100/985/211` 不反推具体学校的确定性保护没有覆盖整个方案
- 退役 V30 原来会清洗 nicknameOptions、advantages、headline、bios 等多个输出中的无证据具体学校名。
- 当前昵称、headline、bios 分别被新 Owner 控制后相对安全；但 `proposal.advantages` 仍主要保留模型输出，未见等价确定性 scrub。
- 影响：优势板块仍可能出现“QS 前100 → 某具体大学”之类无证据事实。
- 判定：高置信事实约束缺口；应把“类别信息不得推断具体事实”升级为方案级合同，而不是昵称单点合同。

### 9. 脚本详情上一篇/下一篇 UI 与当前推荐模块接口断链
- V17 仍生成上一篇/下一篇按钮。
- 点击调用旧的 `window.scriptRecommendationV1.openDetail()`。
- 当前推荐模块导出的是 `window.aiaScriptRecommendation={load,reset}`，没有旧对象也没有公开 `openDetail`。
- 判定：确定运行时断链。

### 10. V17 仍使用全 `document.body` class MutationObserver
- 79 已修 `profile-float` 全页面 observer，但 V17 仍对 `document.body` subtree 的所有 class 变化监听。
- 与 79 属同类放大风险，虽然回调较轻，但没有理由观察全页面。
- 当前稳定性测试只检查 `profile-float.js`，没有覆盖 V17。
- 判定：确定性能治理缺口。

### 11. 无 IP 脚本库分页 UI 缺失
- 后端 library API 已提供 `page/pages/total/page_size`。
- 当前前端有 `libraryPage` 状态并请求 `pageSize=20`，但没有看到可操作的上一页、数字页码、下一页、总条数组件。
- “全部脚本”因此不能通过 UI 可靠遍历完整 total。
- 判定：确定/极高置信回归。

### 12. 无 IP 脚本库桌面/平板两列布局未落地
- 最新规则要求电脑/平板两列、手机一列。
- 当前 `script-recommendation-v1.css` 中 `.script-card-list` 始终单列；`script-library-grid` 没有两列规则。
- 判定：确定 UI 回归。

### 13. 小红书 Emoji 密度低于当前有效规则
- 当前规则：平均每 1–2 句话至少 1 个 Emoji，任何连续 2 个完整句子至少有 1 个。
- 当前后端提示词仍是每 2–3 句话 1 个，最多连续 3 句话无 Emoji。
- 结构治理前 V5 的确定性密度补强已删除，未迁移。
- 判定：确定规则执行降级。

### 14. 小红书孤立标点/成对符号的确定性校验未形成可见保护
- 当前规则明确要求最终展示前程序化扫描并修复孤立 `【】（）、引号、句末标点` 等问题，不能只靠模型。
- 当前可见后端链主要依赖 Prompt + 结构标签清理；未发现对应的确定性输出校验/修复合同。
- 判定：高置信缺口；修复前应再做函数级确认。

### 15. 复制能力仍不是一个真正的公共 Owner
- Owner/基线要求创作结果复制反馈走公共组件。
- V28 自己实现 `writeClipboard()`；V10 仍另有昵称/简介 `navigator.clipboard.writeText()`。
- 功能表面可用，但同类基础交互存在两套实现。
- 判定：确定治理缺口。

### 16. “复制唯一 Owner”合同测试存在盲区
- `test_clipboard_success_has_one_owner()` 只检查 V22 与 V28，没有检查 V10 的直接 Clipboard 写入。
- 因而测试通过仍可能存在第二实现。
- 判定：确定测试假保护。

### 17. 创作 loading 尚未真正统一成公共状态组件
- 基线要求脚本改写等待态与小红书等待态统一管理。
- 当前 V22 只标准化小红书 waiting 文案；`app.js` 的脚本改写仍直接创建自己的“正在保留原文事实…”消息和状态文本。
- 判定：治理规则未完全落地；当前用户可见文案未必错误，但公共 Owner 目标未完成。

### 18. 一批 E2E 测试已经过期，无法提供真实保护
确认至少包括：
- `product-contract-v27.spec.js` 仍调用已不存在/退役的 `normalizeNicknameOptionsV19()`、`aiaProfileRulesV27.nicknameAudit()`；
- `product-integration-v30.spec.js` 仍要求 V30 是最后加载层、悬浮按钮两行文字，已与当前“V30 停载 + 纯图标”规则冲突；
- `product-contract-v29.spec.js` 部分文案断言与当前 V29 实现已不一致。

判定：确定测试资产过期，必须重写为当前 Owner 契约，不应重新加载旧代码让旧测试变绿。

### 19. ECS 本地必要检查没有运行上述 E2E
- `scripts/check-preview-local.sh` 当前只运行 3 个 Python 静态/合同测试文件；不运行 Playwright E2E。
- GitHub-hosted Actions 额度耗尽期间，旧 E2E 既没有自动运行，本地轻量检查也没有覆盖。
- 这解释了“contract 13/13 通过，但浏览器效果仍大面积回归”的一部分原因。
- 判定：确定 QA 覆盖缺口。后续应设计不依赖 Hosted Actions 的轻量浏览器冒烟或 self-hosted/ECS 方案，但仍遵守开发阶段不过度跑全量 QA 的节奏。

### 20. 客户反馈/资料与测试描述存在版本错位
- 旧 PR 清单仍保留“身边人怎么看我折叠摘要”等历史描述；最新 baseline 已改成“客户反馈单独成板块、按原问卷问题展示”。
- 当前产品应以 latest baseline 为准，不恢复旧折叠摘要。
- 判定：历史验收文档需要标注被替代项，否则后续开发可能误恢复旧效果。

### 21. `rules/ip-content-strategy-rules.md` 与最新 baseline 冲突
- 旧规则仍写“前台保险主线只能是保险科普 / 增员”。
- 最新 `CURRENT_PRODUCT_RULES_BASELINE_20260824.md` 明确更新为受控保险业务主题：保险科普、家庭保障、重疾保障、医疗保障、养老规划、财富规划、教育规划等，或增员/职业发展。
- 按版本治理规则，最新 baseline 胜出。
- 判定：旧规则文档应标为 superseded/更新，不能让未来开发误回退。

## 五、第二轮结论

第二轮证明第一轮不是“把所有问题都查完了”。新增发现集中在四类：
1. 退役 Owner 下线前未完整迁移；
2. 规则文档已确认但唯一 Owner 只实现了一部分；
3. 展示/调用接口改名造成运行时断链；
4. 测试看似存在但已过期或覆盖盲区。

在进入下一次 Preview 之前，应先按本文件与第一轮审计合并形成修复任务，不逐项打后加载补丁。修复应以当前 baseline + Owner 清单为准，并在每个根因修复时同步补当前 Owner 的 regression/contract test。
