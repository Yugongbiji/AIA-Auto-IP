# AIA Auto IP 最新有效需求总账（2026-08-25）

> 目的：把 AIA Auto IP 过去多轮产品修改从“历史意见堆叠”整理为“当前最新有效需求”。
>
> 本总账不是简单复制某一份旧文档，也不以当前代码现状反推需求。判断规则：**最新明确确认的需求覆盖冲突维度；新需求没有修改的旧维度继续有效；已经实现且符合最新需求的行为保持不动；历史已正确实现但后来回归的效果应恢复到当前唯一 Owner；从未完整实现的有效需求必须补齐。**

## 0. 事实源与版本判定方法

当前需求判定依次使用：

1. 最新明确确认的产品需求 / 当前产品基线；
2. 同期专项产品规则（昵称、简介、内容方向、脚本改写、小红书排版、通用交互、合规等）；
3. 更早产品设计中未被后续需求覆盖的维度；
4. 历史 Preview / 代码只用于证明“某效果曾经实现”，不能反过来覆盖最新需求。

冲突处理：

- 同一维度有明确后续意见：后者生效，前者标记 `SUPERSEDED`；
- 后续意见只改一个维度：其他旧维度继续有效；
- 专项文档负责细节、当前 Baseline 负责总边界；若 Baseline 后来明确否定专项文档中的某个具体写法，以 Baseline 为准；
- 无法通过时间、确认状态和覆盖维度判断时，才进入“需要产品确认”。

## 1. IP 业务目标

### 最新有效需求

- `primaryGoal` 最终只能是拓客 / 增员二选一。
- 报名资料为“两者都要 / 同时 / 兼顾 / 打造专业形象 / 个人品牌”等非唯一目标时，必须重新询问。
- 增员路径后续使用“准增员对象 / 准增员年龄”语义，不继续使用目标客户语义；增员年龄不含 55 岁以上。
- 后续提问、IP 方案、内容方向和脚本推荐必须读取同一标准化目标。

### 当前实现状态

- `web/ip-policy-core.js` 已成为目标与目标人群语义 Owner，并已覆盖二选一、目标人群题目切换、canonical proposal。
- **状态：✅ 基本实现；仍需真实路径/E2E 验证。**

## 2. 资料收集、复用与修改

- 过往职业/长期经历为多选；学历包含“大专”。
- 快捷选项删除“其他 / 不希望填写 / 跳过”等逃逸项，但允许自由输入。
- 登录/刷新复用已有资料和历史方案。
- 方案生成后，用户可在 IP 对话中直接修改资料；新字段（目标、职业、身份、爱好、服务等）也必须可保存。

## 5. 推荐昵称

### 最新有效需求

- 每个最终昵称必须有且只有一个人物称呼主体。
- 称呼优先级：客户反馈高频真实称呼 > 本人明确希望使用的称呼 > 姓名自然亲和称呼 > 本名兜底；已长期使用且自然的原昵称人物锚点应谨慎保留。
- “无 / 暂无 / 没有”等必须识别为缺失值。
- QS 前100、985/211、留学层级不得推断具体学校/国家。
- 推荐先经过合规、证据、唯一称呼、核心资产、受控模板；AI 只在受控模板无法自然匹配时兜底，且不得创造事实。
- 可用素材维度包括：真实身份/职业、经证实性格、真实地域、专业/经历、学历层级、真实成就、中性内容方向；但不能机械堆标签。
- 最新 Baseline 明确禁止 `成都+称呼`、`TOT+称呼`、`985+称呼`、`有温度+称呼` 这类机械拼接。因此专项词库中早期 `[真实地域]+[人物称呼]` 等简单模板只能在形成自然表达时使用，不能直接机械套模板。
- 原有昵称先谨慎审查；没有充分理由不武断要求修改；多个问题按 1/2/3 解释。
- 原昵称建议位于推荐昵称板块上方；保留“AI 推荐仅供参考、本人长期喜欢的昵称可能更适合”的短提醒。

### 版本关系

- 2026-08-24 08:33 的《昵称受控词库与模板 V1》提供六类模板细节。
- 2026-08-24 12:16 的 Current Baseline 后续明确禁止“成都/TOT/985/有温度 + 称呼”机械生成，因此后者覆盖“简单直接拼接”这一维度，其余六类素材/证据规则继续有效。

### 当前实现状态

- `nickname-policy-v1.js` 已实现真实高频称呼优先、唯一人物称呼、原昵称/职业/家庭身份/高频性格/中性内容的部分受控路线。
- **缺口：🔴 尚未完整实现受控词库要求的素材选择/策略体系，地域、学历、成就、长期原昵称人物锚点、AI 最后兜底等维度没有完整实现；同时必须避免把补齐这些维度做成机械标签拼接。**
- **测试：🟡 已有“无”、QS、双称呼等合同，但需要新增受控模板/证据/原昵称保留/机械拼接拒绝的行为测试。**

- 自然中文，不做“职业+转型+行业+荣誉”标签墙。
- 不发明专家/导师/顾问等身份。

### 当前实现状态

- **状态：🟡 结构符合，但固定模板化程度较高，需要真实资料样本做语言质量验收；不应为了改善文案再增加第二 Owner。**

## 7. 内容方向：保险主线 / 内容支线

### 最新有效需求

- 板块名称为“内容方向”。
- 保险主线与内容支线严格分开。
- 拓客保险主线只能来自受控保险业务主题；增员使用增员与职业发展主线。
- 健康养生、育儿、美食、读书、旅行、智能家居、运动等不得进入保险主线。
- 内容支线必须综合家庭/生活身份、过往职业、个人介绍、爱好、客户反馈、口头补充等真实证据。
- 未收录的新方向不能因为词库没有就直接丢弃；进入统一评分。
- 多来源证据增加可信度和优先级；排序结合业务价值、客群、持续输出、真实性，并按拓客/增员调整。
- 最终优先保留一个真实、长期可讲、业务价值更高的内容支线。
- 展示必须保留：内容方向、合集推荐、对账号的作用、来源、内容聚焦提醒；底部可跳转推荐脚本。

### 当前实现状态

- V14 已实现未知方向、证据累计、多来源 bonus、拓客/增员 bonus；Core 唯一写最终支线；V20 负责展示信息层。
- **状态：🟡 结构已明显对齐；仍需要固定真实样本验证排序结果是否符合业务价值，而不只验证代码存在。**

## 8. 推荐简介

### 最新有效需求

- 简介回答“我是谁 / 我有什么优势 / 我能带来什么”。
- 人物资产 A/B/C 级真实证据可用，AI 推断原则上禁止进入最终事实。
- 素材包括个人介绍、过往职业、家庭身份、学历、从业年限、真实荣誉、客户反馈、真实服务、保险主内容方向；地域、1–2 个真实兴趣可在有定位价值时使用。
- 从素材池选 3–5 个高价值信息，形成自然语言，不是标签墙。
- 三个版本分别走专业背书 / 人设记忆 / 价值服务策略，不能只是替换几个词。
- 自动删减同义身份/性格、过多荣誉、过多兴趣、重复事实。
- 保险始终是主内容；生活兴趣只作次要人设。
- 服务必须来自真实资料，不得因为保险营销员身份自动创造服务。
- 保留既有 Emoji 视觉锚点，但 Emoji 不是用来掩盖信息不足。
- 合规尾部只有 `complianceFooter` 一个 Owner；小红书只固定声明，视频号/抖音按“个人意见声明 → 营销服务部 → 执业证编号”，编号只出现一次，营销员编号不得冒充执业编号。

### 当前实现状态

- Core 已实现三策略、Emoji、真实职业/家庭/学历年限荣誉/客户反馈/服务、平台尾部。
- **缺口：🔴 当前实现仍偏固定 4–5 行模板，没有完整实现专项规则中的“人物资产证据等级 → 最强资产选择 → A/B/C 组合 → 自动删减”流程；地域几乎没有进入简介资产，兴趣/重复维度的自然组织也较简化。**
- **测试：🟡 合规尾部已有较强 contract；需要增加“信息密度、三策略差异、同义删减、服务真实性、地域/兴趣仅有价值时使用”的结构化测试。**

## 10. 脚本推荐

### 最新有效需求

#### 有 IP 方案

- 前台只分“保险主线 / 内容支线”两个板块，保险主线在前。
- 读取与 IP 方案完全相同的标准化主线/支线，不自行重算归属。
- 脚本不可重复，不为填满数量跨到明显无关脚本。
- 每个板块独立“换一批”；不足两批时禁用并说明。
- 展示用户本地当天日期 / 今日推荐。

#### 无 IP 方案

- 仍然可浏览完整脚本库，不能空白。
- 一级标签 → 对应二级标签；真实分页可遍历全部脚本。
- 电脑/平板两列、手机一列。
- 顶部提示完成 IP 可获得更精准推荐并可跳转。

#### 从更早产品设计继续有效、未被后续需求覆盖的维度

- 列表标题默认第一标题；热点有标识；元信息同一行包含一级/二级标签、字数、预计口播时长。
- 推荐阶段显示脚本库原始正文，不偷偷改写。
- 脚本使用行为应记录曝光、详情点击、脚本改写、小红书排版等行为，用于后续推荐优化。

### 当前实现状态

- V5 推荐模块 + V21 展示增强已覆盖两板块、去重、今日推荐、换一批；无 IP 已有标签和分页。
- 已记录 `impression`、`detail_click`。
- **缺口：🟡 旧产品设计中“点击脚本改写 / 点击小红书排版”的 activity 埋点当前 handoff 未明确记录；该维度没有被后续需求取消，应补齐。**
- **状态：🟡 页面结构基本对齐，需真实 API / 空库 / 少量脚本 / 多页脚本动态测试。**

## 12. 智能脚本改写

### 最新有效需求

- 保留原文事实、知识点、数字、核心结论，不随意改专业事实。
- 默认输出 3 篇明显不同的完整改写稿；多标题时分别处理。
- 人设代入不只是称呼，还包括真实定位、目标人群、优势、经历、荣誉及账号表达风格；仅在相关时自然代入，不强行编个人经历。
- “稿件处理说明”明确说明 IP / 账号表达风格代入情况。
- DeepSeek 格式异常自动重试/宽容解析，不把重提原文成本丢给用户。
- 可复制正文不混入分析、版本说明、内部标签或 `#标签`；标签单独给 10–15 个，前 5 个重点。
- 结果后给发布前人工微调提示。
- 用户明确“确认修改/按建议修改/重新改写”等应立即触发新版本，并继承本轮已确认修改意见。

### 当前实现状态

- `backend/script_persona_rules.py` 已读取 `contentTone/accountTone` 并在 breakdown 明示账号表达风格；有一次格式自动重试。
- 专项脚本改写规则仍是当前有效细节源。
- **状态：🟡 核心链路已实现；需要对“多标题拆分、确认修改立即触发、3 篇差异度、标签不进正文、既有修改意见继承”逐项建立/复核 E2E。**

## 13. 小红书排版

### 最新有效需求

- 只做换行、分段、少量 Emoji 和风险提示，不修改、删除、替换原文字词和标点。
- 每段最多 2 个完整句子；长句优先按自然停顿换行。
- 不允许 `【`、`】` 或其他孤立标点独占一行。
- 当前专项规则（2026-08-18）明确：**原则上每 2–3 句话配置 1 个 Emoji；若连续 3 句话没有合适关键词，在其中一句加中性 Emoji；避免每句都加。**
- Baseline 2026-08-24 只规定“具体表情库/密度以专门排版规则为准”，没有把密度收紧成“两句话必须一个”。因此专项规则仍有效。
- 等待态固定简洁为“正在排版，请稍候…”。
- 排版完成后给 10–15 个建议标签，正文外展示；风险检测只识别不改原文。
- 复制成功/失败反馈走公共 Clipboard。

### 当前实现状态

- 原文字词保护、孤立标点修复、公共 loading/copy 已存在。
- **回归：🔴 当前 `backend/xhs_formatting_contract.py` 被前一轮误收紧为“每连续两句话至少一个 Emoji”，这与最新有效专项规则冲突，需要恢复到 2–3 句节奏 / 最多连续 3 句无 Emoji，同时保留孤立标点修复和原文保护。**

## 14. 通用 Composer / 多选 / 自动滚动

### 最新有效需求

- 工作台优先聊天心智：问题 → 快捷项 → 同一输入框（已选标签 + 自由输入）→ 唯一发送按钮。
- 业务选择状态只能有一个真源。
- 禁止视觉层维护第二套 `Set` 作为提交真源。
- 禁止通过隐藏确认按钮、延迟 `.click()`、DOM 文本回读模拟提交。
- 点击标签不主动拉起手机键盘；已选标签在输入框内部；上下取消同步。
- 多选 + 自由文本一次性作为同一条用户消息提交；提交后清空并真实进入下一题。
- 桌面端选择标签后可直接 Enter；手机端只有用户主动点输入区才拉键盘。
- 新消息/下一题自动跟随；用户主动上滑阅读历史时不强拉，显示“回到最新”。

### 当前实现状态
