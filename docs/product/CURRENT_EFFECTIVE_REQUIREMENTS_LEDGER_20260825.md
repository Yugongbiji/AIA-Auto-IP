## 0. 需求版本判定方法

事实源优先级：

1. 本文件 `CURRENT_EFFECTIVE_REQUIREMENTS_LEDGER_20260825.md`；
2. 本文件明确引用/委托的专项规则；
3. `CURRENT_PRODUCT_RULES_BASELINE_20260824.md` 中未被本总账覆盖的维度；
4. 更早产品设计中未被后续需求覆盖的维度；
5. 历史 Preview / 代码只能证明某效果曾实现，不能覆盖产品需求。

冲突处理：

- 后续明确意见覆盖相同维度，旧规则标记 `SUPERSEDED`；
- 后续意见只修改一个维度，其他旧维度继续有效；
- 专项规则若明确写“补充并更新某旧规则，冲突以本文件为准”，且后续总账/Baseline 未再次否定，则专项规则是该维度当前细节源；
- 只有无法通过时间、明确确认和覆盖维度判断时才提交产品负责人确认，不自行折中。

## 5. 推荐昵称

### 最新有效需求

- 每个最终昵称必须有且只有一个人物称呼主体。
- 称呼来源优先：客户反馈高频真实称呼 > 本人明确希望使用的称呼 > 已长期使用昵称中的稳定人物锚点 > 姓名自然亲和称呼 / 本名兜底。
- 客户反馈同频时按公开自然度、亲和力、记忆度、发音输入、真实姓名关联等排序。
- “无 / 暂无 / 没有”等识别为缺失值，绝不能建议保留。
- QS 前100、985/211、留学层级不得推断具体学校/国家。
- 真实人物资产可以来自身份/职业、经证实性格、地域、专业经历、学历层级、真实成就、中性内容方向。
- 人物资产不能变成标签墙：禁止机械 `成都+称呼`、`TOT+称呼`、`985+称呼`、`有温度+称呼`。
- 受控策略优先，AI 仅在受控候选不足时兜底，仍必须通过人物称呼、事实、合规和非机械拼接围栏。
- 原昵称先谨慎审查；自然、好记、合规、有稳定识别时优先建议保留；多个问题按 1/2/3 解释，不武断否定。
- 推荐通常给 3–5 个不同路线；保留“AI 推荐仅供参考，本人长期喜欢且有特殊含义的昵称可能更适合”的短提醒。

### 版本关系

- `rules/nickname-source-ranking-v1.md` 规定真实称呼来源排序；其中早期示例“成都涛哥”等机械地域拼接已被后续禁令覆盖。
- `docs/昵称受控词库与模板-V1-20260824.md` 保留人物资产与证据规则；机械模板示例受后续禁令限制。

### 实现 / 测试状态

- `nickname-policy-v1.js` 已补齐高频称呼、本人称呼、原昵称人物锚点、职业/家庭身份、受控性格、地域、学历层级、成就、内容支线和受控 AI fallback。
- **状态：✅ 结构性缺口已补；🟡 需真实样本验证候选自然度与原昵称审查体验。**

## 7. 内容方向：保险主线 / 内容支线

### 最新有效需求

- 板块名称统一为“内容方向”。
- 保险主线与内容支线严格分开。
- 拓客保险主线只能来自受控保险业务主题；增员使用增员与职业发展主线。
- 健康养生、育儿、美食、读书、旅行、智能家居、运动等不得进入保险主线。
- 内容支线综合家庭/生活身份、过往职业、个人介绍、爱好、客户反馈、口头补充等真实证据。
- 未收录新方向不得因词库缺失直接丢弃，应进入统一评分。
- 多来源一致证据提高可信度和优先级；排序结合业务价值、客群、持续输出、真实性，并按拓客/增员调整。
- 最终优先保留一个真实、长期可讲、业务价值更高的内容支线。
- 展示保留：内容方向、合集推荐、对账号的作用、来源、内容聚焦提醒，并提供跳转推荐脚本入口。
- “合集推荐”的合集名称前台统一使用中文书名号，例如 `《家庭保障》`、`《育儿手记》`。

### 实现 / 测试状态

## 8. 推荐简介

### 最新有效需求

- 简介始终围绕三个问题组织：**我是谁 / 我的优势 / 我能提供什么价值**。
- 三个维度均可根据真实资料丰富程度使用 **1–3 行**，不要求平均分配，也不要求每个维度只能一行。
- 简介不是口播脚本或自我介绍文章；表达必须高度概括、凝练、信息密度高。能用更短表达准确说明同一事实时优先更短表达，例如“硕士学历”优先写“硕士”。
- 只使用 A/B/C 级真实证据：报名明确事实、本人自我介绍明确事实、多人客户反馈；AI 推断不得作为事实。
- 必须区分 `原始字段 → 已确认事实 → 简介允许表达`。模糊关键词不得升级成人物经历：资料只有“法律”时，不得写“曾从事法律工作 / 法律行业背景 / 法务工作经验 / 法律专业人士”；只有明确存在法务经历与年限时，才可写如“6年企业法务工作经验”。
- 后台可以保留客户评价的频次、人数和来源用于资格判断与排序，但最终简介只呈现结论，例如 `靠谱｜细致｜有耐心`；禁止“客户高频评价 / 客户都评价我 / 大家眼中的我 / 多位客户认为”等系统解释式前缀。
- 取消原机械减法：不再强制荣誉只留 1–2 个、职业经历只留一个、兴趣最多 1–2 个、服务最多 3–4 项。只要真实、有价值、有辨识度、合规且平台空间允许，就尽量保留。
- 仍必须删除重复信息、无事实依据的信息、AI 自行推断、AI 套话和空话、明显低价值信息、不合规内容。
- 单行空间利用是硬规则：不得让“靠谱 / MDRT / 硕士”等极短信息在有同维度可合并内容时单独浪费一行；同时不能过长导致自动换行。
- **每一行必须保持同一语义维度。** 例如 `二宝妈妈｜10年企业法务工作经验` 可共同回答“我是谁”；`硕士｜8年保险从业经验｜MDRT`、`靠谱｜细致｜有耐心` 可回答“我的优势”；`家庭保障｜养老规划｜子女教育` 可回答“我能提供什么价值”。禁止 `二宝妈妈｜跑步｜阅读` 或 `MDRT｜家庭保障｜二宝妈妈` 这类跨维度硬拼。
- 最终生成后必须做版面优化：检查过短行、过长换行、同维度合并机会、三个核心维度是否充分；仍有空间时补充下一优先级的真实高价值资料。
- 每位用户最终只推荐 **2 套平台简介**：小红书 1 套最终推荐版；视频号 / 抖音 1 套共用最终推荐版。两套差异来自平台合规、允许表达的信息和固定尾部，不为制造差异而拆散人物资料。
- 保险仍是主要业务内容；生活/兴趣只能在有真实证据且有助于人设时出现，不能挤掉更高价值人物信息。
- 保留成熟 Emoji 视觉锚点，但 Emoji 不能掩盖信息不足，也不能破坏同一行的语义维度。
- 合规尾部只有 `complianceFooter` 一个 Owner：小红书固定个人意见声明；视频号/抖音按“个人意见声明 → 营销服务部 → 执业证编号”，每项一次；营销员编号不得冒充执业证编号。
- 详细表达边界以 `docs/简介受控词库与模板-V1-20260824.md` 的 2026-08-25 最新确认版本为准。

### 版本关系

- `SUPERSEDED`：同一平台固定生成“专业背书 / 人设记忆 / 价值服务”三套简介。
- `SUPERSEDED`：从人物资产池固定只选 3–5 个信息。
- `SUPERSEDED`：兴趣最多 1–2 个、服务最多 3–4 项、荣誉机械压缩到 1–2 个等数量上限。
- `SUPERSEDED`：为了短而短、导致每个维度只有一条单薄信息的强制减法。

## 10. 脚本推荐

### 有 IP 方案

- 前台只分“保险主线 / 内容支线”两个板块，保险主线在前。
- 读取与 IP 方案相同的标准化主线/支线，不自行重算归属。
- 同批脚本不可重复，不为填满数量跨到明显无关脚本。
- 每个板块独立“换一批”；不足两批时禁用并说明。
- 展示用户本地当天日期 / 今日推荐。

### 无 IP 方案

- 可浏览完整脚本库，不能空白。
- 一级标签 → 对应二级标签；真实分页能遍历全部脚本。
- 电脑/平板两列、手机一列。
- 顶部提示完成 IP 可获得更精准推荐并可跳转。

### 更早设计中继续有效的未冲突维度

- 列表默认第一标题；热点有标识；一级/二级标签、字数、预计口播时长同一行。
- 推荐阶段显示脚本库原始内容，不偷偷改写。
- 行为记录：曝光、详情点击、点击脚本改写、点击小红书排版。

### 实现 / 测试状态

- `script-recommendation-v1.js` + V21 已覆盖两板块、去重、今日推荐、换一批、无 IP L1/L2 和真实分页。

## 12. 智能脚本改写

### 最新有效需求

- 保留原文事实、知识点、数字、核心结论，不随意修改专业事实。
- 默认输出 3 篇明显不同的完整改写稿；多标题时分别处理。
- 人设代入不只是称呼，还包括真实定位、目标人群、优势、经历、荣誉及账号表达风格；仅在相关时自然代入，不强行编个人经历。
