# Conversation Controls and Output Guardrails Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an agent revise or restart only their dialogue-derived IP information, while ensuring generated nickname, bio, and headline outputs are governed by deterministic rules rather than prompts alone.

**Architecture:** Profile editing lives in the existing profile drawer and reuses the existing question flow; completing an edit generates a new proposal version. A narrow reset endpoint removes only dialogue-derived profile fields and their dependent IP/content-planning history. The canonical front-end policy remains the sole writer of final nickname, headline, and bios; its rule enforcement is made explicit and regression-tested.

**Tech Stack:** Python 3.12, SQLite/PostgreSQL adapter, vanilla JavaScript, pytest.

**Spec:** Product items 170 and 171 confirmed 2026-11-05.

## Global Constraints

- Preserve name, agent ID, imported registration data, and customer-feedback data during reset.
- Reset only IP dialogue, IP proposals, and dependent content-planning records; leave script and XHS history intact.
- A single-field edit re-asks that exact question and generates a new IP proposal version after the answer is saved.
- `ip-policy-core.js` remains the sole canonical owner of nickname, headline, and bios.

## Review Focus

- Resetting must not erase peer-review feedback or imported profile values.
- A multi-select field follows the same edit/regenerate path as a normal field.
- Reset removes stale proposal cards so users cannot mistake old output for the restarted profile.
- Generated headline rejects unsupported claims and falls back to confirmed evidence.
- Generated bios append the fixed platform footer after deterministic body construction.
