# AIA Auto IP 新功能开发检查表

本检查表适用于任何新增页面、AI 功能、后台功能、用户体系、上传能力、数据结构、自动化流程，以及对现有功能进行较大扩展的任务。

目标：在写代码之前先判断“该不该自己做”，在完成之前检查“是不是把本来可以自动完成的技术工作又交给产品负责人手工验收”。

## A. 开发前：Build vs Reuse

- [ ] 这项能力属于 AIA Auto IP 核心业务，还是通用工程能力？
- [ ] 如果是通用工程能力，是否已经优先查找成熟组件、框架、官方方案或稳定第三方方案？
- [ ] 当前仓库里是否已有可复用模块、公共组件、接口、数据结构、规则或测试？
- [ ] 是否可以通过配置扩展现有能力，而不是复制代码或重新实现？
- [ ] 是否真的需要自定义？如果需要，是否记录了成熟方案不适用的原因？
- [ ] 新方案是否顺着当前技术栈，而不是为了局部需求强行重构整个项目？
- [ ] 是否避免并行引入多个解决同一问题的组件库/工具链？

## B. 业务与数据边界

- [ ] 核心业务目标、输入、输出和用户流程是否明确？
- [ ] AI Prompt、内容规则、合规规则是否与代码逻辑分离到合理位置，避免散落硬编码？
- [ ] 易变化的题目、选项、字段、文案、模型参数、环境差异是否可以配置？
- [ ] 是否复用了既有 API、字段定义和数据结构？
- [ ] Web 与未来微信小程序可以共享的业务逻辑、API、数据结构是否保持平台无关？
- [ ] 是否明确 Preview 与 Production 数据隔离要求？
- [ ] 是否存在可能破坏正式用户数据的迁移、批量更新或覆盖行为？若有，是否具备回滚/备份方案并升级为高风险操作？

## C. UI / UX 与组件

- [ ] Button、Select、Modal、Drawer、Tabs、Upload、Table、Form、DatePicker、Pagination、Tooltip、Loading、Empty、Error 等是否优先复用成熟方案或现有公共组件？
- [ ] 是否遵循“可以换皮，不轻易换骨头”：只做 AIA 品牌视觉适配，不随意重写成熟交互行为？
- [ ] 是否复用了 ChatWorkspace、Composer、QuickChoices、WelcomeCard、ProfileBar、ResultCard 等既有公共契约？
- [ ] 手机输入法、焦点、滚动、弹层关闭、标签状态、返回行为等是否由公共规则处理，而不是单页面打补丁？
- [ ] 是否考虑 360px、390px 手机和 1440px 桌面？
- [ ] 是否检查横向溢出、长文本、长标签、异常字符串、按钮可点击区域？
- [ ] 是否满足基础可访问性要求？

## D. 状态、异常与权限

- [ ] 是否有 Loading 状态？
- [ ] 是否有 Empty 状态？
- [ ] 是否有 Error 状态？
- [ ] 失败后是否有可执行 Retry，而不是只显示报错？
- [ ] 重试是否复用原业务入口，而不是复制一套旁路逻辑？
- [ ] 是否需要操作日志、任务日志或错误日志？
- [ ] 是否涉及登录、角色、权限或敏感数据访问？
- [ ] 是否对异常输入、重复提交、网络失败、API 超时、空结果等做了处理？

## E. 自动测试

- [ ] 是否为新业务主路径补充自动测试？
- [ ] 是否为本次修复的基础 Bug 增加回归测试？
- [ ] 公共组件变化后是否验证其他功能没有被连带破坏？
- [ ] 是否覆盖 Loading / Empty / Error / Retry？
- [ ] 是否覆盖移动端焦点、键盘和滚动行为（若相关）？
- [ ] 是否覆盖页面刷新、历史恢复或连续课堂使用路径（若相关）？
- [ ] 是否检查 serious / critical accessibility 问题？
- [ ] 是否把本可自动判断的基础技术问题留给产品负责人手工发现？如果是，继续补自动化，不应直接进入验收。

## F. CI / CD 与环境

- [ ] 新代码是否进入现有 Frontend QA / 自动测试流程？
- [ ] 是否在开发分支完成，而不是普通需求直接在 main / 正式环境试错？
- [ ] QA 通过后是否进入独立 Preview 环境供业务验收？
- [ ] Preview 是否继续使用独立测试数据，不写入正式 RDS？
- [ ] 正式部署是否继续依赖 main QA 成功？
- [ ] 正式部署后的 systemd、HTTP 健康检查和失败自动回滚是否保持有效？
- [ ] 是否避免用临时 SSH 手工操作替代已有标准部署流程？

## G. 可追溯与完成定义

- [ ] 重要技术选择是否记录了 Build vs Reuse 结论？
- [ ] 新增规则、配置、脚本是否进入 GitHub，而不是只存在聊天或个人电脑？
- [ ] 是否更新了相关文档，而不是让代码行为与规则文档长期不一致？
- [ ] 是否能说明本次改动的测试方式和回滚方式？
- [ ] QA 全绿是否仅代表“可以进入 Preview”，而不是默认允许正式上线？
- [ ] 是否已经获得产品负责人明确的“可以上线 / 合并 main / 发布正式版”授权？没有则不得自行合并正式发布。

## Codex 执行约束

Codex / 开发者在接到明确需求后，不应把这张表逐项反问产品负责人。

正确做法是：工程侧自行完成能够判断的技术检查，并只在以下情况请求产品决策：

1. 产品方向或核心业务规则有明显分叉；
2. 会明显影响成本、安全、权限、用户数据或长期架构；
3. 两种方案会造成明显不同的用户体验；
4. 准备把已经通过 Preview 验收的版本正式合并到 main。

除此之外，默认连续完成开发、测试、修复和 Preview 更新。
