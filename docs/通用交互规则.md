# AIA Auto IP 通用交互规则 V1

本规则适用于 IP 人设、内容规划、脚本改写、小红书排版，以及未来新增的所有对话型功能。局部功能不得另做一套相互冲突的多选、输入和页面跟随逻辑。

## 1. 核心原则

整个工作台优先呈现“聊天”体验，而不是“填表”体验。

- 快捷选项只是帮助用户快速填写答案，不是独立表单。
- 所有选择、自定义补充最终统一汇聚到底部输入区。
- 每一轮回答只保留一个最终动作：**发送**。
- 新对话出现后，正常情况下用户应立即看到最新内容，不需要手动向下寻找。

## 2. 多选题：快捷选项 + 输入框统一发送

### 2.1 页面结构

从上到下固定为：

**问题 → 快捷选项 → 已选标签/自由输入 → 发送按钮**

不得再出现“确认已选”之类的第二个提交按钮。

### 2.2 快捷选项

- 多选项放在底部输入区上方。
- 手机端优先保持单行横向排列，超出屏幕宽度后左右滑动，不向下堆叠很多行。
- 右侧可自然露出部分下一选项，让用户感知还能横向滑动，不额外添加冗长说明。
- 空白选项必须删除。
- 普通选项默认白底、细边框；选中后使用极浅红底、AIA Red 文字与边框。
- 选中状态不得使用大片实心红，避免多选时视觉过重。

### 2.3 已选内容进入输入区

用户点击一个快捷选项后，该选项立即以独立标签显示在底部输入区，例如：

`年轻家庭 ×` `新手爸妈 ×`

标签和自由输入内容必须视觉区分，不能简单连成一长串普通文字。

### 2.4 双向取消

上下状态必须同步：

- 再次点击上方已选选项：取消选择，底部对应标签同步消失。
- 点击底部标签的 `×`：标签消失，上方对应选项同步恢复未选中。

不得出现上下状态不一致。

### 2.5 自定义补充

- 用户始终可以直接在最下面的输入框补充其他内容。
- 不再生成空白“其他：____”输入项。
- 若保留“其他”快捷项，它只负责把输入焦点移到底部输入框，不作为一个空答案提交。
- 输入框 placeholder 应尽量结合当前问题，例如“还可以补充其他情况…”。

### 2.6 提交

用户最终只点击底部 **发送**。

提交时，将结构化的已选项和自由文本一起作为本轮答案发送。程序内部如有需要，应继续分别保存：

- `selectedOptions`
- `customText`

避免后续统计、画像或规则判断失去结构。

## 3. 单选题的兼容原则

单选题也尽量遵循同一心智：快捷项用于快速填写，底部发送用于最终提交。若现阶段某些单选题采用“点一下直接进入下一题”，后续优化时应优先统一为同一套输入心智，避免一个工作台出现多种完全不同的提交方式。

## 4. 新消息自动跟随规则

### 4.1 默认自动跟随

在正常连续对话中，只要产生新的用户消息、助手回复、新问题、生成状态或结果提示，对话区应自动滚动到最新内容，使新内容进入可视区域。

尤其是：

- 用户点击发送之后；
- 系统显示下一道问题之后；
- AI 返回新回复之后；
- 首次进入功能时欢迎卡后出现第一问；

以上场景不得要求用户再手动向下滑动。

### 4.2 尊重用户阅读历史

如果用户主动向上滑动，并距离底部超过约 `140px`，视为正在阅读历史内容。

此时：

- 新消息到达后不要强行把页面拉到底部；
- 显示轻量的 `回到最新 ↓` 按钮；
- 用户点击按钮后平滑滚动到最新内容。

一旦用户主动发送新消息，应退出“阅读历史”状态，并重新跟随最新对话。

### 4.3 滚动方式

- 对话过程使用平滑滚动，避免页面突然跳动。
- 只滚动当前功能的对话容器，不滚动整个浏览器页面。
- 切换功能后，各功能分别维护自己的对话位置。
- 自动滚动不得把固定的顶部导航、快捷选项或底部输入框顶出布局。

## 5. 手机端优先规则

- 页面左右安全边距保持 `12–16px`。
- 快捷选项横向滑动，不因为选项多而显著压缩对话区域。
- 已选标签区可以横向滚动，避免无限增高底部输入区域。
- 底部始终只保留一个主要提交按钮。
- 可点击控件建议最小高度约 `40–44px`；小型已选标签的删除按钮除外，但需保留足够触控区域。
- 新消息出现后，用户在正常聊天状态下第一时间看到新内容。

## 6. 适用范围

本规则是工作台级公共规则。当前以及未来所有功能，只要出现以下元素，就默认套用本规则：

- 对话消息；
- 快捷选项；
- 多选题；
- 自定义补充输入；
- 新回复/新问题；
- 历史消息滚动。

若单个功能确实需要例外，必须在该功能规则中明确说明例外原因，而不是自行形成另一套交互方式。
