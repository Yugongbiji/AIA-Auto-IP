# AIA Auto IP 工程效率与复用原则

本文件用于约束 AIA Auto IP 的长期开发方式。目标不是追求“技术上什么都自己写”，而是把有限开发精力集中到真正产生业务价值的部分：产品业务逻辑、内容规则、培训场景、AI 输出质量和用户核心流程。

本规则适用于 Codex、ChatGPT、人工开发者以及后续任何参与项目的工程实现。

> 总原则：**业务创新自己做，基础能力优先复用成熟方案；开发优先、阶段验收、一次发布、失败先诊断。可以配置就不硬编码，可以复用就不复制，可以自动化就不长期依赖人工。**

## 1. 职责边界

产品负责人主要负责确认：

- 产品目标与功能优先级；
- IP 人设、脚本推荐、脚本改写、小红书排版等核心业务逻辑；
- 培训场景与课堂使用方式；
- AI Prompt、输出结构、内容规则与合规要求；
- 用户核心流程和阶段 Preview 的业务验收；
- 会明显影响业务结果、成本、安全、权限或长期架构的关键取舍。

工程侧默认负责：

- 通用 UI / UX；
- 标准组件与交互；
- 登录、权限、上传、表单、弹层、分页、错误态等成熟工程能力；
- 数据访问、日志、异常处理、配置管理；
- 自动测试、CI/CD、Preview、部署与健康检查；
- 基础 Bug、响应式、可访问性与回归问题。

通用工程技术选择原则上不反复抛给产品负责人做细节选择。只有当选择会明显影响业务结果、成本、安全、权限、数据风险或长期架构时，才需要升级为产品决策。

## 2. 六条长期原则

### 2.1 业务创新自己做，基础能力优先成熟方案

属于 AIA Auto IP 核心差异化的能力可以自定义，例如：

- IP 人设问答与资料补齐逻辑；
- 内容主线方法论；
- 脚本推荐逻辑；
- 脚本改写规则；
- 小红书排版规则；
- 友邦培训场景中的 AI 对话流程；
- 特定合规与内容生成规则。

不属于核心差异化的能力，如果已有成熟组件、框架、官方能力或稳定第三方方案，默认不得从零开发。典型包括：

- Button、Select、Modal、Drawer、Tabs、Upload、Table、Form、DatePicker、Pagination、Tooltip；
- 登录、会话、权限、文件上传；
- 日志、重试、错误处理；
- 调度、任务状态、健康检查；
- 自动测试、可访问性检查、CI/CD；
- 常规后台管理能力。

只有成熟方案无法满足明确业务要求，或引入成本/风险高于自定义实现时，才允许自研，并记录原因。

### 2.2 配置优于硬编码

容易变化的内容应优先配置化，例如：

- 题目顺序、快捷选项、字段映射；
- Prompt 参数、模型名、环境地址；
- 文案、状态提示、功能开关；
- 权限角色、上传限制、分页大小；
- Preview / Production 环境差异。

不得因为“先跑起来”把大量业务值散落在多个 JS/Python 文件中长期维护。

### 2.3 复用优于复制

同一业务含义或交互行为只能有一个主要实现来源。

发现两个页面出现相同逻辑时，优先抽公共模块、公共配置或公共组件，不允许长期通过复制代码分别修改。

特别是：聊天工作区、Composer、快捷标签、自动滚动、Loading / Empty / Error、复制结果、重试等能力，应按现有公共规则复用。

### 2.4 自动化优于人工重复操作

能够稳定自动判断的事情，不长期交给产品负责人手工检查。

优先自动化：

- 基础 UI 回归；
- 移动端 viewport 与横向溢出；
- 键盘/焦点/滚动；
- Loading / Empty / Error / Retry；
- API 冒烟与健康检查；
- 阶段 QA；
- Preview 部署；
- 正式部署后的最小健康检查和必要回滚。

自动化不等于“每个小改动都跑全部检查”。检查必须分层，在合适的阶段执行。产品负责人主要验收业务体验和结果，不承担“人肉测试基础组件”的职责。

### 2.5 标准流程优于临时脚本

一次性的临时脚本可以用于排障，但凡出现第二次使用需求，就应评估进入正式流程、命令、后台入口、CI 或自动任务。

不得形成只有某个开发者记得如何执行的隐性操作。

### 2.6 可追溯优于“现在能跑就行”

重要变更必须能回答：为什么改、改了什么、如何测试、如何部署、出错后如何定位或回滚。

相关规则、代码、配置和工作流应进入 GitHub。但可追溯不代表为每个微小修改建立独立 PR 或完整发布链；同一自然开发阶段可以集中提交、集中验收、集中发布。

## 3. 新功能开发前必须做 Build vs Reuse 与 Now vs Later 判断

任何新增页面、AI 功能、后台功能、用户体系、上传、数据结构或自动化流程，在写代码前先判断：

1. 这是 AIA Auto IP 的核心业务能力，还是通用工程能力？
2. 当前仓库是否已有可复用模块、规则、接口、数据结构或测试？
3. 浏览器原生能力、现有技术栈、成熟组件/框架、官方方案或成熟第三方方案是否已经覆盖？
4. 是否可以通过配置扩展现有实现，而不是复制或新写一套？
5. 这是当前核心闭环必须做的吗？不做是否阻塞当前主要功能？
6. 能否放到后续阶段，在真实使用反馈出现后再做？
7. 如果仍要自定义，实现带来的业务收益是否足以覆盖维护、测试和兼容成本？

默认决策顺序：

`当前核心闭环 → 现有模块复用 → 配置扩展 → 当前技术栈兼容的成熟方案 → 小范围封装 → 最后才是从零开发`

非当前核心闭环所必需的工程扩展默认延后，避免项目早期过度工程化。

## 4. 当前项目技术栈下的具体约束

当前仓库前端以 `web/` 下原生 HTML / CSS / JavaScript 为主，后端由 Python 服务提供；Node 目前主要承担 Playwright / axe 自动验收。

因此：

- 不为了“看起来工程化”强制把整个项目迁移到 React、Vue 或其他大型框架；
- 新需求先顺着现有轻量架构实现；
- 新增复杂通用组件时，优先选择与当前静态前端兼容、维护成本低的成熟方案；
- 如果未来确实需要引入统一前端框架，必须因为规模、复用、维护收益已经明显成立，而不是为了某一个按钮或弹窗重构全站；
- 一旦项目正式选定新的组件体系，后续优先沿用同一体系，不再并行引入多套相同用途的 UI 库。

## 5. 对未来 Web 与微信小程序的复用要求

未来如果增加微信小程序版本，应优先复用：

- 业务规则与 Prompt；
- 后端 API；
- 数据结构与字段定义；
- 权限与用户状态模型；
- 内容生成逻辑；
- 合规规则；
- 设计 Token、品牌色与信息层级；
- 测试用例中的业务场景。

Web 与小程序可以拥有不同的视图组件，但不得各自复制一套业务规则和服务端逻辑。

## 6. 默认开发流程：开发优先、阶段验收、一次发布

### 6.1 开发期：连续开发，只做必要的局部检查

同一自然功能阶段内，默认允许连续完成一批相关修改。不要每改一点就重复执行全量 QA、Preview、PR、main 合并和正式部署。

开发期只运行与当前改动直接相关的快速检查，例如语法、目标接口、目标页面或少量关键用例。普通小修改可以集中在同一开发分支和同一阶段 PR 中。

### 6.2 阶段验收：一个完整功能或自然节点完成后统一 Preview

当一个完整功能、一个页面优化批次或一个自然开发阶段完成后，再统一执行相关自动测试并部署一次 Preview。

产品负责人在 Preview 上集中体验业务效果、内容、UI 和核心流程，并一次性提出修改意见。反馈继续在当前阶段集中修改，不因为每轮小反馈重复走正式发布流程。

### 6.3 阶段收口：只在准备合并时跑完整 QA

完整 Frontend QA、Playwright 回归、可访问性检查以及其他较重检查，原则上放到阶段准备收口时统一执行一次。

如果改动只影响明确局部，可按风险选择相关测试；涉及公共组件、核心主流程、数据安全或大范围样式时，再扩大回归范围。

### 6.4 正式发布：原则上一个阶段只发布一次

推荐主流程：

`连续开发 → 阶段 Preview → 集中修改 → 完整 QA → 合并 main → 正式部署 → 最小生产冒烟`

只有收到产品负责人明确的“合并 main / 正式上线”指令后才发布生产。除紧急线上故障外，不因为每个小修改频繁发布生产。

### 6.5 正式发布后的最小检查

生产发布默认只需要确认：

1. GitHub `main` 当前 commit 与 ECS 实际运行 commit 一致；
2. 正式核心服务处于 active / healthy；
3. 正式首页和本阶段核心功能可访问。

数据库、所有 API、所有页面、所有交互不应无差别绑成每次发布的阻塞门槛；它们应根据本次变更风险进入阶段 QA 或针对性冒烟检查。

## 7. 生产故障规则：失败先诊断，禁止连续改代码碰运气

当正式站没有更新、页面异常、接口异常或部署失败时，根因未确认前不得连续创建多个“尝试修复”PR。

默认诊断顺序：

1. 读取 GitHub `main` 当前 commit；
2. 读取 ECS `/opt/AIA-Auto-IP` 当前 commit；
3. 如果二者不一致，**立即停止下游排查，先解决代码同步/部署问题**；
4. 确认 systemd 实际 WorkingDirectory、ExecStart 和运行进程；
5. 确认本机正式端口返回的版本/页面；
6. 确认 Nginx / 反向代理实际指向；
7. 最后才排查浏览器缓存、数据库和具体业务 API。

### 7.1 版本一致性优先级最高

`GitHub main commit != ECS commit` 时，不允许先去修改页面、数据库、Nginx 或业务代码。

2026-08-21 的正式发布排障已经证明：Preview 和 QA 均正常时，生产 ECS 仍可能停留在旧 commit。以后遇到“Preview 是新版、正式站是旧版”，第一检查项必须是 GitHub main 与 ECS commit 是否一致。

### 7.2 增加可直接识别生产版本的能力

项目应保持一个简单的 `/version` 或等价健康接口，返回当前运行 build / commit。若当前实现尚未具备，应在不阻塞核心产品开发的前提下，于最近的合适工程阶段补上。

以后判断“正式站是否已经更新”时，优先使用版本接口或 commit 对比，不依赖肉眼判断页面，也不先猜浏览器缓存。

### 7.3 一次性诊断优于反复人工命令

需要 ECS 排障时，优先一次性收集 commit、systemd、端口、Nginx、健康检查等必要信息。不要让产品负责人反复 SSH、逐条复制命令、逐步试错。

重复出现的诊断动作应逐步封装为脚本、健康接口或自动部署日志。

## 8. 测试分层规则

长期测试分为三层，不允许每一步把三层全部重复执行：

- **开发期：** 快速局部测试，只覆盖本次修改直接影响范围；
- **阶段收口：** 完整自动测试 + Preview + 产品业务验收；
- **正式发布：** 最小生产冒烟，重点验证版本一致、服务正常、本阶段核心功能可用。

安全、权限、生产数据迁移等高风险变更可以提高检查级别，但必须基于风险，而不是默认所有修改都走最高强度流程。

## 9. 项目计划允许动态微调

项目上线总计划继续作为方向地图，但不是一次性施工清单。

每进入一个新功能或阶段，都应重新判断：

- 当前最重要的核心闭环是什么；
- 哪一步不做就无法继续；
- 哪些功能可以真实使用后再补；
- 哪些工程建设现在投入产出比过低；
- 是否出现新的真实反馈，需要调整最早的计划顺序。

优先完成主要功能的小闭环，再逐步增加后台、监控、复杂自动化、跨端能力等扩展。

## 10. Codex / ChatGPT / 开发者默认工作方式

接到需求后默认连续完成：

1. 读取当前 main、项目看板与相关规则；
2. 判断当前最重要任务以及 Now vs Later；
3. 做 Build vs Reuse 判断；
4. 在开发分支连续实现当前自然阶段的一批相关修改；
5. 开发中只做必要的局部检查；
6. 到自然验收节点后统一跑相关测试并更新 Preview；
7. 由产品负责人集中验收并反馈；
8. 阶段收口时再跑完整 QA；
9. 主动判断是否已经适合合并 main，并给出合并建议；
10. 只有收到明确“合并 / 上线”后才进入正式发布；
11. 正式发布后执行最小生产冒烟；
12. 若失败，先按第 7 节完整诊断，再决定修复，不靠连续 PR 试错。

普通技术细节不需要逐项请求产品负责人确认；改变产品方向、核心业务规则、生产数据风险、高风险上线以及重大架构/成本/权限选择除外。

## 11. 与其他规则的关系

本文件负责“是否应该现在做、是否应该自己开发、如何提高开发与发布效率”的最高层工程原则。

具体前端行为继续以以下文件为准：

- `docs/前端工程化与自动验收规范.md`
- `docs/公共组件契约.md`
- `docs/通用交互规则.md`
- `docs/界面设计规范.md`

如果其他工程文档中的“每次修改都必须执行完整 QA / Preview / 发布”等流程性要求与本文件冲突，以本文件的**测试分层和阶段验收原则**为准；安全、权限、生产数据等高风险专项规则除外。

具体业务逻辑继续以 `rules/`、业务方法论文档和对应功能规则为准。
