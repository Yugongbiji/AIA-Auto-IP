# AIA Auto IP 前端工程化与自动验收规范 V2

本规范用于把 AIA Auto IP 从“功能能跑 + 人工逐项找问题”升级为“设计系统约束 + 成熟组件复用 + 公共交互组件 + 自动化验收 + Preview 业务验收 + 受保护正式部署”。

> 重要：本规范**不替代、不删除现有 AIA 品牌视觉规则**。`docs/界面设计规范.md` 中已经确定的 AIA Red `#D31145`、深红、80%/60%/40%/20% 红、中性色、页面留白、辅助文字等继续作为项目视觉基准。本规范只补充工程化、组件化、复用和自动验收要求。

> 开发总原则同时遵循 `docs/工程效率与复用原则.md`：**业务创新自己做，通用工程能力优先复用成熟方案。**

## 1. 产品与工程职责边界

产品负责人主要负责：

- 功能板块与业务流程；
- 需要展示和收集的内容；
- 业务规则、培训逻辑、问答顺序、生成结果；
- AI 输出方向与核心用户体验；
- Preview 的最终业务验收。

前端工程与自动测试应负责：

- 手机键盘与焦点行为；
- 页面滚动和新消息可见性；
- 响应式布局与溢出；
- 按钮、输入框、标签、卡片、弹层等基础交互；
- Loading / Empty / Error / Disabled 等通用状态；
- 可访问性与常见浏览器兼容；
- 回归测试，避免修一个地方坏另一个地方；
- 成熟组件/原生能力/现有公共组件的选型与复用。

不得把上述基础交互问题长期依赖产品负责人手工发现，也不得把普通 UI 技术选型反复抛给产品负责人。

## 2. 设计规则来源与优先级

### 2.1 品牌视觉层

优先遵循现有 AIA 品牌视觉规范：

1. `docs/界面设计规范.md`；
2. 已确认的 AIA 官网视觉参考；
3. 项目内既有品牌色、字号、间距和卡片层级。

### 2.2 通用交互层

交互细节优先参考成熟平台规范，不在项目里从零发明：

- Apple Human Interface Guidelines：移动端输入、触控、滚动、反馈与一致性；
- Material Design：组件状态、布局、表单和响应式原则；
- WCAG 2.2：可访问性、焦点、对比度、触控目标、语义信息。

当成熟交互规范与 AIA 品牌视觉冲突时：**交互行为遵循成熟规范，颜色与品牌表达保留 AIA 规范。**

## 3. 成熟组件优先：可以换皮，不轻易换骨头

### 3.1 标准交互不得默认从零开发

以下通用组件/能力，新增需求时必须先检查当前仓库、浏览器原生能力和成熟组件方案，不允许默认手写一套新的交互逻辑：

- Button
- Select / Combobox
- Modal / Dialog
- Drawer / Sheet
- Tabs
- Upload
- Table
- Form / Validation
- DatePicker
- Pagination
- Tooltip / Popover
- Loading / Skeleton
- Empty
- Error / Retry
- Toast / Message
- 常规菜单、下拉、确认框、开关和分页导航

AIA Auto IP 可以根据品牌视觉调整颜色、字体、圆角、间距、边框、图标和视觉层级，但原则上不重写成熟组件已经验证过的键盘、焦点、关闭、无障碍、触控和状态管理行为。

一句话原则：**可以换皮，不轻易换骨头。**

### 3.2 当前技术栈下不强制重构

当前前端以 `web/` 下原生 HTML / CSS / JavaScript 为主，项目没有为了业务页面引入 React/Vue 等大型前端框架；Node 当前主要用于 Playwright / axe 自动测试。

因此：

- 不为了使用某个组件库强行重构全站；
- 简单、稳定、浏览器原生已经解决的能力优先使用平台能力；
- 新增复杂通用组件时，优先评估与当前静态前端兼容、依赖少、维护成熟的方案；
- 如果当前公共实现已经稳定且有自动测试，可以继续复用，不因“外面有库”而无收益替换；
- 如果未来项目规模确实需要引入统一前端框架，应做一次整体 Build vs Reuse / 架构评估并统一选型，而不是每个页面各自引入一套 UI 库；
- 一旦选定统一组件体系，后续同类组件优先沿用，不再并存多套重复方案。

### 3.3 只有业务独有交互才优先自定义

真正值得自定义的是 AIA Auto IP 的差异化体验，例如：

- IP 人设缺失资料追问；
- 内容规划的特定方法论流程；
- AI 对话与结构化快捷选项的组合；
- 培训课堂连续使用流程；
- 内容生成、改写、排版结果的特定交互；
- 友邦业务/合规要求带来的特殊流程。

即使是业务独有流程，其中的按钮、弹层、输入、上传、表格、错误提示等基础零件仍优先复用成熟能力。

## 4. 公共组件原则

以下能力必须视为工作台级公共组件，不允许每个功能重新实现一套：

### ChatWorkspace
统一负责：

- 消息列表；
- 新消息自动跟随；
- 用户查看历史时暂停自动跟随；
- “回到最新”入口；
- 移动端可视区域与固定输入区协调。

### Composer
统一负责：

- 文本输入；
- 已选标签嵌入输入区；
- 发送按钮；
- 手机键盘焦点；
- 输入区高度增长与内部滚动；
- 禁止点击快捷标签时主动唤起软键盘。

### QuickChoices
统一负责：

- 单选 / 多选快捷项；
- 选中 / 取消状态；
- 手机横向滑动；
- 与 Composer 中标签双向同步；
- 不产生第二个“确认已选”按钮。

### WelcomeCard
统一负责首次进入功能时的产品介绍卡样式、层级和间距。

### ProfileBar
统一负责 IP 资料悬浮摘要、展开/收起、只读展示和辅助说明。

### ResultCard
统一负责 AI 生成结果、复制、重新生成、错误与加载状态。

公共组件的详细行为以 `docs/公共组件契约.md` 和 `docs/通用交互规则.md` 为准。

## 5. 组件状态最低要求

每个可交互公共组件至少覆盖：

- default；
- hover（桌面端）；
- focus-visible；
- active / selected；
- disabled；
- loading；
- empty；
- error；
- long-content；
- narrow-mobile。

不得只实现“正常状态”。

弹层类组件还必须覆盖：

- ESC / 返回行为（适用平台）；
- 点击遮罩是否关闭的明确规则；
- 焦点进入与退出；
- 背景滚动锁定；
- 手机端键盘与 viewport；
- 重复打开/关闭；
- 异常内容长度。

这些属于工程验收，不应等待产品负责人逐项发现。

## 6. 移动端硬性验收规则

手机端至少以常见窄屏宽度进行自动测试（目前包括 360px、390px）。

必须满足：

- 页面无非预期横向溢出；
- 固定顶部导航不遮挡主要内容；
- 底部输入区始终可达；
- 快捷选项超宽时横向滚动；
- 标签点击不主动 focus 文本输入；
- 已选标签与文本输入位于同一视觉输入容器；
- 新问题出现后，在正常聊天状态下自动进入可视区域；
- 用户主动上翻历史时不被强制拉回；
- 点击发送后恢复自动跟随；
- 重要触控控件建议达到约 44px 的可触控尺寸；
- 长文字、长昵称、长标签不得破坏布局；
- 手机输入法、焦点、自动滚动、弹层关闭、返回和键盘行为不能以“产品负责人人工试出来”为主要发现机制。

## 7. 自动测试分层

### L1 静态与布局冒烟测试
每次提交都跑：

- 页面能打开；
- 四个功能入口存在；
- 360px / 390px / 1440px 无明显横向溢出；
- 关键输入框和发送按钮可见；
- 基础 WCAG 自动扫描无 serious / critical 错误。

### L2 公共交互测试
公共组件变化时跑：

- 快捷标签选择/取消；
- 标签不会主动唤起输入焦点；
- 标签进入 Composer 内部；
- 发送后清空本轮临时选择；
- 新消息自动跟随；
- 上翻历史后显示“回到最新”；
- 再次发送后恢复自动跟随；
- viewport / 键盘变化；
- 超长文本；
- Loading / Empty / Error / Retry；
- 弹层或新基础组件的关键关闭、焦点和异常状态（若本次涉及）。

### L3 核心业务流程测试
持续覆盖：

- 匹配到营销员资料；
- 无资料直接进入；
- IP 首次问答；
- 内容规划首次问答；
- 生成方案；
- AI 请求失败、超时、空结果；
- 页面刷新和历史恢复；
- 四功能连续课堂使用路径。

发现基础 UI Bug 后，应同时评估：**修公共实现 + 增回归测试**，而不是只在单页面打补丁。

## 8. Web 与未来微信小程序

如果后续增加微信小程序：

优先共享：

- 后端 API；
- Prompt 与 AI 编排；
- 业务规则；
- 字段与数据结构；
- 权限/用户状态模型；
- 合规规则；
- AIA 品牌 Token 和设计规范；
- 业务测试场景。

Web 与小程序可以使用各自平台成熟的 UI 组件体系，不要求强行共享视图层代码；但不得复制两套业务规则和服务端逻辑。

## 9. CI / Preview / 正式部署门禁

当前标准流程：

`开发分支 → Frontend QA → QA 通过 → 自动部署 Preview → 产品负责人业务验收 → 明确允许上线 → 合并 main → main 再跑 Frontend QA → QA 成功 → 自动部署正式 ECS → 健康检查`

硬性规则：

- QA 全绿 ≠ 自动允许正式上线；
- QA 全绿只代表可以进入 Preview 进行产品验收；
- 未收到“可以上线 / 合并 main / 发布正式版”的明确指令，不得自行进入正式发布；
- Preview 与 Production 数据必须隔离；
- 不得为了普通开发直接在正式 ECS 上试错；
- 正式部署必须保留现有 systemd + `127.0.0.1:8000` HTTP 健康检查；
- 新版本启动失败或健康检查失败时，保留自动回滚上一 commit 的保护机制。

## 10. 开发完成定义（Definition of Done）

以后 Codex / 开发者说“完成”前，至少应满足：

1. 功能逻辑完成；
2. 完成 Build vs Reuse 判断；
3. 通用能力优先使用成熟方案或已有公共组件，不重复造交互；
4. 手机与桌面基础自动测试通过；
5. 无明显横向溢出；
6. 焦点、键盘、滚动、弹层等符合公共规则；
7. Loading / Empty / Error / Retry 等必要状态完整；
8. AIA 品牌颜色和视觉层级未被破坏；
9. 相关规则文档同步更新；
10. QA 通过后进入 Preview，而不是直接把普通改动上线；
11. 产品负责人主要做业务验收，不承担逐个寻找基础交互 Bug 的职责。

## 11. 当前改造策略

当前项目继续采用渐进式工程化：

- 不大规模重写现有 HTML/CSS/JS；
- 先复用成熟能力和现有公共实现；
- 继续用自动测试约束行为；
- 重复逻辑出现时逐步收敛为真正公共模块；
- 当原生架构的维护成本已经明显高于统一框架收益时，再做整体架构评估。

禁止两种极端：一是所有基础交互都自己造；二是为了“先进技术栈”无业务收益地重构整个可用系统。
