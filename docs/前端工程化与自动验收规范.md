# AIA Auto IP 前端工程化与自动验收规范 V1

本规范用于把 AIA Auto IP 从“功能能跑 + 人工逐项找问题”升级为“设计系统约束 + 公共交互组件 + 自动化验收 + 测试通过后部署”。

> 重要：本规范**不替代、不删除现有 AIA 品牌视觉规则**。`docs/界面设计规范.md` 中已经确定的 AIA Red `#D31145`、深红、80%/60%/40%/20% 红、中性色、页面留白、辅助文字等继续作为项目视觉基准。本规范只补充工程化、组件化和自动验收要求。

## 1. 用户与开发职责边界

产品负责人主要负责：

- 功能板块与业务流程；
- 需要展示和收集的内容；
- 业务规则、问答顺序、生成结果；
- 最终产品体验是否符合业务目标。

前端工程与自动测试应负责：

- 手机键盘与焦点行为；
- 页面滚动和新消息可见性；
- 响应式布局与溢出；
- 按钮、输入框、标签、卡片等基础交互；
- Loading / Empty / Error / Disabled 等通用状态；
- 可访问性与常见浏览器兼容；
- 回归测试，避免修一个地方坏另一个地方。

不得把上述基础交互问题长期依赖产品负责人手工发现。

## 2. 设计规则来源与优先级

### 2.1 品牌视觉层

优先遵循现有 AIA 品牌视觉规范：

1. `docs/界面设计规范.md`；
2. 已确认的 AIA 官网视觉参考；
3. 项目内既有品牌色、字号、间距和卡片层级。

### 2.2 通用交互层

交互细节优先参考成熟平台规范，不在项目里从零发明：

- Apple Human Interface Guidelines：移动端输入、触控、滚动、反馈与一致性；
- Material Design：组件状态、布局、表单和响应式原则；
- WCAG 2.2：可访问性、焦点、对比度、触控目标、语义信息。

当三者与 AIA 品牌视觉冲突时：**交互行为遵循成熟平台规范，颜色与品牌表达保留 AIA 规范。**

## 3. 公共组件原则

以下能力必须视为工作台级公共组件，不允许每个功能重新实现一套：

### ChatWorkspace
统一负责：

- 消息列表；
- 新消息自动跟随；
- 用户查看历史时暂停自动跟随；
- “回到最新”入口；
- 移动端可视区域与固定输入区协调。

### Composer
统一负责：

- 文本输入；
- 已选标签嵌入输入区；
- 发送按钮；
- 手机键盘焦点；
- 输入区高度增长与内部滚动；
- 禁止点击快捷标签时主动唤起软键盘。

### QuickChoices
统一负责：

- 单选 / 多选快捷项；
- 选中 / 取消状态；
- 手机横向滑动；
- 与 Composer 中标签双向同步；
- 不产生第二个“确认已选”按钮。

### WelcomeCard
统一负责首次进入功能时的产品介绍卡样式、层级和间距。

### ProfileBar
统一负责 IP 资料悬浮摘要、展开/收起、只读展示和辅助说明。

### ResultCard
统一负责 AI 生成结果、复制、重新生成、错误与加载状态。

## 4. 组件状态最低要求

每个可交互公共组件至少覆盖：

- default；
- hover（桌面端）；
- focus-visible；
- active / selected；
- disabled；
- loading；
- empty；
- error；
- long-content；
- narrow-mobile。

不得只实现“正常状态”。

## 5. 移动端硬性验收规则

手机端至少以常见窄屏宽度进行自动测试（约 360–430px）。

必须满足：

- 页面无非预期横向溢出；
- 固定顶部导航不遮挡主要内容；
- 底部输入区始终可达；
- 快捷选项超宽时横向滚动；
- 标签点击不主动 focus 文本输入；
- 已选标签与文本输入位于同一视觉输入容器；
- 新问题出现后，在正常聊天状态下自动进入可视区域；
- 用户主动上翻历史时不被强制拉回；
- 点击发送后恢复自动跟随；
- 重要触控控件建议达到约 44px 的可触控尺寸；
- 长文字、长昵称、长标签不得破坏布局。

## 6. 自动测试分层

### L1 静态与布局冒烟测试
每次提交都跑：

- 页面能打开；
- 四个功能入口存在；
- 360px / 390px / 桌面尺寸无明显横向溢出；
- 关键输入框和发送按钮可见；
- 基础 WCAG 自动扫描无严重错误。

### L2 公共交互测试
公共组件变化时跑：

- 快捷标签选择/取消；
- 标签不会主动唤起输入焦点；
- 标签进入 Composer 内部；
- 发送后清空本轮临时选择；
- 新消息自动跟随；
- 上翻历史后显示“回到最新”；
- 再次发送后恢复自动跟随。

### L3 核心业务流程测试
后续逐步加入 API mock：

- 匹配到营销员资料；
- 无资料直接进入；
- IP 首次问答；
- 内容规划首次问答；
- 生成方案；
- AI 请求失败、超时、空结果。

## 7. CI / 部署门禁

目标流程：

`提交代码 → Playwright 自动测试 → 通过 → 才允许部署`。

现有生产部署工作流先保持不变，工程化分支先建立独立 CI。待自动测试稳定后，再把部署工作流改成依赖测试成功，避免一次性改变生产链路。

## 8. 开发完成定义（Definition of Done）

以后 Codex / 开发者说“完成”前，至少应满足：

1. 功能逻辑完成；
2. 使用公共组件，不重复造交互；
3. 手机与桌面基础自动测试通过；
4. 无明显横向溢出；
5. 焦点、键盘、滚动符合公共规则；
6. AIA 品牌颜色和视觉层级未被破坏；
7. 相关规则文档同步更新；
8. 再提交 PR / 合并 main。

## 9. 当前改造策略

V1 不大规模重写现有前端框架，先建立“规则 + 测试底座”，并对现有 HTML/CSS/JS 做可持续约束。待测试稳定后，再逐步将重复逻辑收敛为真正的模块化组件，避免一次重构影响当前上课使用的网站。
