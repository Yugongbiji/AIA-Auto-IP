# 产品修改防回归规则

> **长期项目管理门禁。** 目标：防止“这次改好了，下一次改别处后旧问题又回来”。
> 本文件属于项目管理规则，不是本轮 PR 的临时说明。

## 1. 当前事实源优先级

继续开发前必须按以下顺序读取：

1. `docs/product/CURRENT_EFFECTIVE_REQUIREMENTS_LEDGER_*.md` —— 最新有效需求总账；
2. 与当前功能相关的专项产品规则（昵称、简介、内容方向、脚本改写、小红书、通用交互、合规等）—— 负责被总账保留/委托的细节；
3. `docs/product/CURRENT_PRODUCT_RULES_BASELINE_*.md` —— 上一版产品基线快照，只保留未被后续总账覆盖的维度；
4. `rules/product-rule-ownership.md` —— 每个核心输出的唯一 Owner；
5. `rules/product-change-governance.md` —— 修改、测试、Preview、发布治理；
6. `docs/项目管理/当前任务看板.md` —— 当前阶段进度；
7. 代码当前真实状态。

**历史聊天、旧 PR 描述、旧 Vxx 文件不得覆盖上述当前事实源。**

## 2. 同一需求不是累加，而是版本化

- 同一功能发生多次修改，以**最新明确确认的意见**覆盖冲突维度。
- 新意见没有修改的维度，旧规则继续有效。
- 被替代规则必须标记 `SUPERSEDED`，不能因为旧代码还在仓库里而重新生效。
- 例：悬浮按钮早期“两行文字”已被最新“纯图标”替代，但“只在 IP 对话页显示”继续有效。
- 例：昵称专项词库允许地域作为人物资产，但后续 Baseline 明确禁止 `成都+称呼` 机械拼接，因此“地域可用”继续有效，“直接城市+称呼”被替代。
- 例：小红书 Emoji 密度由最新总账明确委托专项排版规则，因此不得由后续工程重构自行收紧成另一套密度。

## 3. 单一 Owner 是硬门禁

核心业务输出必须只有一个 Owner。当前 Owner 以 `rules/product-rule-ownership.md` 为准。

任何修改前必须先检查：

- 现在是谁在写这个字段/组件？
- 是否还有旧文件第二次写入？
- 是否存在后加载 wrapper / MutationObserver 再次覆盖？

如果存在多个写入点：**先收口 Owner，再开发产品修改。**

禁止：

- 新增 V34/V35 等“最后覆盖层”；
- 依赖脚本加载顺序保证业务正确；
- AI、前端、旧补丁分别生成同一个声明/执业编号；
- 用 MutationObserver 修改最终业务数据。

## 4. 已出现过的问题必须变成回归测试

每个产品负责人已经发现并确认的问题，修复时必须增加自动回归检查。

至少永久覆盖：

- “无”不得被判断为好昵称或建议保留；
- QS 前 100 不得推断具体学校；
- 昵称必须有且只能有一个称呼；
- 成都/TOT/985/有温度等不得机械拼昵称；
- 健康养生不得进入保险主线；
- IP 方案与脚本推荐读取同一个内容支线；
- 每个简介中执业证编号只能出现一次；
- 营销员编号不得当作执业证编号；
- 一句话 IP 定位不带称呼；
- 个人介绍必须展示并参与语义提取；
- 客户反馈必须按问题分组展示；
- 多选后 Enter 可以直接发送；
- 推荐脚本不得重复、不得空白；
- 复制改写/排版必须有成功反馈；
- 已确认的成熟 UI/字段完整性不能因修改其他功能而被无意改变。

**同一个问题不得依赖产品负责人第二次人工发现。**

## 5. Preview 前必须执行“禁止复活检查”

进入产品验收前，工程侧必须先确认：

1. `index.html` 当前真实加载链；
2. `SUPERSEDED` 文件没有被重新加载或动态注入；
3. 同一核心字段没有第二写入点；
4. 当前 Owner contract tests 通过；
5. 本轮影响范围 regression tests 通过；
6. 最新有效需求总账中的当前阶段条目没有未说明缺口；
7. 专项规则与总账委托维度一致，测试没有继续验证旧版本需求；
8. 页面 smoke：无空白、无重复字段、按钮可用、关键流程可完成；
9. 固定真实营销员样本输出没有旧问题复活；
10. 未被本轮需求修改的成熟 UI / 字段 / 交互没有发生意外变化。

任一项失败，**不交给产品负责人 Preview 验收**。

## 6. 产品负责人与工程侧的验收边界

产品负责人主要判断：业务是否合理、内容质量是否好、表达是否符合真实场景。

以下基础问题必须由工程侧先发现：

- 页面空白；
- 同一编号/声明重复；
- 已删除选项重新出现；
- 旧规则复活；
- 多选组件键盘失效；
- 推荐脚本重复；
- 固定文案错误；
- 明确违反最新有效需求总账的结果；
- 未被需求修改却发生变化的版式、字段和基础交互。

## 7. 与低 Actions 成本流程结合

继续遵守：**开发优先、阶段验收、一次发布、失败先诊断**。

- 连续完成同一阶段相关修改，不为每个小改动重复完整 QA/Preview；
- 开发阶段只跑 owner + 影响范围测试；
- 自然验收节点统一 Preview；
- 合并 main 前再跑完整 QA；
- Actions/部署失败先读日志找根因，禁止连续提交碰运气。

## 8. 完成定义

一个产品修改只有同时满足以下条件才算真正完成：

- 当前有效需求已经进入最新有效需求总账；
- 被替代旧规则已失去加载/写权限；
- 最终输出只有一个 Owner；
- 回归测试已新增或更新；
- 影响范围检查通过；
- Preview 前禁止复活检查通过；
- 产品业务验收通过。

**“现在页面看起来对”不等于完成。**
