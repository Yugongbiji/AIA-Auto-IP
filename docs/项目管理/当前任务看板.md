9. 完成后更新本看板的状态和必要的技术决策记录。

## 8. 自动判断是否应该合并 main

这是长期项目规则，不依赖产品负责人主动询问。

### 8.1 什么时候必须主动判断

出现以下任一情况，Codex / ChatGPT / 开发者都应主动检查当前 PR 是否应该收口并合并 main：

- 一个相对完整的产品阶段已经开发完成；
- PR 已经变大，继续叠加新功能会明显增加回归或审查风险；
- 自动测试、Frontend QA、Preview 已经具备完整验收条件；
- 准备开始一个边界清晰的新功能或下一阶段开发；
- 产品负责人连续要求“继续”时，也不能只无限往当前 PR 堆代码，应同步判断是否到了合并节点。

### 8.2 建议合并 main 的门槛

原则上同时满足以下条件时，应主动告诉产品负责人：**“当前 PR 已达到可合并状态，建议合并 main。”**

1. 当前阶段范围已经完整，不存在必须与本 PR 同时完成的阻断项；
2. 后端/单元测试通过；
3. Frontend QA 通过；
4. Preview Deploy 成功；
5. Preview 核心业务流程无阻断性回归；
6. 没有已知的高风险数据、权限、安全或生产配置问题；
7. 后续工作可以自然拆到新的分支 / PR，不需要继续扩大当前 PR。

如果自动检查未达到门槛，应直接说明还差哪一项，而不是笼统说“再等等”。

### 8.3 只建议，不自动合并

- 达到门槛后，系统必须**主动给出合并建议**，不等产品负责人问“什么时候合并”。
- 给建议时应简要说明：QA、Preview、主要验收结果，以及下一阶段准备拆到哪个 PR。
- **不得因为判断为可合并就自行合并 main。**
- 必须收到产品负责人明确表达“可以合并 / 合并 main / 上线”等授权后，才执行合并。
- 合并后应核对 main QA、正式部署和 Production 健康检查；失败时按现有回滚规则处理。
