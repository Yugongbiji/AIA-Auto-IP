## 1. 当前阶段

**阶段：Web 培训版本已具备完整工程底座，正在从“持续微调”进入“上线收口”。**

当前 main 已有四个功能入口、Python 后端、DeepSeek、RDS 路径、Preview 隔离、Playwright/axe QA、正式 ECS 自动部署与回滚。现在优先级不是继续堆基础设施，而是用现有工程能力把核心业务流程、移动端体验、AI 输出和上线验收收口。

当前开发分支 `agent/login-screen-simplify` / PR #2 正在收口一组相关产品修改，暂未合并 main：

- 登录页删除四功能介绍卡与红人计划大图；
- 修复 QuickChoices → Composer → Send 的多选提交链路；
- 直接进入 IP 时按“姓名 → 9 位营销员编号 → 城市…”收集，并在编号后尝试二次匹配资料库；
- 不再主动收集/展示个人介绍和生成偏好；
- 内容规划主目标删除“两者兼顾”；
- 视频号/抖音简介末尾固定连续输出“个人意见声明 → 营销服务部 → 执业证编号”，并明确营销员编号不得替代执业证编号；
- 小红书合规声明固定放在简介最后一句。

## 3. 当前 P0：上线收口

> P0 的定义：影响下一次真实培训/正式使用，不应被低优先级优化打断。

### A. 四功能业务验收

- [ ] IP 人设：按真实营销员资料完整走一遍“识别 → 补充 → 生成 → 修改 → 再进入恢复”
- [ ] 内容规划：验证自动带入 IP 档案、生成和历史恢复
- [ ] 脚本改写：按规则文档做至少一组真实长脚本验收
- [ ] 小红书排版：按规则文档做至少一组真实内容验收
- [ ] 确认四个功能的 AI 输出中没有互相串规则

### B. 培训现场旅程

- [ ] 已报名营销员正常匹配资料
- [ ] 未匹配/Guest 路径符合预期
- [ ] 手机端从进入网站到拿到结果不需要异常刷新或绕路
- [ ] 重复进入时历史状态符合规则
- [ ] AI 请求慢、失败、超时、空结果时营销员知道发生了什么以及如何继续

### C. 自动化覆盖核对

- [ ] 将当前 P0 业务验收中可自动化的部分补进 Playwright，而不是长期留给产品负责人手测
- [ ] 核对移动端 360–430px 关键路径
- [ ] 核对 Loading / Empty / Error / Disabled
- [ ] 核对键盘、焦点、标签、滚动回归测试
- [ ] 核对 axe 严重问题

### D. 正式发布前核对

- [ ] Preview 验收通过
- [ ] 正式环境 RDS 配置确认
- [ ] DeepSeek 正式密钥/模型配置确认，不泄露到仓库
- [ ] main QA 通过
- [ ] ECS 部署成功
- [ ] Production HTTP 健康检查通过
- [ ] 上线后四功能 smoke
- [ ] 有明确回滚路径

## 7. Codex 开工规则

每次开始新任务：

1. 先读本看板；
2. 再读与任务相关的业务规则和工程规则；
3. 判断任务属于 P0/P1/P2；
4. 做 Build vs Reuse；
5. 优先解决当前 P0，不擅自扩 scope；
6. 可自动验收的内容必须补自动测试；
7. 完成后更新本看板的状态和必要的技术决策记录。
