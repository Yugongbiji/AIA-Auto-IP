## 6. Codex / ChatGPT 开工规则

每次开始或继续开发：

1. 先读本看板；
2. 再读相关业务规则和工程规则；
3. 读取当前 main、开发分支和 PR 的真实状态，不按聊天记录猜代码；
4. 判断任务属于 P0/P1/P2；
5. 做 Build vs Reuse；
6. 优先解决当前 P0，不擅自扩 scope；
7. 自动测试要与开发阶段匹配，不得因为每个小 commit 都跑全量 UI 回归而阻断连续开发；
8. 每完成一个相对完整阶段，都自动判断是否应该合并 main；
9. 完成后更新本看板和必要的技术决策记录。

## 7. 开发与验收节奏（长期规则）

### 7.1 核心原则

**先形成可见、可用的完整功能闭环，再集中验收；测试服务于开发，不让开发服务于测试。**

跨数据库、API、前端页面的功能，不能每完成一个小步骤就停下来等待整套 Playwright / Preview。产品负责人应尽早看到完整页面和真实业务流程。

### 7.2 开发过程中：快速自检，不跑全量回归

连续开发期间，只做与当前修改直接相关、能快速完成的检查，例如：

- Python / JS 语法与模块加载；
- 新增单元测试或目标测试；
- API 能启动且核心接口不报错；
- 页面能打开、核心组件能渲染；
- 当前修改涉及的关键路径做定向检查。

原则上不要因为每一个小 commit 都等待完整 Frontend QA / 全量 Playwright / Preview Deploy 才继续下一步。即使 workflow 自动触发，也不需要停下开发等待结果，除非暴露会阻断后续开发的基础性错误。

### 7.3 完整功能闭环后：阶段性 QA

当一个用户能实际使用的闭环完成后，再集中运行相关自动验收，并让产品负责人实际体验页面。

### 7.4 PR 收口 / 合并 main 前：全量 QA

准备收口 PR 时运行完整质量门禁：后端/单元测试、Frontend QA / Playwright、Preview、核心业务人工验收和阻断性回归检查。

### 7.5 日常长时间开发

一天内持续开发多个步骤，可以白天连续开发、晚上或阶段结束时统一跑一轮较完整 QA。全量回归不应成为白天每个小步骤之间的串行等待环节。

## 8. 用户零运维原则（长期强制规则）

### 8.1 核心原则

**产品负责人不是项目运维人员。除首次云资源授权、账号创建、白名单、安全确认等确实无法由系统代办的一次性动作外，不应要求产品负责人反复 SSH、复制 SQL、修改 systemd、执行 curl、手工部署或人工排查服务器。**

偶发、不可自动化且确有必要时，可以请求产品负责人执行一次明确操作；但这必须是例外，不能成为常规开发流程。

### 8.2 必须自动化的事项

以下工作原则上由代码、后台、脚本或 CI/CD 完成，不交给产品负责人：

- 建表、加字段、数据库结构升级；
- 批量脚本/资料导入、去重、upsert、数据验收；
- 服务启动、停止、重启；
- Git 拉取、reset、版本切换；
- systemd 配置更新；
- 端口、curl、API、数据库健康检查；
- 正式版本切换和回滚；
- 部署失败后的恢复；
- 重复性的数据库权限/结构检查。

### 8.3 “出现两次就自动化”规则

**任何人工运维步骤，只要在项目中出现第二次，就必须优先判断能否转成自动脚本、后台能力、migration 或 CI/CD；能够自动化的，不允许继续把同样操作交给产品负责人。**

### 8.4 基础设施故障诊断规则

遇到服务器、数据库、部署等基础设施问题时：

1. 先收集足够的诊断证据，再下结论；
2. 不允许基于未经验证的猜测连续让产品负责人执行试错命令；
3. 如果确实需要人工执行诊断，优先提供“一次采集完整诊断信息”的命令，而不是“一条命令 → 截图 → 再猜 → 再一条命令”；
4. 每次人工操作前必须说明目的、风险和预期结果；
5. 能在 Preview、临时端口或隔离环境验证的，不直接在正式环境试错；
6. 生产环境发生故障时，第一优先级是恢复已知稳定版本，不一边修复一边继续叠加新功能。

### 8.5 数据导入规则

长期目标流程：

`后台上传 Excel → 自动字段校验 → 数据体检/预览 → 自动去重 → 事务写入 RDS → 自动验收 → 展示导入结果`

产品负责人不应因为新增一批脚本而进入 DMS、执行大段 SQL 或 SSH 到 ECS。

### 8.6 数据库结构规则

数据库 schema 变化必须版本化管理（migration）。新增表、字段、索引、约束等应跟随代码版本自动升级并保留迁移记录，不依赖聊天中临时生成 SQL 再由产品负责人手工执行。

### 8.7 生产部署规则

生产部署采用“先验证、后切换”原则：

`构建/拉取新版本 → 隔离启动新版本 → 自动健康检查 → 数据库/API 验证 → 全部通过 → 切换正式流量 → 上线后复检`

任何预检失败都不得影响当前正式版本。切换失败必须自动恢复旧代码、旧服务配置和旧流量状态，不允许把正式站留在 502。

### 8.8 产品负责人应看到的状态

工程系统应尽量把复杂状态收敛成产品负责人容易理解的少数状态：

- 开发中；
- 等待产品验收；
- 正在安全发布；
- 已正式上线；
- 发布失败但正式旧版正常。

不应要求产品负责人理解或持续跟踪 workflow run、systemd、端口、进程、psycopg 等工程细节。

## 9. 自动判断是否应该合并 main

出现以下任一情况必须主动判断当前 PR 是否应收口：

- 一个相对完整产品阶段开发完成；
- PR 已明显变大，继续叠加会增加回归风险；
- 自动测试、Frontend QA、Preview 已具备完整验收条件；
- 准备开始边界清晰的新功能；
- 产品负责人连续要求“继续”时，不能只无限堆代码。

同时满足阶段范围完整、测试通过、Preview 成功、核心业务无阻断回归、无已知高风险问题、后续可自然拆分时，应主动提示“当前 PR 已达到可合并状态，建议合并 main”。达到门槛后只建议合并；必须收到产品负责人明确授权后才执行。

## 10. 状态标记规则

- `[ ]`：未完成；
- `[x]`：已有明确实现/规则/工程底座；
- 不因为“代码存在”就把业务验收标为完成；
- 无证据时宁可保持未完成，不猜测。
