每次开始或继续开发：

1. 先读本看板；
2. 再读相关业务规则和工程规则；
3. 读取当前 main、开发分支和 PR 的真实状态，不按聊天记录猜代码；
4. 判断任务属于 P0/P1/P2；
5. 做 Build vs Reuse；
6. 优先解决当前 P0，不擅自扩 scope；
7. 自动测试要与开发阶段匹配，不得因为每个小 commit 都跑全量 UI 回归而阻断连续开发；
8. 每完成一个相对完整阶段，都自动判断是否应该合并 main；
9. 完成后更新本看板和必要的技术决策记录。

## 8. 开发与验收节奏（长期规则）

### 8.1 核心原则

**先形成可见、可用的完整功能闭环，再集中验收；测试服务于开发，不让开发服务于测试。**

脚本推荐这类跨数据库、API、前端页面的功能，不能每完成一个小步骤就停下来等待整套 Playwright / Preview。产品负责人应尽早看到完整页面和真实业务流程。

### 8.2 开发过程中：快速自检，不跑全量回归

连续开发期间，只做与当前修改直接相关、能快速完成的检查，例如：

- Python / JS 语法与模块加载；
- 新增单元测试或目标测试；
- API 能启动且核心接口不报错；
- 页面能打开、核心组件能渲染；
- 当前修改涉及的关键路径做定向检查。

**原则上不要因为每一个小 commit 都等待完整 Frontend QA / 全量 Playwright / Preview Deploy 才继续下一步。** 即使 GitHub workflow 因 push 自动触发，也不需要停下开发等待结果，除非它暴露的是会阻断后续开发的基础性错误。

### 8.3 一个完整功能闭环完成后：阶段性 QA

当一个用户能实际使用的闭环完成后，再集中运行相关自动验收。例如脚本推荐 V1 的闭环是：

`真实脚本数据 → 推荐 API → 推荐列表 → 脚本详情 → 一键脚本改写 / 小红书排版 → 埋点`

此时运行相关 Playwright、后端测试和 Preview，并让产品负责人实际体验页面。

### 8.4 PR 收口 / 合并 main 前：全量 QA

准备收口 PR 时必须运行完整质量门禁：

1. 后端 / 单元测试；
2. 完整 Frontend QA / Playwright；
3. Preview Deploy；
4. Preview 核心业务人工验收；
5. 阻断性回归检查。

只有这一阶段的全量 QA 是合并 main 的硬门槛。

### 8.5 日常长时间开发

如果一天内持续开发多个步骤，可以白天连续开发、晚上或阶段结束时统一跑一轮较完整 QA。全量回归不应成为白天每个小步骤之间的串行等待环节。

如果自动 workflow 已经触发但当前功能尚未形成闭环，可以继续开发；后续新 commit 会自然触发新的有效验收结果。不要为了修复明显已经过时、且马上还会被当前开发继续改变的测试断言而频繁打断产品开发。

## 9. 自动判断是否应该合并 main

出现以下任一情况必须主动判断当前 PR 是否应收口：

- 一个相对完整产品阶段开发完成；
- PR 已明显变大，继续叠加会增加回归风险；
- 自动测试、Frontend QA、Preview 已具备完整验收条件；
- 准备开始边界清晰的新功能；
- 产品负责人连续要求“继续”时，不能只无限堆代码。

原则上同时满足以下条件时，应主动提示：**“当前 PR 已达到可合并状态，建议合并 main。”**

1. 当前阶段范围完整，无必须同 PR 完成的阻断项；
2. 后端 / 单元测试通过；
3. Frontend QA 通过；
4. Preview Deploy 成功；
5. Preview 核心业务无阻断回归；
6. 无已知高风险数据、权限、安全或生产配置问题；
7. 后续工作可以自然拆到新 PR。

如果未达到门槛，必须明确说明还差哪一项。

达到门槛后只**建议**合并；不得自行合并。必须收到产品负责人明确“可以合并 / 合并 main / 上线”等授权后才执行。合并后继续核对 main QA、正式部署和 Production 健康检查。
