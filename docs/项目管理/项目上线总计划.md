# AIA Auto IP 项目上线总计划

> 更新时间：2026-08-20
> 适用范围：AIA Auto IP Web 正式可用版本，以及后续日常迭代。

## 1. 项目目标

AIA Auto IP 是面向友邦营销员培训与日常使用的 AI 内容工作台。当前产品主线不是房地产数据看板，也不是通用 AI SaaS；上线目标是让营销员可以稳定完成以下四类任务：

1. IP 人设；
2. 内容规划；
3. 脚本改写；
4. 小红书排版。

项目同时需要满足培训现场可用、移动端可用、AI 输出可控、合规规则可追溯、生产环境稳定等要求。

## 2. 当前真实基线

截至 2026-08-20，main 已具备：

- `web/`：原生 HTML / CSS / JavaScript 前端；
- `server.py`：Python 服务与 API 入口；
- DeepSeek API 接入；
- 正式环境阿里云 RDS、Preview 独立 SQLite；
- `rules/`：合规、字段、IP onboarding、内容规划 onboarding；
- `src/`：compliance、fields-schema、prompt-engine 等可复用模块；
- Playwright + axe-core 自动验收；
- GitHub Actions Frontend QA；
- Preview 独立部署与诊断工作流；
- main QA 通过后自动部署 ECS，并带健康检查和失败回滚；
- 已建立工程效率、复用、公共组件、通用交互等长期规则。

当前不采用“为了工程化而重写 React/Vue”的路线，继续渐进式完善现有轻量技术栈。

## 3. 上线定义

“代码已经部署”不等于“项目已经上线完成”。AIA Auto IP 的上线完成必须同时满足：

- 四个核心功能达到本期约定的业务范围；
- 培训现场核心路径可完整跑通；
- 手机端基础交互稳定；
- AI 输出符合业务规则和合规规则；
- 资料、历史版本、异常状态符合现有产品规则；
- 自动测试覆盖核心工程问题；
- Preview 与 Production 隔离；
- 正式部署、健康检查、失败回滚可工作；
- 关键技术决策和上线状态有文档记录。

## 4. 上线阶段

### 阶段 A：产品主流程收口

目标：四个功能的“能不能用”收口为稳定业务流程。

重点：

- IP 人设：资料匹配、缺失资料补充、生成、自然语言修改、历史恢复；
- 内容规划：复用 IP 档案、首次流程、生成、历史恢复；
- 脚本改写：输入 → 改写 → 可复制结果，严格按现有内容规则；
- 小红书排版：输入 → 排版 → 可复制结果，严格按现有内容规则；
- 不在本阶段扩张非必要功能。

### 阶段 B：移动端与公共交互收口

目标：不再依赖产品负责人逐个发现键盘、焦点、滚动等基础 Bug。

重点：

- ChatWorkspace / Composer / QuickChoices 等公共行为统一；
- 标签选择不错误唤起键盘；
- 已选标签位于输入容器；
- 新消息自动跟随，查看历史时不强拉；
- Loading / Empty / Error / Disabled；
- 360–430px 常见窄屏；
- 长文本、溢出、触控区域、可访问性。

### 阶段 C：AI 与合规收口

目标：AI 不仅“能返回”，而且业务上可用。

重点：

- Prompt 与规则文档保持一致；
- 固定合规要求不依赖模型临场发挥；
- AI 超时、失败、空结果、格式异常有明确处理；
- 不把营销员编号错误用于公开执业编号；
- IP、内容规划、脚本、小红书输出分别按对应规则验收。

### 阶段 D：数据与历史状态收口

目标：培训现场重复进入、修改、刷新后不会丢失关键业务状态。

重点：

- 正式 RDS 路径验证；
- Preview 不接生产 RDS；
- 已生成/已调整方案可恢复对应完整版本；
- 资料修改有明确确认与保存逻辑；
- Guest 与正式营销员数据边界明确；
- 敏感配置不进入仓库。

### 阶段 E：自动验收与发布链路收口

目标：普通工程问题由自动化承担。

当前已有：Playwright、axe-core、Frontend QA、Preview、ECS 部署、健康检查、回滚。

上线前继续确保：

- smoke；
- onboarding；
- content planning；
- classroom journey；
- chat interaction；
- mobile boundaries；
- async states；
- main QA → production deploy 链路稳定。

### 阶段 F：业务验收与正式发布

产品负责人重点验收：

- 内容是否对；
- AI 是否理解业务；
- 培训流程是否顺；
- 页面是否符合业务使用场景；
- 结果是否值得营销员实际使用。

不要求产品负责人重新逐项承担基础浏览器、响应式、键盘、焦点、Loading/Error 等工程验收。

## 5. 上线优先级

### P0：不上线就会影响使用

- 四个核心功能主路径；
- 移动端核心交互；
- AI 失败/超时处理；
- 合规硬规则；
- 正式数据库与资料安全；
- CI/CD、健康检查、回滚；
- 培训现场核心旅程。

### P1：上线后应尽快完善

- 更完整的自动化覆盖；
- 重复前端逻辑继续组件化；
- 更系统的后台管理能力；
- 日志、运营与异常诊断体验；
- 用户/权限体系按真实对外使用需求逐步完善。

### P2：未来扩展

- 微信小程序；
- Web / 小程序共享 API、数据结构、业务规则；
- 更完整的运营后台；
- 新 AI 工具模块。

P2 不应阻塞当前 Web 培训版本上线。

## 6. 默认开发节奏

每个需求默认执行：

`读取当前任务看板 → Build vs Reuse → 开发分支 → 自动测试 → Preview → 业务验收 → 明确允许上线 → main → main QA → ECS → 健康检查 → 更新任务看板/技术决策记录`

若只是文档治理且产品负责人明确要求直接写 main，可按当次授权执行。
