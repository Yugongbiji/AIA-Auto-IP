# AIA Auto IP 技术决策记录

> 用途：记录“为什么这样做”，防止以后 Codex / 开发者因为缺少上下文反复推翻已经确认的架构。
>
> 只记录会影响长期架构、成本、安全、开发方式或跨端复用的重要决策；普通 CSS 微调、文案修改不记录。

## ADR-001：当前 Web 保持原生 HTML/CSS/JavaScript，渐进式工程化

**状态：已采用**

**背景**：当前 `web/` 已有可运行的原生 HTML/CSS/JS，实现正在用于真实产品迭代。为了“看起来现代”整体迁移 React/Vue 会带来较大重写和回归成本。

**决策**：

- 当前不强制迁移大型前端框架；
- 先通过公共组件契约、统一交互规则、Playwright 和渐进模块化降低维护成本；
- 未来只有当复杂度、多人协作或跨端收益足以覆盖迁移成本时，再单独做架构评估。

**约束**：不能把“不重构框架”理解为“继续复制代码”。重复逻辑仍必须收敛。

## ADR-002：业务创新自研，通用工程能力优先复用成熟方案

**状态：已采用**

**背景**：产品负责人的时间应集中在业务、内容、培训场景和 AI 规则，而不是 Button、上传、登录、测试、部署等成熟能力。

**决策**：新功能开发前强制 Build vs Reuse。非 AIA Auto IP 核心业务能力已有成熟组件、框架、官方方案或第三方成熟方案时，不默认从零开发。

**例外**：成熟方案明显影响成本、安全、权限、性能、业务结果或长期架构时，才升级为产品/架构决策。

---

## ADR-003：AIA 品牌视觉保留，成熟交互行为不轻易重写

**状态：已采用**

**决策**：

- 颜色、字体、圆角、间距、视觉层级可按 AIA 品牌调整；
- Button、Select、Modal、Drawer、Tabs、Upload、Table、Form、DatePicker、Pagination、Tooltip、Loading、Empty、Error 等基础交互优先成熟实现；
- 原则为“可以换皮，不轻易换骨头”。

**原因**：减少手机键盘、焦点、可访问性、弹层、滚动等基础 UX 缺陷。

---

## ADR-004：Python `server.py` 继续作为当前服务入口，但后续拆分采用渐进方式

**状态：已采用 / 持续观察**

**背景**：当前服务已经由 Python `server.py` 承载 API、DeepSeek、数据访问等逻辑，直接重写后端框架会增加当前上线风险。

**决策**：

- 当前不为了架构整洁重写后端；
- 新增明显可复用的业务逻辑优先进入独立模块；
- 当 `server.py` 的复杂度继续增长时，按功能逐步拆分，并由现有自动测试保护；
- 不进行一次性“大爆炸式”重构。

---

## ADR-005：AI 当前使用 DeepSeek API，模型和密钥通过环境配置

**状态：已采用**

**决策**：

- 当前 AI 生成继续使用 DeepSeek；
- API Key 不进入 Git；
- 模型等可变项优先环境配置，而不是散落硬编码；
- 业务 Prompt、合规规则与产品规则要可追溯。

**未来**：若更换模型供应商，优先保持业务规则与调用层解耦，不把整个产品逻辑绑定到单一模型细节。

---

## ADR-006：正式环境使用阿里云 RDS，Preview 使用隔离 SQLite

**状态：已采用**

**背景**：Preview 必须允许自动/人工验收，但不能误操作真实营销员生产数据。

**决策**：

- Production 使用 RDS；
- Preview 明确强制 SQLite；
- Preview 可复用 DeepSeek 凭证，但不得继承生产 RDS 设置；
- 环境隔离优先于“预览环境完全复制生产数据”。

**约束**：任何 Preview 改造不得为了方便而直接接生产 RDS。

---

## ADR-007：Playwright + axe-core 作为当前 Web 自动验收底座

**状态：已采用**

**背景**：项目曾依赖产品负责人逐个发现手机键盘、焦点、自动滚动等问题，成本高且容易回归。

**决策**：

- Playwright 负责浏览器 E2E / 交互回归；
- axe-core 负责基础可访问性自动扫描；
- 已建立 smoke、onboarding、content planning、classroom journey、chat interaction、mobile boundaries、async states 等测试；
- 新功能能自动验收的部分必须进入测试，不把测试债务长期转嫁给人工。

---

## ADR-008：正式部署由 main QA 成功后触发 ECS，并保留健康检查与回滚

**状态：已采用**

**决策**：

- Frontend QA 是正式部署门禁；
- main QA 成功后 GitHub Actions 部署 ECS；
- 部署后检查 systemd 服务与本机 HTTP；
- 健康检查失败自动恢复上一 commit；
- “QA 通过”不替代业务上线授权。

---

## ADR-009：Preview 与 Production 分离，产品业务验收优先在 Preview 完成

**状态：已采用**

**决策**：普通功能开发默认走：

`开发分支 → 自动测试 → Preview → 产品业务验收 → 明确上线 → main → 正式部署`

**原因**：避免在正式 ECS 上试错，同时让产品负责人看到真实网页效果。

---

## ADR-010：未来微信小程序优先共享业务逻辑、API、数据结构和设计规范，不追求 UI 代码完全复用

**状态：方向已确定，尚未实施**

**背景**：项目未来可能提供微信小程序版本，但当前 Web 仍处于上线收口阶段。

**决策**：

- 优先共享后端 API、字段 schema、业务规则、Prompt、合规规则、设计 token；
- 可共享的纯业务逻辑尽量抽离；
- Web DOM 组件与小程序原生组件不强求一套 UI 代码硬复用；
- 不因未来小程序提前大规模重构当前 Web。

---

## ADR-011：项目管理状态进入 Git，而不是只存在聊天上下文

**状态：已采用**

**决策**：项目长期维护四份管理文档：

1. 项目上线总计划；
2. 当前任务看板；
3. 上线验收清单；
4. 技术决策记录。

**更新规则**：

- 总计划：阶段/方向变化时更新；
- 当前任务看板：任务开始/完成时更新；
- 上线验收清单：每次正式发布前使用；
- 技术决策记录：重大架构/工具/流程决策发生时追加 ADR。

这样新对话或新 Codex 线程可以先读取仓库恢复真实项目状态，而不是要求产品负责人重新解释历史。
